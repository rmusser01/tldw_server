## Confirmed cause
`NotificationLifecycleProvider.tsx:140` computes a strict verification predicate (connected phase, isConnected, neither demo nor offline bypass). Both `startWork:233` and synchronous projection:533–534 translate any false verification to auth-required. Thus the observed connection.errorKind=unreachable outage is mislabeled as sign-in failure even though credentials remain valid. Actual notification error classification at shared notification-lifecycle.ts:92–103 already distinguishes401, permanent4xx and retryable network/5xx correctly; leave it unchanged.

`NotificationsRoute.tsx:74` currently uses auth-required/unavailable both as presentation and as permission to request. Simply projecting degraded would let its initial refreshInbox effect perform private list reads (`:119–168`) while the provider correctly refuses its own requests. A header-only mask would conceal the inconsistent provider/route contract. Reusing unavailable retains the gate but falsely describes an account permission denial. Gating all degraded/connecting states would block legitimate retry/catch-up while the server is verified.

## Recommended minimal implementation
Two production files, existing tests; no new store, enum, transport, timer, or auth mechanism.

1. Add required derived `connectionVerified: boolean` to the context value and explicitly omit it from NotificationRuntimeSnapshot. Expose the existing strict predicate directly on every render; do not persist/copy it into snapshot state.
2. Use one consistent derived unverified presentation state in startWork and synchronous projection. Known unreachable/network failure with configured credentials becomes degraded. True connection auth failure and existing missing-configured-auth detection remain auth-required. Preserve unrelated unconfigured/demo/bypass decisions unless a regression requires adjustment; all remain unverified and unable to request. Both callbacks/memo dependencies must include the chosen derived state: false verification can remain false while errorKind changes from unreachable to auth, so verification alone is insufficient as a dependency.
3. Evaluate known missing credentials in the synchronous projection too, so no child effect can run during a connected-but-cleared-credential render before startWork sets auth-required. Reuse existing authStorage detection/events rather than new token parsing or config policy.
4. In the route derive `canRequest = connectionVerified && !isTerminal`. Use that for list/preferences dispatch and retries, mutation entry guards (mark/read/dismiss/snooze/cancel/preference/retry), and disabled controls. Preserve isTerminal for actual authentication/permission presentation. Add early guards to callbacks as well as disabled buttons; currently most mutation callbacks have no terminal guard.
5. Change the existing route stop/cleanup effect to react to loss of canRequest: abort list reads, clear retry timer, stop loading. Reuse existing generation/scope guards for late reads/preferences/mutations; test these transitions before adding any new invalidation logic. No mutation replay on reconnection. Re-verification of the same credentials starts fresh normal work through the existing effect.
6. Avoid new false text: route:537 currently renders 'Last updated before the connection was lost' for every degraded state, while an unverified projected initialSnapshot gets Date.now(). Hide this last-success claim when unverified (smallest), or use an actual successful timestamp; do not fabricate one from a fresh projection. Existing degraded/reconnecting copy can otherwise be reused, without adding a sign-in action for network failure. Do not claim private retry was dispatched while the verification gate is closed.
