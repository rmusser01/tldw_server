# UAT246 — native Character stream transport delay, read-only audit

## Observed, not attributed
The actual PG single browser displayed `BEEP BOOP.`; root separately confirmed canonical user+assistant rows after reload. The retained CDP trace has headers200 at0.304415s, no observed body until **41.461102s after headers /41.765517s after request**, then1,065,461 decoded bytes versus15,309 encoded bytes in two adjacent events. Terminal `net::ERR_ABORTED` follows those bytes. Safe projection is in native-safe-projection.json; no large body or authentication material was exported.

The frontend parser returns upon `[DONE]` and always calls reader.cancel in finally (`background-proxy.ts:1804–1807,1834–1838`). Thus this terminal network marker is compatible with normal completed-iterator cancellation; it does not establish generation failure. It also does not prove the observed request reached `[DONE]` rather than another cancellation. Successful UI/canonical evidence is separate.

## Ranked hypotheses

1. **Next rewrite compression buffering — strongest source-supported candidate.** Installed Next16.1.4 `router-server.js:110–112` enables compression unless explicitly disabled; `:205–207` applies it before the external rewrite `:359`. The compiled compression module (`next/dist/compiled/compression/index.js`, minified source offsets~2648–4750) treats text/* as compressible, writes into zlib.createGzip/default options and exposes explicit `res.flush()`, but its ordinary write does not flush. It skips transformation for Cache-Control:no-transform or an existing nonidentity Content-Encoding. `proxy-request.js:26–37,110–113` constructs http-proxy; its compiled implementation pipes proxyRes to the response without a compression flush. The configured180000ms proxy timeout only prevents premature termination, not buffering. The observed encoded/decoded ratio and single compressed burst fit this hypothesis but do not establish compression location or when upstream first yielded.

   Actual Character unified SSE headers are only no-cache/X-Accel-Buffering:no (`character_chat_sessions.py:6921–6929`); its legacy provider response (`:7006–7010`, default STREAMS_UNIFIED0 at:6395) supplies no explicit cache/buffering headers. Fallback text SSE (`:6759–6762`) only sets those headers under unified mode. `no-cache` is not `no-transform`, and X-Accel-Buffering is not consumed by installed Next compression. **Do not fix only unified mode.**

2. **Provider or upstream HTTP decoding/line buffering.** Headers precede provider iteration: Starlette sends response.start before waiting for its iterator. The local adapter forwards each complete iter_lines result (`local_adapters.py:474–490`), so upstream silence, delayed newline, or upstream content compression can also defer the first yielded line. This trace lacks provider/API-side first-byte timing and Content-Encoding. The1MB decoded total does not show whether data accumulated progressively or arrived at once from upstream.

3. **Application iterator or downstream browser aggregation.** Character `_iterate_character_provider_stream` forwards one bounded async/sync item at a time (`:497–558`). Installed Starlette StreamingResponse sends every iterator chunk (`responses.py:246–254`). Its GZip middleware explicitly excludes text/event-stream (`middleware/gzip.py:8,55–60`), and no app GZipMiddleware registration was found. These facts lower the likelihood of a deliberate backend whole-body buffer, but direct iterator tests omit ASGI/socket/proxy/browser layers and therefore cannot eliminate runtime interference or browser/CDP event aggregation.

Original246's precise cause remains unproven; this new successful request provides a concrete candidate, not retrospective attribution.
