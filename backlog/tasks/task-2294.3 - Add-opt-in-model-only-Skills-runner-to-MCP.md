## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Design and deliver the first executable MCP Skills slice as a separate disabled-by-default skills_runner module exposing one bounded model-only skills.run tool. Security review decomposed delivery into three ordered children: a generic MCP known-failure outcome, a capability-gated fixed provider/model completion adapter, and a strict single-file Skill snapshot runner. Nested tools, workflow scripts, subagents, durable Jobs, and approval continuation remain out of scope.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A separate skills_runner module exposes only skills.run, is disabled by default, has an explicit model-execution risk tier, and leaves the read-only Skills module unchanged.
- [ ] #2 A generic host-neutral known tool-failure outcome preserves sanitized isError results, correct closed/half-open neutral-versus-shared breaker semantics, safe logs, and no failure caching without Skills logic in protocol.py; prepared calls HMAC-bind an immutable execution policy, normalized key relationship, complete identity context, and detached canonical definition/scope snapshots, then perform a second full integrity and live registry check after all waits.
- [ ] #3 IdempotencyManager is extracted from protocol.py; bounded sticky ownership guarantees at-most-once callback invocation per request, strict bounded local/Redis replay parity, authenticated active-scope replay partitioning without raw IDs, a cancellation-shielded success commit, and no post-success fallback redispatch.
- [ ] #4 Only user-scoped, user-invocable, model-visible, integrity-verified fork-mode Skills with no declared tools, authored model, or directory entry beyond one regular SKILL.md are eligible under an explicit resource-bounded strict frontmatter allow-list.
- [ ] #5 One targeted mutation-checked Skill snapshot reconciles no unrelated row, validates both registry raw-text hash and canonical Context Integrity digest for skill_execution, and closes request-scoped database resources before model work.
- [ ] #6 Normal tool and Skill(name) authorization applies; tool-definition and call classification agree that skills.run is effectful, network-using, and fail-closed when rate-limit admission is unavailable.
- [ ] #7 One capability-gated injected completion port uses only explicit server-authenticated positive numeric user and optional active team/organization scope identity plus a server-generated execution ID, authoritative membership and credential-precedence resolution, a fixed provider/model, conservative quota accounting, existing egress enforcement, and breaker failure only for trusted shared-infrastructure provenance.
- [ ] #8 At most one physical tool-disabled native-async provider dispatch occurs with hard token/response/input/output/timeout bounds, retained-child cancellation containment, and no retry or fallback.
- [ ] #9 Results, failures, logs, and telemetry expose no prompt, raw provider payload, credentials, endpoint, path, client/request identifier, or raw exception content.
- [ ] #10 Documentation discloses successful output retention in owner-scoped idempotency cache, including that output may reproduce sensitive input and persistence may degrade to process-local; failures and plaintext request/prompt/argument fields are excluded while the existing argument fingerprint binding remains for its TTL.
- [ ] #11 TASK-2294.3.1, TASK-2294.3.2, and TASK-2294.3.3 are implemented and verified; nested execution remains isolated in TASK-2294.4 and TASK-2294.5.

## Implementation Notes

The first slice is intentionally model-only; nested tool execution is deferred.
Architecture refinement after repository surface review: use a separate `skills_runner` module instead of mixing an effectful tool into the static read-only `skills` risk tier. This keeps catalog/render health and concurrency isolated and makes operator opt-in visible in `/mcp/status`.

2026-07-25 security re-review validated eight design gaps: generic failures were not preserved through breaker/runtime handling; RequestContext lacked trusted credential membership scope; sync adapters could not meet cancellation; equal timeouts raced; authored model selection/retries broadened dispatch risk; token/transport bounds were unenforceable; catalog/rate classification disagreed with call classification; and idempotency/snapshot/sanitizer contracts were incomplete. The revised spec addresses all findings and decomposes implementation into TASK-2294.3.1, TASK-2294.3.2, and TASK-2294.3.3.
2026-07-25 final consistency review found and corrected three remaining ambiguities: execution now uses exact Context Integrity purpose skill_execution and a canonical filesystem digest distinct from registry file_hash; strict frontmatter has an explicit key/type allow-list including user-invocable true; and module-wide breaker failures require trusted shared-infrastructure provenance so one request's content or user-scoped state cannot disable execution for other users.
2026-07-25 deeper repository review added validated safeguards for targeted (not catalog-wide) Skill reconciliation, fail-closed billable rate admission, same-request Redis fallback duplication, strict/capped cache serialization, half-open breaker neutrality, provider-child containment, model-port identity minimization, and extraction of IdempotencyManager from protocol.py.
2026-07-25 prepared-call integrity review validated one additional generic risk: frozen PreparedToolCall currently retains unsigned mutable tool_def metadata that runtime uses for rate and idempotency decisions. The design now requires an HMAC-bound versioned immutable execution policy plus a detached canonical tool-definition snapshot before TASK-2294.3.1 implementation.
The prepared-call review then expanded the same boundary to cover normalized idempotency-key/cache-key binding, bounded scope-reporting snapshots, and live registry/module/definition revalidation. Stale or tampered prepared state now fails before admission or dispatch.
2026-07-25 credential-scope review corrected an over-minimized model identity: user_id alone cannot preserve TASK-12963's active team/organization precedence. The immutable port identity now includes only explicit server-authenticated positive numeric active scope IDs, and the adapter revalidates membership without guessing or accepting request metadata.
2026-07-25 idempotency cancellation review added a bounded shielded success commit. After a valid callback result, canonical local replay commits before Redis awaits; cancellation or remote finalization failure cannot discard that process-local result or re-enter the paid callback.
2026-07-25 active-scope replay review confirmed current MCP idempotency keys are user-scoped only. The design now adds an HMAC-bound digest of explicit authenticated active team/organization scope, preventing same-user cross-scope replay without exposing raw IDs or changing personal/no-scope key compatibility.
