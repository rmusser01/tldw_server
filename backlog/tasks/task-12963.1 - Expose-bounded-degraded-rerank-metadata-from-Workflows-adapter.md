## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The standalone Workflows rerank adapter creates a fresh advanced reranker without an LLM client, then serializes only ScoredDocument fields and drops reranker.last_metadata. TASK-12963/PR #2727 makes missing or failed LLM reranking fail closed by preserving the original document order and scores, so the remaining defect is observability: workflow callers cannot distinguish a successfully applied requested strategy from a safe degraded no-op. Add a backward-compatible, bounded degradation envelope at the adapter boundary without introducing provider fallback, automatic generation gating, or raw provider/config/credential diagnostics.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 When the underlying reranker reports degraded=true, the adapter returns an additive bounded reranking envelope containing only degraded, failure_code, and verification_available; arbitrary backend metadata, exception text, provider configuration, endpoints, and credentials are not serialized.
- [x] #2 A degraded llm_scoring or two_tier call preserves the original document order and scores and does not emit calibration, sentinel, fused, calibrated_prob, or gated fields.
- [x] #3 An adapter-boundary regression covers the missing-LLM-client path from create_reranker through the serialized workflow result.
- [x] #4 An event-gated asyncio concurrency regression runs a degraded and a healthy rerank call together and proves their result metadata cannot bleed across requests.
- [x] #5 Existing documents, count, strategy, and query output keys remain backward compatible, and the change does not add provider retries, config fallback, or automatic Workflows generation suppression.
<!-- AC:END -->

## Implementation Notes

<!-- SECTION:IMPLEMENTATION_NOTES:BEGIN -->
- 2026-07-15 investigation: exact flow is `Workflows/engine.py:_run_step_adapter` -> `Workflows/adapters/content/rerank.py:38-198`. The adapter resolves query/documents, calls `create_reranker(strategy, config)` without `llm_client` at lines 174-175, serializes `ScoredDocument` values at lines 177-187, and returns only documents/count/strategy/query at lines 189-194. The engine persists that exact dict as the step output and next-step `prev`/`last` context. No Workflows code consumes `gated`, `verification_available`, or reranking calibration. Use an allowlist rather than copying `last_metadata` wholesale. Each adapter call already creates a fresh reranker, so retain that ownership model and verify event-gated concurrency isolation. This is P3 observability only after TASK-12963's local missing-client fail-closed fix is committed; PR #2727's currently pushed SHA a28b5bdf56 does not yet contain that local fix.
- 2026-07-16 implementation: the Workflows rerank adapter now adds a `reranking` envelope only when its per-call reranker reports degradation. The envelope is constant-bounded to `degraded=true`, `failure_code=provider_unavailable`, and `verification_available=false`; raw reranker metadata is never copied. Existing documents/count/strategy/query output remains unchanged for healthy calls, and degraded output retains the reranker's fail-closed document order and scores. Adapter exception logging now records only the exception type, not exception text or provider diagnostics.
- TDD evidence: the four focused regressions first failed as expected (three missing `reranking` failures plus one raw-secret log leak), then passed 4/4 after the minimal production change. Final widened rerank selectors passed 11/11 with `PYTHONHASHSEED=12963` and 11/11 with `PYTHONHASHSEED=2727`. AST parse, Ruff for both touched files, scoped `git diff --check`, and Bandit for the production adapter all exited 0.
