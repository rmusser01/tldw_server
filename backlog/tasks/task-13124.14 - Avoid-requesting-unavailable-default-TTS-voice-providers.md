## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Retained real-backend UAT repeatedly logs GET /api/v1/audio/voices/catalog?provider=kitten_tts 404 Provider not found or unavailable whenever Chat loads. The WebUI requests a provider-specific catalog before establishing that the backend exposes that provider, generating avoidable console errors and potential Next dev issue-counter noise.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Chat does not request the kitten_tts catalog when that provider is unavailable.
- [x] #2 Available TTS providers still load their voice catalogs normally.
- [x] #3 The retained Chat workflows pass against the real backend without the kitten_tts 404.
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Trace voice-provider initialization and catalog fetching; capture a failing unavailable-provider regression; gate catalog lookup on backend capability or handle unavailable defaults without an error request; rerun focused and live Chat workflows.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
TDD covered both capability-loading and health-loading races. Provider-specific catalogs now wait for capability discovery and audio health, suppress providers whose normalized capability envelope reports disabled/failed/unavailable, and fail open for older or unreachable health endpoints. Hook suite: 14 passed. Both retained Chat workflows passed in 2.0 minutes; captured console showed no kitten_tts request after the cold-load fix.
