Bob review-entry snapshot shows blocking modal Request was aborted during token refresh for flashcards analytics, plus auth/sessions401 polling. Backend log PDT03:21:29.474 and03:23:03.442 reports Database is temporarily locked in SessionManager.refresh_session, then auth.py converts to invalid-session401. Independent diagnosis ongoing; no session-eviction claim or session-limit changes. No implementation until frozen matrices finish.

Stronger read-only cause: refresh_token uses Depends(get_db_transaction), whose SQLite path opens BEGIN IMMEDIATE for the request, then SessionManager.refresh_session calls AuthnzSessionsRepo.update_session_tokens_for_refresh with a second transaction against the same DB. The outer writer lock blocks the inner refresh. Existing get_login_db_connection avoids this exact separate-service self-lock. Alice03:19:33.937 and Bob03:21:29.474 Pacific logs confirm the sequence. Reuse non-locking request reads while preserving inner atomic refresh/CAS and replay/revocation controls; require a real SQLite request regression, not mocked token success. This supersedes the initial external-contention hypothesis.

Parent frontend source trace: request-core constructs AbortError for caller cancellation during refresh, then its catch flattens name/code into status0 plus text. request-events strict cancellation matcher does not match the trailing during-token-refresh phrase, so background-proxy dispatches backend-unreachable. Preserve structured caller cancellation; do not hide genuine deadline timeouts by treating every AbortError alike. useServerOnline continues checkOnce on disconnected interval; connection.tsx only early-gates missing single-user auth, while multi mode always selects auth/sessions. Refresh helpers also collapse status into generic errors and retry with stale tokens. Scope terminal credential clearing to authoritative refresh rejection, preserve retryable status and avoid replaying unsafe application writes without proof.
