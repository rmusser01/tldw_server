## Independent canonical source history

The requester approved the independent Notes/Sync design on 2026-10-06. [ADR065](../ADR/065-independent-notes-knowledge-provenance.md) records the decision. A strict, independently versioned `notes.provenance` record now belongs to its canonical note and authenticated owner; the existing core-note v1 payload is unchanged. A normal Markdown update omits history and preserves it. Canonical active history wins over a conflicting portable marker, while a retained history tombstone forbids marker fallback.

Sourced saves check both current versions and commit the note, history and organization changes in one Notes transaction. Active Sync uses its existing durable groups and a shared pair projector, with recovery between product commit and Sync checkpoints. Inactive Sync uses owner-scoped durable receipts in the same local transaction, so an unchanged request identity recovers the original acknowledgment after later edits. Receipt migrations are SQLite76/PostgreSQL80; the records themselves use SQLite75/PostgreSQL79. Local receipts remain retained after note purge to prevent an old retry recreating a removed note; their unbounded retention is an operational limitation.

Old clients can delete a note without advertising the new capability: deletion also tombstones its history. Restoring the core note leaves history deleted. The separate retained-history restore requires an active owned parent, its exact current version and the retained child version/hash. It advances both heads and accepts no replacement payload. Read, export and acknowledgment replay apply the same active Sync encryption policy and current attestation gate as writes before exposing canonical history or markers.

JSON/CSV exports serialize active canonical history into a validated portable marker, including after an old editor removed that marker from Markdown. Deleted history cannot be revived by export/import. Source IDs, URLs and retained excerpts remain descriptive evidence; they grant no source-read permission and do not establish that a source is still accessible or current. Owner tests use production per-user SQLite files, plus forced PostgreSQL owner RLS; these tests do not qualify legacy co-resident multi-owner SQLite access.

Enrollment captures provenance-bearing parents and the exact existing edit target, preserving their owned versions. Unrelated large plain Notes do not block an otherwise valid sourced save. If the required parent is missing or exceeds the existing Sync envelope ceiling, the save fails visibly rather than inventing an accepted base.
