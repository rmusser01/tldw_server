## Findings

### R1 — P2: Keep recoverable asset claims on soft delete

**Document:** lines **85** and **146**. Line 85 groups soft, hard and bulk deletion together and says deletion releases claims. Line 146 makes released, unowned candidates eligible for byte cleanup. The same paragraph permits an explicit chat restore but only addresses the receipt's replayability.

**Failure scenario:** Fork a chat with a retained original document or generated image; soft-delete the child into trash; cleanup releases/unlinks its independent native bytes; restore the child. Restore makes the conversation live again, but the originally ready child's required asset revisions have been destroyed. Keeping the creation receipt `gone` correctly prevents accidental recreation, but it does not make the restored chat usable or recover its assets.

**Actual source:** `tldw_Server_API/app/core/DB_Management/chacha/conversation_store.py:1248-1255` soft-deletes by flipping the conversation flag; `:1318-1325` restores that same conversation by clearing the flag. `tldw_Server_API/app/api/v1/endpoints/character_chat_sessions.py:7885-7891` exposes “Restore chat session from trash” and `:7922-7937` restores/returns its existing state. Embedded image rows are independently preserved until actual row deletion (`ChaChaNotes_DB.py:1164-1170`); immediately releasing the proposed external claims would give external assets a different, destructive trash lifetime.

**Bounded repair:** Separate receipt tombstoning from asset retention. Soft delete should burn the creation receipt and deny ordinary access but keep recoverable claims/bytes charged to storage. Restore reactivates access to those retained claims without making the creation operation replayable. Release claims only on hard purge or an explicit documented irreversible retention action. Apply this rule to bulk/workspace trash as well as single-chat deletion. Add an acceptance case that runs cleanup between soft delete and restore and verifies exact document/generated bytes remain usable; hard purge should reclaim them while replay stays `gone`.

### R2 — P2: Fence physical publication as well as DB adoption during reclamation

**Document:** lines **73**, **79**, **94**, **144-146**. Generation CAS and `reclaiming` stop a stale worker from adopting a child, but the chosen filesystem writer does not consult those states. The stated cleanup sequence can finish before that stale worker's external publication finishes.

**Failure scenario:** Attempt A pauses inside `commit_upload` before its final rename. A's lease expires; same-key recovery fences A, records its candidate `reclaiming`, observes/removes an absent final object and completes cleanup/release. A resumes and publishes its final blob, then fails the generation CAS. No child is created, but bytes now exist after cleanup considered the candidate reclaimed; repeated abandoned attempts leak storage and invalidate reservation/release accounting. The same issue applies to a slow chunk writer after upload-directory cleanup.

**Actual source:** `tldw_Server_API/app/core/Sync/v2/blob_store.py:77-126` assembles and publishes with `temp_path.replace(final_path)` at `:122`, with no database-generation check or shared GC lock. `delete_namespace_blob` uses a `blob-gc` file lock at `:275-285`, but the publisher never acquires it. Its absent-object outcomes at `:293-295` and `:337-338` do not prove a paused publisher cannot subsequently create the object. Upload chunks also require explicit `discard_upload` (`:380-388`); successful publication does not remove them automatically.

**Bounded repair:** Specify one native per-candidate I/O guard shared by every chunk/final publisher and reclaiming worker. A publisher checks the durable attempt/candidate state while holding that guard before writing, and cleanup marks the candidate non-adoptable before waiting for the same guard outside the chat transaction. After previous writers have drained, cleanup removes both exact final bytes and per-attempt upload chunks and only then finalizes reclamation/releases physical storage accounting. Equivalent explicit writer-drain/reconciliation semantics are acceptable. Merely adding another DB CAS after `commit_upload` is insufficient. Add barriers before chunk publication/final rename to prove that cleanup cannot be followed by an untracked late write and that a resumed generation uses a different namespace.

### R3 — P2: Define the quota authority behind the claimed existing owner budget

**Document:** lines **94**, **146** and **148**. The design says staging counts against the same existing owner storage budget and quota reservation/release is transactional with ChaCha candidates/claims so concurrent preparation cannot exceed that budget. It does not identify how those ChaCha reservations participate in the existing quota authority, which is elsewhere.

**Failure scenario:** An owner has 10 MiB available. H2 reserves/prepares 8 MiB in ChaCha while an existing generated-file upload checks the same owner's quota and writes another 8 MiB. The existing consumer cannot see the native reservation; a ChaCha-only candidate lock cannot serialize its check. Committed H2 bytes likewise remain absent from existing counters until a separately defined update/recalculation occurs. Native preparations may serialize correctly against each other while still exceeding the budget that the document says they share.

**Actual source:** `tldw_Server_API/app/services/storage_quota_service.py:201-215` checks cached values or `users.storage_used_mb`/`storage_quota_mb` in AuthNZ. Its combined user/team/org checks are separate at `:706-733`. `register_generated_file` checks that service at `:859-865` and updates usage separately at `:889-896`. `calculate_user_storage` scans directories then independently rewrites AuthNZ counters at `:106-151`; it does not read native pending reservations. The existing byte helper explicitly calls this service before writes (`tldw_Server_API/app/core/Storage/generated_file_helpers.py:178-207`). None of these paths share a ChaCha candidate transaction.

**Bounded repair:** State the authoritative budget and accounting boundary explicitly. If this is the existing aggregate user/team/org budget, add a small operation-keyed reservation/accounting integration in that existing owner service before native byte I/O, with idempotent reconciliation for reserve/adopt/release and its crash boundary; it must be visible to other consumers and usage recalculation. If H2 intentionally offers transactional protection only for native candidates/claims while retaining existing cross-feature quota semantics, say so and remove the stronger shared-budget guarantee. Do not place AuthNZ/network work inside the chat commit or silently create an unrelated second full allowance. Qualify the chosen semantics with concurrent native and existing-consumer admission plus crash/reconciliation accounting tests.

## Additional assessment

No hidden cross-owner or live-source fallback is required by the reviewed contract: owner mismatch, unsupported projections, enrolled Sync routing and legacy atomic-protocol conversion are explicitly closed. Implementation must still enforce those gates; this review is not runtime qualification.

The operation-before-conversation contract and the conversation-before-native-asset contract are compatible as stated for fork admission. Preserve that full order in cleanup/deletion implementation, and account for existing row-first writers when deleting message graphs. The concrete reclamation defect above is a physical-writer fencing gap, not a recommendation to add old-message row locks after the conversation fence.
