# H2 explicit native asset retention refinement: bounded review

Reviewed source: worktree `.worktrees/chatbook-h1-history-design`, base `ac76c4bc5b035561bf816009c1326a114e87def9`. This is a source/design review only; no repository edits or tests. Paths below are relative to that worktree.

**Verdict: the proposed ownership boundary is sound and is a scoped refinement of D2.** No inherent P1/P2 remains in the architecture if promotion commits complete independently owned native bytes/claims before the fork capture is accepted. An authorized download followed by explicit upload is a new user-submitted copy. Once its native retention transaction commits, external MediaDB/CollectionsDB deletion or revocation is no longer an authority dependency of that native copy. Fork authorization then concerns the native source conversation, immutable native asset revision and child adoption—all in ChaCha. This removes the cross-database revoke/adopt race rather than disguising it as a distributed transaction.

D2's constraints still apply: no silent promotion/fallback, no one-shot export consumption, existing ingestion limits, exact selected revisions, independent asset lifetime, truthful strict/degraded admission, no model work inside fork, and native source authorization/deletion checked at commit. Both clients must implement the retention UI and typed manifest; a server-only API with old string/event rendering does not close rich H2.

## Three concrete P2 integration requirements

1. **Do not treat a successful existing Media ingest as completed native retention.** Existing `process_documents.py:90–94` uses MediaDB; original persistence in `Ingestion_Media_Processing/persistence.py:3368–3393` writes StorageBackend + MediaFiles separately. That return value is not a ChaCha asset claim. The retention action needs a narrow native destination adapter using the existing validated upload machinery, followed by an owner/fence transaction that attaches native immutable claims to the source chat. It must retain actual bytes in the native managed namespace, not preserve a MediaFiles path. Until that adoption is observed/reconciled, the client cannot recapture the source as rich-fork-ready.

2. **Do not re-upload extracted text as an original PDF/DOCX.** `apps/packages/ui/src/services/chat-document-processing.ts:695–702` replaces `UploadedFile.content` with extracted text while preserving original filename/type/size. Its `asUploadFile` at `:211–220` then encodes non-data-URL content as UTF-8 using that old filename/MIME. Reusing it blindly for “Retain attachments on server” would corrupt representation/fidelity. The typed promotion input must distinguish original binary, extracted text/OCR snapshot, and image revision; use exact actual byte length/MIME/hash. If historical original bytes are gone, retain only the explicitly chosen text representation, restore/re-upload the original, or show reviewed degradation. Never label text retention as original-document parity.

3. **Bind promotion to the chosen asset revision and drop executable foreign references.** Freeze bytes/hash and selected revision before asynchronous upload. A late completion must not attach to a changed chat/account/workspace or silently replace another selected image/document version. Generated request metadata currently includes `referenceFileId` (`hooks/chat-modes/normalChatMode.ts:337–366`), and event metadata contains artifact `fileId` plus variant index/count (`hooks/chat/useChatActions.ts:1158–1219`). These are not native asset identity. Runtime refine/send references must resolve to new native claims or be unavailable; preserve only safe inert historical provenance. After promotion, recapture/review the native manifest and reject an old pre-promotion selection digest.

These are concrete implementation traps in current reusable paths, not objections to explicit retention itself.

## Exact existing seams to reuse

- Browser upload transport: `services/chat-document-processing.ts:430–460` uses `bgUpload` with multipart `files`; `:223–233` converts data URLs to File. Reuse transport with captured request-owner scope and representation-aware bytes, not the extracted-text-as-original behavior above.
- Capability/limits: `core/Ingestion_Media_Processing/document_upload_preflight.py:34–36,131–185`, exposed by `endpoints/media/document_upload_processing.py:52–67`.
- Validated upload sink: `core/Ingestion_Media_Processing/input_sourcing.py:83–111,358–403`, `save_uploaded_files(..., validator, expected_media_type_key, allowed_extensions)`; actual endpoint example at `media/process_documents.py:176–203`. This imports shared `Upload_Sink.FileValidator` and `process_and_validate_file` (`input_sourcing.py:25–31`). Reuse the helper/sink instead of adding parallel multipart parsing or invoking full analysis/chunking Jobs merely to retain bytes.
- Image validation: `core/Utils/image_validation.py:228–248` decodes/verifies supported data-URI bytes; external URL fetching is deliberately unsupported (`:249–255`). Existing native MessageCreate magic-byte/size checks are at `endpoints/character_messages.py:401–437`.
- Managed immutable bytes: the prior report's separate native-root adapter over `Sync/v2/blob_store.py:36–144` gives verified chunks and atomic byte publication without sync enrollment. Native promotion and fork adoption use ChaCha reservations/claims/GC fences; the root is separate from existing Media/Notes cleaners.
- Native ownership/CAS precedent: `core/DB_Management/chacha/note_attachment_store.py:392–460` accepts caller connection and checks owned parent. H1 selection validation uses caller connection at `chacha/message_store.py:526–548`. Promotion advances the relevant native asset/context fence; successful fork copies/adopts under the established source fence.

## Required narrow tests / semantics

- User downloads an authorized external original, external source is later deleted, then explicitly uploads those bytes: native retention and later native fork succeed, without claiming continued source linkage or permission.
- Upload source chat is deleted/revoked or its selected asset changes while upload is held: no attachment to the wrong/stale source; prepared bytes remain safely reconcilable/reclaimable. Lost retention response is not retried under a new upload identity without reconciliation.
- Browser only holds extracted text, expired/consumed image export, or image mirror with omitted preview: no false original/image readiness. Strict mode blocks; reviewed degraded/native text representation has distinct digest and send policy.
- Promotion succeeds, old selection is submitted: reject stale capture; freshly recaptured native manifest succeeds. Alternative views/assets remain untouched.
- Delete external source after native retention; delete native source after fork; delete child first: exact bytes remain available to the remaining native owner in every ordering. GC/adoption race uses the same ChaCha claim fences.
- Both shells reopen typed native assets and submit asset-dependent requests through native claims; old clients fail capability admission rather than send source IDs or silently lose the typed manifest.

**Explicit assumption:** this refinement changes the source authority only at the successfully committed explicit retention operation. External source IDs/URLs remain inert provenance afterward. Requiring external revocation to retroactively revoke already user-submitted native bytes would reintroduce the cross-database authority dependency and contradict the proposed boundary; the spec should state this clearly. Existing endpoints do not yet implement the native destination adapter, manifest or claim GC, so their completion remains real H2 work.
