## Important findings

### F1 — P2: fence retained send recovery when the native owner is invalidated

**Locations:** `apps/packages/ui/src/hooks/chat/useHistorySelection.ts:1053–1086` and `:1088–1105`; related invalidation at `:169–177` and `:715–730`. Presentation is `apps/packages/ui/src/components/Common/Playground/HistorySelectionReview.tsx:185–229`.

Changing account/connection configuration invalidates the native lease and publishes `unsupported_history_capability`, but retains the same owner/view object. `invalidate()` clears fork outcomes only. Recovery refresh checks the view and owner kind, and publishes both successes and failures using only `sameView`; the recovery effect does not depend on the invalidation epoch or qualification. Consequently already-published recovery text remains available, and a held old-owner read can republish it after invalidation. The review UI still renders the original input/result and Copy/Dismiss controls in the unavailable state.

The action side is also unsafe: `dismissRecovery()` checks only owner/conversation strings. An old displayed or retained entry can call the original durable dismissal operation after `validate_lease()` is false. This is not merely stale wording: it exposes another account's retained text and permits retiring its recovery record without a currently verified native owner. The binding spec at line 151 explicitly requires the same profile and verified owner and prohibits account changes exposing/reassigning recovery.

**Independent evidence:** `/private/tmp/h1-whole-review/recovery.test.tsx` uses the actual controller and its registered configuration subscription with mocked storage/transport boundaries. Two focused cases cover published data and held successful reads; both fail the expected-empty assertion after proving the lease invalid. `/private/tmp/h1-whole-review/recovery.log` records 2 failures, 27 unrelated filtered cases. A separate action probe proves the invalid lease and then observes one call to `dismissHistoryTurnRecovery` with the original profile/client/owner/conversation/operation; `/private/tmp/h1-whole-review/recovery-dismiss.log` records 1 failure, 29 filtered cases. This action probe demonstrates invocation of the real durable API seam; it does not claim an actual browser database was modified. The production storage method supplies the terminal update.

**Smallest correction:** apply the existing mounted/epoch/owner/profile/lease discipline to recovery presentation, success/error publication, manual refresh and dismissal. Clear only transient presentation when authority is invalidated; preserve original durable records. Reopening under a freshly verified original owner should rediscover them. Keep browser-local recovery available independently of remote account availability. Add published/held-success/held-error/manual-refresh/stale-dismiss regressions and positive original-owner/local-owner cases. A blanket deletion or server-account gate for local owners would violate the contract.

### F2 — P2: the inner positional message key still discards a retained editor

**Location:** `apps/packages/ui/src/components/Option/Playground/PlaygroundChat.tsx:1397–1398`.

The new outer timeline wrapper uses stable message/block identity, but its `PlaygroundMessage` child still has ``key={`m-${blockIndex}`}``. This is reachable with the supported legacy review ordering and with removal of an earlier legacy row whose stored parent is null; the latter does not require bypassing the explicit non-leaf graph-delete restriction.

The original scroll-away defect is repaired; this distinct list-change defect is not. The positional line predates fix1, but it remains within the mandatory whole-branch stable-identity/editor integration and was explicitly deferred for this review. `VirtualChatTimeline.edit-retention.test.tsx` tests reordering with an unkeyed substitute message, so it cannot certify the production inner child's lifetime.

**Independent evidence:** `/private/tmp/h1-whole-review/key.test.tsx` mounts the actual `PlaygroundChat` and actual timeline with a small stateful child boundary in place of the heavy message component. It types an unsaved draft into the second message, removes the preceding block while preserving the second message's ID and owner, then observes a different textarea reset to the original text. `/private/tmp/h1-whole-review/key.log` records 1 assertion failure, 37 unrelated filtered cases. This proves the actual parent's reconciliation behavior; it is not an end-to-end database deletion test or a claim that the full real EditMessageForm was used. The real form's parent-owned state inspected in `Message.tsx` has the same remount lifetime. Two earlier harness setup failures are preserved separately in `key-setup.log` and `key-setup2.log`; neither is counted as behavioral evidence.

**Smallest correction:** remove the redundant positional key or use the existing stable message/block identity. Preserve the enclosing owner/conversation remount boundary. Add an actual `PlaygroundChat`/message/form case for a retained message moving after preceding-row removal/review reorder, checking the same form/draft and stable-ID Save/Cancel. Do not add a new draft store or weaken owner changes to preserve an editor.

### M1 — P3: report post-copy record-write failure as its actual failed step

**Locations:** `apps/packages/ui/src/hooks/handlers/messageHandlers.ts:218–219`, `:281–290` (the deferred Task4.2 M2).

`observed` is assigned the successful result before `finishForkOperation`. If that record write fails, control never reaches `loadConversation`, yet the catch says “Copy saved; opening failed.” The string is hardcoded rather than using the translated history-selection outcome vocabulary, and it gives no known child ID/action. A local operation whose outcome write failed may still be presented from its older dispatching record without a candidate, even though this invocation knows the committed child.

The earlier correctness repair is present: the handler returns the known committed/legacy-completed result rather than inventing a rejected fork, and no fallback/retry is issued. The existing test at `messageHandlers.branch.test.ts:230` covers loader failure only; it does not cover the preceding outcome-write failure. Therefore this remains a Minor user-facing classification/discoverability defect, not a second copy/owner corruption finding.

Separate outcome-recording failure from opening failure, preserve and expose the known result/child in translated feedback, and avoid claiming durable outcome recording succeeded. Do not automatically repeat the fork. Add a focused finish-write failure case asserting no opening attempt, unchanged successful return, correct feedback and no second creation. This closes the exact deferred observation; a wording change only to the loader test would not.
