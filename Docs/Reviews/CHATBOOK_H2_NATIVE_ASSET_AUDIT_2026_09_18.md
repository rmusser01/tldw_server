# H2 native fork asset ownership audit

Source: `/Users/macbook-dev/Documents/GitHub/tldw_server2/.worktrees/chatbook-h1-history-design`, HEAD verified as `ac76c4bc5b035561bf816009c1326a114e87def9`. All source references below are relative to that exact worktree; suffixes are line numbers. This was source/test inspection only. No tests, applications, database operations, account actions, or repository edits were run. Character behavior internals, receipt endpoint design, and overall delivery sequencing are outside this audit.

## Finding

Native embedded message images can be copied atomically today through existing connection-aware DB primitives. Native rich assets cannot yet be treated uniformly: browser chat documents live partly in IndexedDB; ingested originals live in MediaDB + StorageBackend; image-generation artifacts live in CollectionsDB/temporary exports, with optional transient generated-file tracking in AuthNZ. Existing native image-event history is a text mirror with an optional small preview, not an owned revision registry.

H2 needs a native-owned, versioned retained-asset projection and an operation-bound preparation/adoption seam. Reusing a source file ID, export URL, path, or a byte hash without an ownership claim is insufficient. Existing storage and ingestion components supply the byte transport and validation; they do not supply the chat ownership transaction automatically.

The binding requirement is D2 at `Docs/Design/2026-09-16-chatbook-chat-parity-review-closure.md:57,71–75`: external transfer before the transaction; source/asset authorization and all child references in one chat commit; cleanup only after operation reconciliation; strict all-selected-assets fidelity by default; explicit digest-changing degraded review; block sends requiring missing content. H1 explicitly does not prove H2/H3/rich parity (`Docs/Design/2026-09-16-chatbook-h1-history-selection-design.md:15,202,215,233`; verification scope `Docs/Reviews/CHATBOOK_H1_HISTORY_SELECTION_VERIFICATION_2026_09_17.md:16,88`). `tldw-agent` has no role in this storage, runtime, browser, or model work.

## Actual asset persistence and lifetimes

### Embedded images

- `tldw_Server_API/app/core/DB_Management/ChaChaNotes_DB.py:1105–1118,1164–1170`: legacy primary bytes/MIME are columns on `messages`; multiple images are `(message_id, position, image_data, image_mime_type)` rows. Both message and image ownership cascade from the conversation. Copying bytes under fresh message IDs gives independent lifetime without an external blob pipeline.
- `.../chacha/message_store.py:984–1119`: `add_message(..., conn=...)` normalizes multi-images, checks each image against `MAX_MESSAGE_IMAGE_BYTES` (default 5 MiB), stores the primary compatibility image and all `message_images` in the caller's transaction, and advances history version. `_insert_message_images(..., conn=...)` is at `:1154–1183`. Use this path rather than repeated HTTP message creation. Do not collapse multi-images to a singular field or duplicate the legacy primary as an extra image.
- `.../chacha/message_store.py:87–173,224–241`: H1 reads chat/source/settings/message metadata and image identities in one SQL statement. Image revisions include SHA-256 + MIME, with bytes returned only for selected messages; selection fails above 32 MiB of selected native image bytes. Assets here mean embedded image rows only. It does not join MediaFiles, external generated files, document session files, or decoded image-event text.
- `.../chacha/message_store.py:1185–1266`: image append has a caller-connection path and updates the history fence; existing images can mutate independently of message row version, so preserve the content hash comparison.
- `.../chacha/conversation_store.py:1389–1396`: hard deletion deletes the conversation in a transaction; schema cascades delete its messages/images. A copied child's new rows survive source deletion, and vice versa.
- The current H1 client is intentionally narrower than the store: `apps/packages/ui/src/services/chat-history-selection.ts:461–525` admits at most one inline image, rejects documents/sources/generationInfo, and checks image magic bytes. Its native fork uses this same payload helper, rejecting nonempty metadata/tools (`:665–693`) before the multi-request copy (`:778–839`). H2 should replace that copy route with native admission while preserving explicit old-server gates.

### Documents, retained text, and ingestion references

- `apps/packages/ui/src/db/dexie/types.ts:77–128`: `UploadedFile` is browser-owned content plus processing state/control IDs; `SessionFiles` owns the file array per browser session. Draft/job IDs are lifecycle controls, not durable attachment ownership.
- `apps/packages/ui/src/hooks/chat/useFileUpload.ts:134–151` puts processed upload content into browser state; `:173–186` removal cancels job/draft work. `apps/packages/ui/src/services/chat-document-processing.ts:649–663` collects ingested `mediaId` separately as `ragMediaIds`; direct/OCR output becomes retained text and `chat_context` at `:695–705`. Cancellation at `:760–819` sends job cancellation and draft deletion. Never copy those controls into the child.
- `apps/packages/ui/src/hooks/chat-modes/documentChatMode.ts:339–362`: files are read from browser session storage and new files are persisted there; the message's `documents` field contains display metadata (filename/size/processed), not complete file bytes. H1 native send explicitly checks/rejects rich payloads at `chatModePipeline.ts:702–720`; do not infer complete native document ownership from what the mounted browser displays.
- H1's local copy is a useful projection precedent: `apps/packages/ui/src/db/dexie/branch.ts:64–122` only retains completed self-contained content with an allowlist and strips ingestion/draft IDs; `:375–398` rejects unresolved document/source/remote-image carriers and generated-image rich state.
- `tldw_Server_API/app/core/DB_Management/chacha/message_store.py:2667–2699` stores RAG citations/retrieved excerpts/settings under `message_metadata.extra_json.rag_context`. This can preserve historical displayed excerpts; a citation/media ID does not itself guarantee independently owned full document content for later retrieval. H2 needs typed retained citation/reference projection, not a wholesale metadata JSON copy.
- `tldw_Server_API/app/core/Ingestion_Media_Processing/document_upload_drafts.py:20–23,73–75,121–155,164–194`: upload handoff drafts are owner-scoped rows in separate `Databases/document_upload_drafts.db`, expire after 15 minutes, cap serialized payload at 20 MiB, and are deleted by owner/ID. They cannot be adopted as a durable child asset merely by copying their IDs.
- Permanent originals are optional, controlled by `keep_original_file`: `.../Ingestion_Media_Processing/persistence.py:3271–3289,3291–3315,3350–3393` authorizes the local processing source within the ingestion temp root, computes SHA-256, stores through the configured StorageBackend using unique `original-<uuid>.<ext>` names, then registers a `MediaFiles` row. The byte store and MediaDB commit are separate. Registration failure deletes the just-created blob (`:3394–3412`); original-file persistence can produce a warning rather than fail ingestion (`:3432–3438`). Consequently, an ingested text record or successful ingest job does not prove original bytes exist.
- `.../media_db/repositories/media_files_repository.py:22–74`: MediaFiles rows carry media ID, storage path, MIME, size, checksum, UUID/version/client ID. `get_for_media` at `:76–94` deliberately returns the latest active registration, so it cannot resolve an already-selected historic file revision. H2 must freeze the exact file-row identity/version/checksum, not call “latest original” on replay.
- `.../api/v1/endpoints/media/file.py:174–215` fails for absent registration or missing blob. A source file URL is a read route, not retained ownership. Source re-upload can replace which bytes that route serves.
- `.../Ingestion_Media_Processing/persistence.py:2609–2663` retires superseded originals only after considering retained registrations; `.../media_files_repository.py:117–136` checks **MediaFiles** references, including recoverable originals. It has no chat-reference lookup. A future chat-only reference to an old source path would be invisible to this cleanup. Either copy bytes to independently owned storage or extend the authoritative lifetime accounting; do not just add a JSON URL to the child.

### Generated images and selected revisions

- `apps/packages/ui/src/hooks/chat-modes/normalChatMode.ts:337–398`: image generation returns inline export bytes as `images`, plus `generationInfo.file_id` (the FileArtifact identity) and request metadata. The local message is the browser's retained image copy.
- `apps/packages/ui/src/hooks/chat/useChatActions.ts:1124–1235`: optional native event sync builds an assistant **text** message containing request/event metadata, variant count/index and the last provided image preview. It does not persist a complete native revision graph; it is also conditional on event sync being enabled.
- `apps/packages/ui/src/utils/image-generation-chat.ts:5–7,590–644`: the serialized event preview is omitted when its data URL exceeds 250,000 characters. File ID is optional and accepted here only as a string. A successful text event can therefore have no recoverable image bytes, even while the browser still displays an image. Loader interpretation is in `hooks/chat/useServerChatLoader.ts:386–411`.
- `tldw_Server_API/app/core/File_Artifacts/file_artifacts_service.py:338–438`: inline export stores no export path and marks it consumed; URL/fallback exports get a TTL/temp output path. Separate generated-file registration occurs only for URL/fallback exports (`:397–406`); generated image registration explicitly uses `is_transient=True` (`:440–462`). These are not immutable chat-revision lifetimes.
- `.../api/v1/endpoints/files.py:198–271`: export download validates owner via user DB, rejects consumed/expired/missing output, marks consumed before delivery, then deletes the file. Do not fetch this one-shot export as a hidden fork side effect or assume its URL is durable.
- `.../Storage/generated_file_helpers.py:316–402`: generated-image storage checks quota, creates a unique user output path, registers checksum in the generated-files service, and removes a file if registration fails. This is useful existing storage machinery but its AuthNZ registration is outside the native chat transaction.
- `.../Image_Generation/reference_images.py:55–109,143–223`: managed reference images are a **different namespace** (`MediaFiles.file_id` joined with live Media), owner path checked, bytes loaded from StorageBackend, size checked and image content probed. Do not confuse `FileArtifact.file_id`, managed reference-image `MediaFiles.file_id`, browser file IDs, or generated-file record IDs because they share a field name.
- For H2, “selected revision” must mean a captured immutable asset ID/hash plus the exact retained bytes and declarative image-generation data. Variant count/index, the latest artifact export, or rerunning the source prompt cannot substitute. A native image-event text row must be classified before the generic text allowlist; preserving it as text does not earn image fidelity.

## Required native asset addition and admission behavior

This is an asset-specific recommendation; root owns API and receipt schema design.

1. **Inventory selected retained asset representations, not just message columns.** Extend the retained projection with typed native image/document/generated-revision/citation requirements and explicit selected revisions. Keep source object identity separate from destination identity and physical content hash. An unsupported/unknown carrier stops preparation; a source with no browser cache is not evidence of absent required assets. Relevant asset identity/hash changes stale an uncommitted request; unrelated source assets outside the retained projection must not.
2. **Resolve authority through owner-scoped DB rows.** A client may name an authorized source object/revision or an already-authorized prepared asset; never submit arbitrary path/URL as file authority. Validate exact namespace, owner, source row revision, expected content hash, MIME and size. Path containment is defense-in-depth after authorization, not its replacement. Keep source credentials, signed URLs, draft/job IDs and source mutation controls out of the child. Known benign historical citation labels/excerpts may survive as display provenance.
3. **Prepare external bytes outside the chat transaction.** Use existing ingestion/storage validation and limits. Materialize independent bytes or acquire a real independently owned immutable blob reference. Persist operation-scoped prepared metadata (owner, operation, immutable source/selected revision, hash/size/type, internal destination handle, state) so a crash has a reconcilable object. Plain native image rows require no external staging. Never use current transient request/draft/export storage as final lifetime.
4. **Adopt atomically into native ownership.** The chat transaction must validate prepared identity/state and current copy authorization, remap references, and create child asset claims together with graph/settings/result/ready state. Add a small typed store under DB_Management, patterned on conn-aware attachments. Existing MediaDB, CollectionsDB and AuthNZ service calls do not join this transaction. For separate-store authority changes, a casual re-read followed by chat commit is still a race: the design needs an owner operation/asset guard honored by revocation/deletion and adoption, or must keep that representation explicitly unsupported until it has such a protocol. There must be no network/model/ingestion await inside the transaction.
5. **Make deletion and cleanup honor adoption.** The safe simple route is independent bytes under new ownership; deduplication is optional. If bytes are shared, all relevant deletion/retirement/GC paths must use committed claims plus in-flight preparation fences, not “does another source path look equal?”. Cleanup first reconciles the operation/receipt and claims; uncertain commit retains staging. A committed child must never reference a blob being reclaimed. Child deletion releases only its claims; source deletion cannot remove child bytes, and retry cannot re-adopt assets for a deleted child. Failed cleanup remains discoverable/retryable.
6. **Advertise exact capability and fidelity.** The successful H1 handshake proves selected history, not H2 asset admission. Return explicit supported asset/representation/projection versions and effective destination limits with strict preparation. Keep unsupported old nodes/clients from writing a lossy projection. A plain/images atomic subset may be a truthful milestone, but it cannot be declared rich document/generated-revision parity.
7. **Degraded copy is a distinct reviewed request.** Default strict preparation lists missing/inaccessible/over-limit assets without writing a ready child. Only explicit review may choose a degraded copy, represented by safe unavailable markers and a new digest; the strict operation must not silently become degraded. Markers can retain authorized display names/reason codes/opaque child-local identity, never dereferenceable source paths/credentials. Child text remains readable. All admission routes that require marked assets must block before provider dispatch until restore/replacement or explicit removal from context. Merely hiding a marker in the UI or deleting source metadata is not resolution. Unknown asset format should not be silently treated as an unavailable known asset.

## Concrete failure and race qualification

Run appropriate owner cases on real SQLite and PostgreSQL using the existing H1 fixture; use deterministic barriers for races and storage doubles only where a fault injection requires them. No such tests were run for this audit.

- Copy primary-only legacy images, multiple ordered images, and equal bytes under different message identities. Verify fresh child IDs, exact bytes/MIME/order on reopen, source edit/delete isolation, and reverse child edit/delete isolation.
- Mutate image bytes/MIME without changing the message row version; mutate selected generated revision; replace selected MediaFiles registration while preserving a source URL. Strict admission must reject stale selected assets; new unrelated registration outside the retained projection must not silently retarget the selected revision.
- Race an actual row-first message/metadata/image edit against fork; retain the established lock order (`message_store.py:64–76,932–979`). PostgreSQL may linearize a copy of the prior coherent committed snapshot before an in-flight edit; no mixed rows, deadlock, or phantom freshness guarantee. Reuse `test_history_selection_transactions.py:228–272` semantics.
- Inject failure after each child message/image/asset reference insert and before ready/receipt commit. Assert no visible child or adopted claim survives rollback; stage remains identifiable for reconciliation. Exact bytes surviving in unadopted staging are not a ready child.
- Crash after external bytes exist but before prepared metadata; after prepared metadata but before commit; after native commit but before response. Cleanup must distinguish orphan/aborted/pending/committed. Hold cleanup while commit races; a cleaner cannot delete committed bytes. Retry must reuse operation/asset identities, not upload again or choose “latest”.
- Delete source, revoke access/change workspace owner, or expire source export during transfer. A precommit losing operation produces no ready child; an already committed result remains independent. Lost response followed by child deletion must not restore child bytes/rows through asset retry.
- Give another user's media/file/artifact ID, another owner with same content hash, forged path, misleading filename/MIME/size, traversal/symlink/name swap, missing byte object, and checksum mismatch. No source authority may derive from URL/path/hash coincidence; cleanup may remove only the operation's exact owned staging.
- Exercise minimum/equal/just-over effective byte limits, aggregate image budget, changed limits during preparation, and quota exhaustion after concurrent preparations. Size/quota failure must precede child commit, not become a warning attached to a supposedly faithful fork.
- Copy a generated event below and above the 250,000-character preview cap; missing preview, numeric/absent fileId, consumed/expired export, and selected nonlatest local revision. Require exact available selected bytes or explicit degraded review. No generation call occurs to recover a fork asset.
- Ingest with `keep_original_file=false` or storage warning; distinguish retained extracted text/citation from promised original-document fidelity. Remove a copied context file and prove no source ingest job/batch/draft cancellation request is sent. Reopen after the original draft expires.
- Confirm degraded digest differs from strict; replay cannot alter policy. Test direct native completion, client-managed send, character send, and prepared/retry paths all reject required missing assets before provider execution; restored/replaced/explicitly removed context is admitted only with new accepted projection.
- Delete source/child in both orders with shared immutable bytes and two remaining owners; race original-file replacement/retirement with asset adoption; final last-owner cleanup removes only unowned bytes. Include imported-media path roots separately if supported. Source deletion alone must not delete child-owned original or selected generated bytes.
- Disable Sync entirely and retain native creation/reopen/usability. Attempt an old client/unsupported asset version; it must fail before any partial child write. Qualify strict rich cases separately from receipt/plain-image cases so missing unrelated model capabilities do not block native atomicity proof.

## Root follow-up: minimal synchronous staging recommendation

I support the proposed bounded synchronous mutation: existing limits provide a preparation bound; source inspection did not establish a need for a new Jobs-powered fork platform. Large or unsupported requests can fail clearly at capability/limit admission. A synchronous HTTP timeout is still an unknown operation result, resolved with the original operation key and native reservation/receipt; it is not permission to rerun under a new key.

**Concrete minimal adapter (proposed, not implemented):** add one native fork asset preparation service with caller-injected authorized source readers and a managed byte store. Keep the adoption/claim store in ChaCha DB. The closest existing reusable byte mechanics are `LocalSyncBlobStore` (`Sync/v2/blob_store.py:36–144`) used directly as a filesystem implementation, with **a separate native root**, for example `DatabasePaths.resolve_user_base_directory(user_id) / "chat_assets"`. That exact new root name is a recommendation, not an existing path. The byte class itself requires no dataset enrollment, sync account, outbox, or model; do not invoke Sync service/GC merely to instantiate it. Current StorageBackend supports only filesystem configuration (`Storage/__init__.py:33–46`), so this is a bounded choice for the audited deployment, not an invented promise for future S3 support. A later pluggable backend can implement the same narrow service contract.

Use the existing verified chunk/write/commit/verify/delete operations instead of writing a second upload endpoint, image fetcher, multipart parser, or arbitrary-path copy pipeline. Existing ingestion validation and effective size/quota policy still run. The adapter reads only bytes returned by an owner-authorized source adapter; it does not accept source filesystem paths from the fork request. For direct native image blobs, bypass external staging and use the existing `add_message(..., conn=...)` copy.

Suggested state sequence, within the root's operation-reservation contract:

1. Reserve a per-attempt opaque asset/namespace identity and expected source revision/hash/size/type in ChaCha **before any byte writes**. The native row records the intended exact physical key, never a source path. This allows recovery of a crash after byte publication but before the prepared-state update. Do not set ready just because an upload token exists.
2. Outside the chat transaction, feed bounded source bytes into `_uploads/<opaque per-asset upload token>/<index>.part`; use the existing `commit_upload(..., storage_namespace_id=...)` to publish a verified immutable candidate at `blobs/v2/<native opaque namespace>/<sha256>.blob`. Verify hash/size again as required by the selected backend; record prepared state under the attempt generation. Per-attempt tokens must satisfy the existing byte-store validators. The proposal does not assume a new arbitrary path API on media-scoped FileSystemStorage or fake Media IDs.
3. The short native fork transaction locks/CASes operation and prepared rows, validates namespace/attempt generation/status/selected projection, and installs fresh child references together with all other child state and receipt. Adoption retains the physical candidate path; there is **no post-commit rename or network transfer required for readiness**. Losing duplicate attempts have distinct physical namespaces and cannot delete the winning attempt's bytes.
4. Reconciliation/cleanup uses those same operation/prepared-row fences. An uncertain or actively owned attempt is retained. A cleaner first establishes that no committed child claim/receipt owns the exact candidate, transitions it to a non-adoptable reclaiming state, then deletes only that exact native namespace/hash outside the DB transaction. Failed deletion keeps a retryable reclamation record; no “unlink and then find out who owned it” ordering. Crash after unlink resumes idempotently. Adoption of a reclaiming object must fail/reprepare under the same operation according to the operation state machine.

**Bytes survive source/child deletion:** initially avoid cross-conversation physical deduplication. Every external child asset gets its own native namespace and verified byte copy; multiple child message refs may share that child's asset claim. The source's MediaFiles retirement, transient export expiry, draft cancellation, or original conversation cascade then has no path into the child's native root. Deleting the child releases only its child claims; byte deletion waits for no remaining claim and no active adoption fence. Embedded images survive because they are new child message/image rows. This is stronger and simpler than claiming independent lifetime from copied pointers. Any later content deduplication requires shared claims/reference accounting across every participating cleaner and is not necessary for H2.

**Explicit assumptions and remaining decision:** separate-root reuse of LocalSyncBlobStore is technically supported by the class's root argument and standalone methods, but no existing native chat asset adapter or GC integration was found or tested; it must be added and qualified. Ordinary disk loss after verification remains a storage failure, not a transaction guarantee. More importantly, copying a MediaDB/CollectionsDB object into independent native prepared storage establishes byte ownership but does not by itself prove the external source's permission/version cannot change before chat commit. The H2 spec must state when source asset authority becomes an immutable owner-authorized prepared snapshot and still revalidate the source conversation/selected native rows inside commit. If policy requires every external source deletion/revocation to invalidate preparation until the final chat commit, the external mutator and adopter need a common guard/authority token checked through ChaCha; a final unguarded cross-DB read is insufficient. Keep any representation lacking that guarantee capability-gated rather than claim cross-DB atomicity. This does not require making the fork a Jobs workflow.
