# H2 candidate reclamation state increment — 2026-09-23

Task 1.2 now has a database fence for abandoned native asset candidates. Under the owner operation lock, `claim_reclamation` locks the exact candidate and refuses active leases or live claims. An expired unclaimed candidate enters `reclaiming`, so `claim_attempt` cannot allocate another generation until cleanup finalizes it. Repeated claims return the same exact namespace/upload/hash/size descriptor. An adopted candidate on a preparing or committed operation remains untouched; a gone adopted candidate still cannot be reclaimed while its claim is live. Cleanup stays available after workspace admission closes.

`finish_reclamation` requires the matching generation, `reclaiming` state, and no live claim. If a quota reservation intent exists, a matching confirmed release intent is required before the candidate becomes `discarded`. This prevents a charged candidate from silently completing cleanup. The method is an internal database transition: the future byte adapter must drain the stable candidate writer guard and verify removal of the exact final blob and upload chunks before calling it. No physical byte removal or external quota release is implemented by this increment.
