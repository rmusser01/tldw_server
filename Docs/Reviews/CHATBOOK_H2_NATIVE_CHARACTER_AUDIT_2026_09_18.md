# H2 native accepted character/settings audit

Read-only audit of `/Users/macbook-dev/Documents/GitHub/tldw_server2/.worktrees/chatbook-h1-history-design`, source baseline `ac76c4bc5b`, performed 2026-09-18. Paths below are relative to that absolute worktree. No repository edits or tests were run. This report separates current facts from proposed H2 interfaces; it does not claim existing gates establish rich fork parity.

## Main conclusions

1. The repository already has independent, canonical accepted behavior storage and caller-transaction insertion seams. Copy those accepted records; do not call character creation or live materialization.
2. Merely copying those records does not yield a usable rich child. H1's selected-history projector rejects worldbooks, memory, exemplars, overlays, author notes and other accepted effects. The regular character completion path does **not** already consume the frozen snapshot; it reloads live cards/presets/memory/worldbooks. H2 needs a frozen projector/composer on the selected-history path and a next-send proof.
3. Keeping the source `character_id` violates deletion independence: the conversation's card FK uses `ON DELETE CASCADE`. Prefer a protected snapshot-owned conversation identity, with no card FK, over manufacturing a hidden mutable card.
4. H1's storage digest currently hashes the entire raw settings JSON. H2 needs a purpose-specific canonical retained projection so changes limited to excluded summary/prefill state do not invalidate a fork. Preserve the stricter send digest.
5. Reopen currently uses live character presentation and browser-local fork detection. H2 must identify the native child from server authority on a cold browser and supply bounded accepted presentation/settings.

D2 authority: `Docs/Design/2026-09-16-chatbook-chat-parity-review-closure.md:57` requires one native transaction containing independent settings/snapshot and prohibits normal creation/greeting/newer behavior resolution; `:71` retains declarative policies and accepted behavior while excluding mutation authority, prefill and old summary/compaction; `:75` requires SQLite/PostgreSQL and character reopen proofs. H1 design `Docs/Design/2026-09-16-chatbook-h1-history-selection-design.md:96` and `:98` explicitly distinguish authoritative context, fork-retained projection and irrelevant fence changes; `:155` and `:161` require selected rows plus preserved server-owned context composition.

## What has actually been frozen

`character_conversation_factory.py:1167` reads owned live sources at acceptance. It freezes presets including section order and templates (`:1230`), source IDs/versions, identity, all prompt fields, greetings and sampling (`:1274`), exemplars and worldbooks (`:1213`, `:1219`, `:1310`). Worldbook projection includes book attachment/priority fields and entry content/matching flags/metadata (`:860`, `:930`). Forking can use these bytes after a source edit or soft deletion without consulting that source.

Default memory (`:1249`, `:1309`) can contain explicitly accepted creation-request text and already frozen persona-memory entries. The latter projection (`:1096`) includes `memory_type`, `source_conversation_id`, content, salience and version. H2 must distinguish accepted authored memory from excluded prior summary/compaction memory using the explicit type/provenance; it must not turn source memory IDs or source conversation IDs into new write authority. If the accepted representation cannot classify a required exclusion, that is a projection limitation to specify, not permission to copy it silently.

Materialized controls (`:362`) include all applied overrides, summary policy/content, prompt/research context, greeting policy, pins, memory scope and turn-taking. Cached summary is duplicated at `:401` and in `applied_overrides` at `:403`; deleting only the public settings `summary` is insufficient. Overlay acceptance (`:1643`) freezes source identity/version plus explicit name/system prompt. It is not a full frozen persona profile. `BehaviorSnapshotV1` does not currently represent persona participants.

## Concrete proposed snapshot-owned identity

**Proposal:** add one server-protected binding mode to the conversation (e.g. nullable `assistant_binding_mode = 'snapshot_v1'`). For this mode use the existing SQL enum `assistant_kind='character'`, `character_id=NULL`, and an opaque child-local string `assistant_id='snapshot:' + child_conversation_id`. The only behavior authority remains the child's existing `conversation_behavior_snapshots` row and bound materialized settings. Validate an unambiguous accepted primary participant at binding creation; derive presentation/primary source from those accepted records. If a separate primary-participant selector is needed for multi-participant support, keep it a validated reference into the accepted participants, not another copied behavior object.

Create the mode/identity/snapshot/settings together under the fork transaction. Enforce the null card FK, child-local ID and valid child-owned snapshot invariant in the protected DB API (and a schema CHECK where practical). Expose a read-only bounded binding descriptor in detail/list responses: mode, opaque ID, accepted display name, snapshot schema/digest and settings revision. Never expose full prompt bodies in list responses. Do not permit ordinary public creation, settings updates, identity updates or legacy sync to manufacture/rebind the protected identity. Existing source IDs/versions are inert provenance inside the accepted snapshot, not live lookups.

Why this fits and what must change:

- **Hard-delete evidence:** `DB_Management/ChaChaNotes_DB.py:1049`–`:1055` defines the card FK with delete cascade. The PostgreSQL schema transformation at `:25485` removes the circular message-lineage FK, not this card FK. Snapshot tables (`:7208` SQLite, `:7256` PG) are child-owned via conversation FK. A snapshot-mode child with null card FK survives actual source-card deletion; a child retaining the source ID does not.
- **SQL/type compatibility:** current assistant-kind CHECK already permits `character`, and `assistant_id` is text (`ChaChaNotes_DB.py:3405`, `:9384`). No new assistant kind is needed. Current `ConversationStore._normalize_conversation_assistant_identity` (`conversation_store.py:326`) insists a character identity resolve to a numeric card ID; add a dedicated internal bound insertion/validation seam rather than weakening generic input validation. Its callers include `add_conversation :407`, legacy sync upsert `:546`, and identity update `:1084`.
- **Public create stays strict:** `api/v1/schemas/chat_session_schemas.py:144`/`:200` requires numeric live-card character creation. Keep that behavior and reject protected-mode spoofing. Extend read-only `ChatSessionListItem :274`/`ChatSessionResponse :319`, generic conversation response models (`chat_conversation_schemas.py:36`, `:124`) and their normalizers with the binding descriptor.
- **Filters:** `_conversation_character_scope_clause` (`conversation_store.py:277`) currently uses only card-FK nullness; snapshot character children otherwise appear as ordinary chats. Update its fixed predicates and consumers at `:859`, `:898`, `:1451`, `:1488`, `:1575` to include snapshot-mode character identities. Card-specific list/count (`:923`) should not silently treat the opaque ID as a live card. Define explicitly whether those views show independent snapshot children by authorized inert provenance.
- **Server presentation:** `api/v1/endpoints/character_chat_sessions.py:1863` (`_conversation_character_lookup_id`), `:1889` (`_conversation_assistant_names`), bulk lookup `:1913`, attachment helpers `:1966`/`:1989`, detail `:5065` and list `:7183` need the accepted-name path. Current detail reads resume state but returns only snapshot status/schema/digest; name lookup still uses the live card. Avoid loading 1 MiB snapshots per list row merely to show a name; a bounded presentation projection may be stored/indexed as derived data, never prompt authority.
- **Settings readers/writers:** `get_chat_settings :7467` strips internal authority and checks greeting against a live card at `:7518`; snapshot-mode children need accepted binding/readiness semantics. `update_chat_settings :7546` and materialization need an accepted-record mutation path for supported child edits; a title/model-only edit must not fail because the original card vanished or resolve a newer card. Changing the selected assistant deliberately is a separate explicit rebind operation, not an incidental settings read.
- **UI API normalization:** `apps/packages/ui/src/services/tldw/TldwApiClient.ts:1072` (`ServerChatSummary`) already accepts string assistant IDs, but `:5361`–`:5428` drops unknown binding fields; carry and validate the server descriptor. `hooks/chat/useServerChatLoader.ts:268` currently turns null character ID into assistant ID at `:313`, then uses `getCharacter` at `:925`. For snapshot mode preserve the distinction, skip live card lookup, and use accepted presentation. `effective-assistant-state.ts:80`–`:148` must not substitute an ambient draft's character/name/system prompt for the bound child.
- **Cold reopen:** `hooks/chat/useHistorySelection.ts:215` currently detects forks using local `findForkCandidate`; `:859` selects scoped canonical settings only for that local recognition. Recognize native binding/ready authority from the server so a different browser with no receipt still reads native canonical settings. Existing lease-fenced `services/chat-history-selection.ts:849`–`:886` is the useful read/update seam.
- **Send identity:** `core/Chat/history_context.py:92`–`:114` compares the conversation ID to participant source and casts it to int. Validate snapshot binding separately and derive original participant identity from accepted records; return no live `character_db_id` for detached children. `native-history-character-send.ts:255` constructs existing-owner requests without a `character_id` override already, so do not widen the general character-name regex just for opaque IDs. That validator (`schemas/chat_validators.py:24`, `:116`) rejects colon IDs. Public new-chat creation at `native-history-character-send.ts:169` remains the live-card route. Bind the selected owner and accepted identity, not an opaque string sent as a live card selector.

**Hidden copied card alternative:** it keeps existing numeric IDs happy temporarily, but creates a second mutable behavior surface with card CRUD, ownership, picker/list and delete lifecycle. No audited hidden-card contract removes those effects. Its prompts would still diverge unless the selected-history pipeline uses the snapshot, so it does not eliminate the required frozen composer. Avoid this alternative.

## Minimal retained-settings projector and digest proposal

Add a pure owner-side `project_native_fork_context(state, projection_policy, retained_message_map) -> ProjectedNativeForkContext` using the coherent resume read. Return validated independent settings, accepted snapshot bytes, protected binding/presentation, supported effect inventory and canonical retained-context digest. Neutral ordinary chats are valid with no snapshot and no assistant binding; do not require `roleplayResumeV1.resume_eligible` for them. Distinguish missing settings row from corrupt required settings. Preserve supported ordinary settings explicitly instead of treating any nonempty settings as a character chat or reconstructing ambient defaults.

For accepted character chats, retain exact base snapshot bytes when all its content is retained. Copy current accepted materialized overrides and validate their binding, then rebuild only projected controls/envelope via existing pure canonical builders. If the policy must remove excluded content inside the snapshot (e.g. classified summary-derived memory), build a new child snapshot and rebind the materialized envelope to its new digest; do not retain an invalid base link. Never call `_materialize_behavior`, `create_character_conversation`, provider inventory resolution, or live card/preset/book/profile readers during this copy.

Preserve accepted preset templates, worldbook definitions/policies, sampling, declarative greeting and summary settings. Strip old summary content/source ranges/timestamps/compression state from public settings, `behavior_controls.auto_summary.summary`, and `applied_overrides.summary`, while retaining normalized enabled/threshold/window policy. Avoid dropping a whole `summary` object when it is the only location of the declarative policy. Remap retained pinned **message** references or remove omitted references according to the reviewed policy; D2 excludes pinned prefill, not automatically every history pin. Pending greeting authority (`chat_settings_validation.py:85`, `:253`) is tied to source readiness and cannot be blindly copied into a ready child. No greeting is newly seeded, including an empty/before-first-message fork; only selected retained greeting rows survive. A subsequent send must not invoke the character-scoped greeting reseeder.

No persisted native prefill field was identified in the audited settings types; request continuation prefill is transient. Do not invent a legacy field list as evidence. Use an explicit projection/version for supported stored fields and classify unknown legacy data before retaining it.

`DB_Management/chacha/message_store.py:288` currently hashes raw `settings_json`, row presence, snapshot hash/status, identity and scope into the storage digest; `:307` only advertises `plain_v1` for empty settings, no snapshot and neutral identity. `:526` re-resolves the selection but therefore still sees raw excluded-setting changes as relevant. H2 capture **and** admission need the same canonical fork-purpose projection. A changed settings version triggers coherent re-read/reprojection; equal retained digest is acceptable, changed retained behavior is stale. Never relax send-purpose snapshot validation or compare only version counters. Scope/owner and protected binding remain in the digest and authorization checks.

## Storage preservation is not next-send fidelity

Current facts:

- `core/Chat/history_context.py:22` is an intentionally narrow settings allowlist. `:74`–`:90` rejects prompt context, pins, enabled summary, author note content and materialized overlay/worldbook/memory/greeting. `:100` rejects persona; `:106` limits single participant/single turn; `:116` rejects participant worldbooks/exemplars/default memory. It already composes **frozen custom preset templates** (`:134`) and accepted sampling (`:149`). Neutral/no-snapshot chats are allowed at `:96` without roleplay eligibility.
- Regular generic completion calls live profile/card resolution in `core/Chat/chat_service.py:892` (`:920`, `:945`). Regular character completion's `_get_completion_settings_row` at `character_chat_sessions.py:4129` reads accepted resume state but returns settings/fences, not the snapshot. `character_chat_completion :6039` obtains live participant cards via `_resolve_chat_turn_context :3295` (`:6083`), live preset (`:6165`/`:3141`), live memory (`:6218`), and live worldbooks (`:6245`). Switching to that path would violate D2 even if it makes a send succeed.
- H1's useful admission seam is `chat_service.py:3965`: under one owner transaction read/lock state, validate selection, project context, then append current inputs at `:3972`. Selected content is later assembled at `:4320`, before provider prompt composition. `api/v1/endpoints/chat.py:4718` explicitly skips live character exemplar retrieval when history admission exists; preserve that guard.

**Smallest concrete integration:** extend the detached H1 projector to validate accepted rich inputs and return an immutable `FrozenHistoryBehaviorPlan` along with identity/sampling. Validate support and freeze it **before input append** within the existing owner admission. Compose that plan over the exact selected messages/current inputs after the transaction, using pure helpers and no live source reads. Keep accepted behavior, selected history and request values separate until that composition. All effects needed by the retained projection must be validated before admitting input; do not discover an unsupported required effect after persistence. No network/model awaits belong inside the owner transaction.

Useful existing algorithms/seams:

- Preset prompt builders are already pure and already used by H1. Use accepted materialized preset preferentially, then accepted base preset; do not resolve a stored ID against current presets.
- `Character_Chat/world_book_prompt_context.py:44` provides recent scan text, `:66` accepts an injected processing service, and `:124` inserts the result into prompt messages. `world_book_manager.py:1650` currently mixes live book/entry fetching (`:1687`, `:1742`) with reusable matching, recursion, priority and budget logic (`:1766`–`:1968`). Extract/pass validated frozen books and entries to that logic. Do not instantiate a DB-mutating WorldBookService or fake global reads merely to reuse it.
- `modules/persona_exemplar_selector.py:551` retrieves live candidates at `:568`, then applies filtering/scoring/packing (`:583`). A frozen list-based entry point can reuse those pure operations. The exact selection/budget config also needs to be frozen or explicitly bound to the admitted request; frozen rows alone do not define all prompt semantics.
- Author-note placement, accepted memory injection and participant selection need list/value-based equivalents of the existing helpers. Existing live memory retrieval is not acceptable. Snapshot greetings are declarative accepted data; creation/first-turn reseeding must remain disabled for a fork.

**Remaining integrations that are required, not satisfied by a gate:** accepted worldbook matching/policy on the next selected-history send; frozen effective preset/sampling and body-level rich validation; supported authored memory/exemplar/author-note composition; remapped selected pins/context references; summary policy continuing from the child's own history without importing old summary; server-recognized cold reopen and child settings edits; snapshot-bound identity handling without live card fallback. Persona-backed primary chats currently lack a BehaviorSnapshotV1 participant representation. Multi-participant/round-robin values can exist in materialized settings even though H1 rejects them; rich overlays/research context/assets have additional consumers. Those cases need their own faithful adapters or explicitly recorded dependent scope, with no claim that a neutral/plain gate completes D2's rich behavior requirement. This report does not propose implementing every mode in the first change; it makes the outstanding contract visible for the combined design.

## Focused proof obligations and existing tests

Recommended H2 tests, using existing SQLite/PG fixtures, not new ad hoc database setup:

1. Accepted rich character child uses exact frozen card/preset/book/author-note/sampling content after live sources change; poison live source readers to prove both cold reopen and the **next selected-history provider payload** avoid them. Storage-byte equality alone is insufficient.
2. Actual source-card hard delete after commit leaves child, settings and snapshot usable. Source deletion before admission rejects; source deletion after committed receipt does not invalidate replay (receipt design is root-owned). No hidden card is created.
3. Empty/before-first fork never seeds a greeting, and next send does not inject a new creation greeting. Retained selected greeting rows are copied once with fresh IDs.
4. Excluded-only summary/prefill updates and raw JSON formatting/no-op settings updates preserve the fork projection digest; retained preset/book/model/policy changes reject the old unaccepted request. Check duplicated materialized summary containers. New child summary state starts empty.
5. Neutral ordinary chats remain neutral even in a workspace with default persona/card settings. Missing snapshot is valid for neutral chat; missing/invalid required character authority is explicit, never defaults. Valid snapshot remains usable after card soft deletion and child independence survives hard deletion.
6. Server-native cold reopen in a browser with no local receipt reads canonical child settings and accepted presentation. Stale Plasmo/draft/model state cannot overwrite or masquerade as accepted child context. Ordinary edits do not re-resolve source definitions.
7. Pins/replay IDs are remapped and source admissions/approvals/credentials are absent. Child settings/snapshot edits do not alter source. Workspace/account mismatches reject without writes.
8. PG source settings edit race and metadata/pin race have bounded completion and no deadlock; retained-source revisions decide admission. One transaction rollback leaves no partly ready child.
