# Usage Quotas

Usage quotas are per-user budgets: audio minutes, LLM tokens, RAG queries, storage, and so on. They are **off by default**. A stock install, single-user or multi-user, returns no usage-quota 402, 403, 413 or 429, and no number ships as a default.

This page is for operators. Decision record: `Docs/ADR/064-usage-quotas-per-user-limits.md`. Design: `Docs/Design/2026-10-02-usage-quota-posture-design.md`. Request rate limits are a separate system (Resource Governor, ADR-056); `Docs/Operations/Rate_Limits_Troubleshooting.md` helps tell the two apart.

## The master switch

`USAGE_QUOTAS_ENABLED` (`true|1|false|0`) turns quota checks on. It resolves in this order:

1. env `USAGE_QUOTAS_ENABLED`
2. env `LIMIT_ENFORCEMENT_ENABLED`, if set (legacy spelling; logs a deprecation warning once)
3. `config.txt` `[Usage-Quotas] enabled`
4. otherwise `false`

The switch gates the checks, never the counters: usage is recorded whether the switch is on or off, so turning it on mid-day or mid-month counts correctly. The switch does not depend on `RG_ENABLED`.

With the switch on, a quota applies only to a user who has a value. Nothing is set by default, so turning the switch on alone limits no one.

## How a user's limit is resolved

Each `limits.*` value is looked up per user, in this order:

1. the user's own value;
2. otherwise the **most generous** value among the teams the user belongs to that set the key;
3. otherwise the most generous value among the orgs the user belongs to that set the key;
4. otherwise unlimited.

- A team or org value is **each member's own allowance**, not a shared pool.
- `0` is the least generous value and blocks the user. A team that does not set the key does not unlimit anyone, and joining a group never lowers an allowance.
- Results are cached per user for 60 seconds. A write clears the cache in the process that handled it; other workers see the change within 60 seconds.
- A failed lookup is treated as unlimited and logged as a warning.

## Setting values

All values are integers `>= 0`. Setting them requires platform admin; an org admin cannot change them.

| Scope | Route |
|---|---|
| User | `PATCH /api/v1/admin/users/{id}/profile`, body `{"updates": [{"key": "limits.rag_queries_per_day", "value": 50}]}`. A `null` value removes the user's own value. |
| Team | `PUT /api/v1/admin/teams/{team_id}/profile/overrides/{key}`, body `{"value": 100}`; `DELETE` the same path removes it |
| Org | `PUT /api/v1/admin/orgs/{org_id}/profile/overrides/{key}`, body `{"value": 100}`; `DELETE` the same path removes it |

Team and org writes emit an audit event and clear the resolver cache. The bulk profile API (`POST /api/v1/admin/users/profile/bulk`) writes per-user values for the users it selects; it is not a group setting.

Storage also has dedicated routes, which write the same `limits.storage_quota_mb` user value:

- `PUT /api/v1/storage/admin/quotas/user/{id}` and `GET`/`PUT /api/v1/admin/storage-quotas/users/{id}` take `quota_mb` (integer, `0` or more, or `null` to remove). See `Docs/API-related/Storage_API_Documentation.md`.
- `PUT /api/v1/storage/admin/quotas/team/{id}` and `.../org/{id}` set a **shared storage pool** (minimum 100 MB). A pool is separate from a member's own `limits.storage_quota_mb` and runs only when the switch is on. `STORAGE_QUOTA_ENFORCEMENT=0` is an extra off switch for it.

Example:

```bash
# Give every member of org 1 500 RAG queries a day
curl -X PUT "$BASE_URL/api/v1/admin/orgs/1/profile/overrides/limits.rag_queries_per_day" \
  -H "X-API-KEY: $API_KEY" -H "Content-Type: application/json" -d '{"value": 500}'
```

## The `limits.*` keys

Days and months are calendar UTC. With the switch on and the key unset, nothing is refused; a token key refuses when this request would take the counter past the value, and a cost key refuses once spend has reached its value.

| Key | Limits | Counter it reads | Refusal |
|---|---|---|---|
| `limits.audio_daily_minutes` | Audio transcription minutes per day (HTTP, WebSocket streaming, realtime, workers) | Resource ledger `user/minutes` (stored in seconds) | HTTP 402 `{"status":"quota_exceeded","message":"Transcription quota exceeded (daily minutes)"}` |
| `limits.transcription_minutes_per_month` | Transcription minutes per month | The same ledger rows summed over the month | HTTP 402 `{"status":"quota_exceeded","message":"Transcription quota exceeded (monthly minutes)"}` |
| `limits.audio_concurrent_jobs` | Audio jobs processing at once per user | The audio Jobs worker's count of `processing` rows for the owner | The job waits until the owner is under the cap. With `0` the job fails with `audio job quota is 0 for this user (limits.audio_concurrent_jobs)` |
| `limits.llm_tokens_per_month` | LLM tokens per calendar month (UTC), checked before every LLM call (see below) | `llm_usage_log` summed per user over the month | HTTP 402 `{"error":"limit_exceeded","category":"llm_tokens_month",...}` |
| `limits.llm_cost_per_day_usd` | LLM spend per UTC day, in US dollars | `llm_usage_log` costs summed per user over the day | HTTP 402 `{"error":"limit_exceeded","category":"llm_cost_day",...}` |
| `limits.llm_cost_per_month_usd` | LLM spend per calendar month, in US dollars | `llm_usage_log` costs summed per user over the month | HTTP 402 `{"error":"limit_exceeded","category":"llm_cost_month",...}` |
| `limits.rag_queries_per_day` | RAG queries per day (unified RAG, Text2SQL, MCP RAG) | Resource ledger `user/rag_queries` | HTTP 402 `{"error":"limit_exceeded","category":"rag_queries_day",...}` |
| `limits.storage_quota_mb` | Per-user storage in MB (media ingest, audio and video downloads, generated files) | `users.storage_used_mb` | HTTP 413 `Storage quota exceeded. Current: ...MB, New: ...MB, Quota: ...MB, Available: ...MB` |
| `limits.media_ingest_mb_per_day` | Uploaded media megabytes per day | Resource ledger `user/ingestion_bytes` (bytes) | HTTP 429 `Daily ingestion size budget exceeded.`, with `RateLimit-*`, `X-RateLimit-*` and `Retry-After` headers |
| `limits.workflows_runs_per_day` | Workflow runs per day, API-started and scheduled | Resource ledger `workflows_runs` | HTTP 429 `Daily quota exceeded` |
| `limits.evaluations_per_day` | Evaluations per day | Evaluations DB `daily_usage.total_evaluations` | HTTP 429 `Daily evaluation limit exceeded` |
| `limits.evaluation_tokens_per_day` | Evaluation tokens per day | Evaluations DB `daily_usage.total_tokens` | HTTP 429 `Daily evaluation token limit exceeded` |
| `limits.chatbooks_exports_per_day` | Chatbook exports per day | `export_jobs` rows since 00:00 UTC | HTTP 429 `Daily export limit (N) reached. Try again tomorrow.` |
| `limits.chatbooks_imports_per_day` | Chatbook imports per day | `import_jobs` rows since 00:00 UTC | HTTP 429 `Daily import limit (N) reached. Try again tomorrow.` |
| `limits.chatbooks_concurrent_jobs` | Chatbook export and import jobs active at once | Active chatbook job rows | HTTP 429 `Maximum concurrent jobs (N) reached...` |
| `limits.media_concurrent_jobs` | Media ingest requests running at once: `/media/add`, including its research-discovery handoff. Queued ingest jobs (`/media/ingest/jobs`) and `/media/process-*` are not counted | One lease per running request (see "Concurrency limits" below) | HTTP 429 `Media ingestion concurrency limit reached.`, with `RateLimit-*`, `X-RateLimit-*` and `Retry-After` headers |
| `limits.audio_concurrent_streams` | Audio streaming sessions open at once: `/audio/stream/transcribe`, `/audio/chat/stream`, `/audio/stream/tts`, `/audio/stream/tts/realtime`, the realtime speech sockets, and `POST /audio/chat` | The same leases | Refused when the stream starts. `/audio/stream/transcribe`: an error frame `Concurrent streams limit reached (N)`, then close code 1000. `/audio/chat/stream`, `/audio/stream/tts` and `/audio/stream/tts/realtime`: the same message in an error frame, then close code 4003 (1008 with `AUDIO_WS_QUOTA_CLOSE_1008`). The realtime speech sockets: close code 4003 before the socket is accepted, with no error frame. `POST /audio/chat`: HTTP 429 with the same message |
| `limits.audio_concurrent_transcriptions` | Direct transcriptions running at once (`/audio/transcriptions`, `/audio/translations`) | The same leases | HTTP 429 `Concurrent transcription limit reached (N)`, with `RateLimit-*`, `X-RateLimit-*` and `Retry-After` headers |

What `limits.llm_tokens_per_month`, `limits.llm_cost_per_day_usd` and `limits.llm_cost_per_month_usd` count:

- The monthly count includes every LLM chat call recorded for the user, not just chat completions: RAG generation, character chat, summarization, evaluations and other calls made during a request. Users reach a token limit sooner than before.
- That includes calls a request triggers without the user asking for them directly, such as query rewriting and classification.
- Provider key validation and first-run chat verification are never counted.
- **A call on the user's own key is not counted or checked** (ADR-083). A call made with the user's own stored provider key (BYOK, `Docs/User_Guides/Server/BYOK_User_Guide.md`) is recorded with its real tokens and cost and `credential_source = user` in `llm_usage_log`. None of the three keys counts it, and it is never refused at the call. That holds only for a provider that bills the user's key, sent to that vendor. A key stored for a custom OpenAI-compatible endpoint or a local server (llama.cpp, Ollama, vLLM and the like) reaches the endpoint you configured, so it is recorded as `user_unmetered` and counts. So does a key for a billed provider (OpenAI, Anthropic and the rest) whose base URL you point anywhere but the vendor's own host, at a self-hosted model server or a gateway: in `config.txt` (for example `qwen_api_base_url`, `moonshot_api_base_url`, `zai_api_base_url`, `huggingface_api_base_url`) or in an environment variable such as `OPENAI_API_BASE_URL`. The vendor's own host is the one its adapter calls by default; another host of the same vendor (OpenAI's data-residency hosts such as `eu.api.openai.com`, `api.cohere.com`, `api.moonshot.ai`, Bedrock's FIPS endpoints) also counts, until it is added to `VENDOR_HOSTS` in `Usage/llm_call_context.py`. Every other call counts: org and team shared keys (`team`, `org`), server keys (`server_default`), keyless local providers (`none`), and rows whose key is unknown (`NULL`): rows written before the column existed, and the auto-router's call. If the column is missing (AuthNZ migration 104 did not run, or the PostgreSQL bootstrap could not add it), every row counts and the server logs a warning. The hosted billing plan's `llm_tokens_month` leaves own-key calls out too. On PostgreSQL that plan limit counted no LLM tokens at all before this release (a timestamp bug), so a hosted plan on PostgreSQL now starts refusing at its `llm_tokens_month`. The other limits still count own-key calls: the Resource Governor's token caps, virtual-key budgets and `limits.evaluation_tokens_per_day`.
- Embedding tokens do not count toward it.
- Recorded: calls made while serving a request, including Messages API calls to Anthropic or llama.cpp; background jobs, including audio analysis and scheduled agent tasks; workflow runs; watchlist output enrichment; audio and realtime WebSocket sessions; MCP tool calls, including tools that `/chat/completions` runs; the in-process claims rebuild.
- Not recorded: system jobs with no user, such as the scheduled quality evaluation, and MCP calls from a caller with no user account.
- The count depends on `LLM_USAGE_ENABLED` (default on). With it off, nothing is recorded and the limit never triggers.
- **Where a refusal happens.** These entry points refuse with a 402 before they start any LLM work, streaming requests included: `/chat/completions`; the Anthropic-compatible Messages API (`/messages` and `/v1/messages`); character chat replies; RAG search, batch, batch resume and streaming, when the request generates an answer; advanced search (`/rag/advanced`) when it generates an answer, which is the default; ablation (`/rag/ablate`) with answers on; document generation from a chat; the flashcards and quizzes study assistants; `/evaluations/geval`, `/evaluations/rag` and `/evaluations/response-quality`; `/evaluations/batch` of type `geval`, `rag` or `response_quality`; evaluation runs (`POST /evaluations/{eval_id}/runs`); benchmark runs (`POST /evaluations/benchmarks/{name}/run` and `POST /benchmarks/{name}/run`); `/media/ingest-web-content` whenever analysis is on, with or without a provider and for every scrape method (without a provider it makes no summary call, but it may still extract with an LLM, and the crawl methods summarize with a default provider); `/media/process-web-scraping` with `summarize_checkbox`, with or without `api_name` (a summary without one uses a default provider); `POST /watchlists/outputs` with `summarize`; the `/media/process-*` endpoints for audio, video, documents, PDFs, ebooks and email, and `/media/add`, when analysis is on and a provider is named (`perform_analysis` defaults to true, but without a provider no analysis runs). Simple search (`/rag/simple`) makes no LLM call.
- **Everything else is checked at the call.** Background jobs (`/media/ingest/jobs`, evaluation recipe runs; a media ingest job that asks for analysis is checked once, when it starts, below), workflow runs, WebSocket sessions (audio, realtime) and every HTTP endpoint not listed above check each LLM call just before the provider is called, and a call for a user over a limit is refused without reaching the provider. What the caller gets back depends on the caller:
  - **An HTTP endpoint** that passes errors through, as most do, returns the same 402: `/translate`, `/media/{id}/insights` and the manuscript analysis endpoints among them. So do Prompt Studio prompt execution (`POST /prompt-studio/prompts/execute`), test runs (`POST /prompt-studio/test-cases/run`) and synchronous evaluations, prompt improvement (`POST /prompts/improve`), manual character memory extraction (`POST /characters/{id}/memories/extract`), and FVA claim verification (`POST /claims/verify/fva`) at its verify or adjudication call; an admin's `?user_id=` runs that request, and charges it, for the named user. An endpoint that catches errors broadly reports its own error, usually a 500.
  - **A workflow:** an `llm` step fails, and so does the run, with `error` set to `402: {'error': 'limit_exceeded', ...}`. Content generation, NLP, bibliography, image description, summarize, translate, claims extraction and evaluations steps fail the step, and the run, the same way; `web_search` skips its optional query rewrite instead. A refused step is not retried, even when it sets `retry` (the run's events show `step_retry_suppressed`), and a `retry` step does not retry it either. A `parallel` step fails when one of its steps is refused. A step's `on_failure` can route around a refused step. In a `map` or `parallel` step, the refusal cancels the step's other sub-steps before the step fails: each one stops at its next wait, and what it had already done is kept. A download that a `media_ingest` sub-step started is stopped: the sub-step now waits for the download, so a cancel always finds it running or finished. So is an ffmpeg command that a `tts` or `multi_voice_tts` sub-step started (TASK-13887).
  - **Watchlist output enrichment** (briefing and per-group summaries, topic grouping) stops at the refusal: the output's metadata gets `enrichment_status: failed` and `enrichment_error: 402: {...}`, and the task is not retried. When the Scheduler is unavailable, enrichment runs as a background task of the request instead, so after an admitted `summarize` request it is admitted with it and not refused.
  - **A job** whose worker reads the error's `retryable` flag (WorkerSDK workers and most others) fails at once and is not retried. A WorkerSDK job records the error code `llm_quota_exceeded`; other workers record their own. An audio analysis job (`/audio/jobs/submit` with `perform_analysis`) is not retried either, but it does not fail: it stores its transcript with `analysis_error.code = "llm_quota_exceeded"`. A media ingest job (`/media/ingest/jobs`) that asks for analysis is checked once, when it starts, not at each call. Refused, it stores the item without analysis: the job's `result` has `status: Warning`, the warning `Analysis skipped: LLM quota exceeded (<category>).` and `analysis_error.code = "llm_quota_exceeded"`. Admitted, it runs to completion, as an admitted request does. Each job of a batch is checked when it starts, so once the user is over a limit the rest of the batch is stored without analysis and makes no LLM call. A media item that reuses an earlier transcript, in a job refused when it starts, keeps the transcript and gets no summary: no LLM call is made, the item's warnings carry the 402, and its `video_lite` metadata records `summary_status: failed` and `summary_error: llm_quota_exceeded`. A Prompt Studio optimization job fails with `llm_quota_exceeded` and is not retried. A Prompt Studio evaluation refused part-way, synchronous or background, ends `failed`, with `error_message` `llm_quota_exceeded: ...`, and its `test_run_ids` list the cases that ran before the refusal. An Explainer node that could not be expanded records `error: llm_quota_exceeded`.
  - **The in-process claims rebuild** (used when claims Jobs are off) fails that media item, keeps its current claims, and goes on to the next.
  - **A WebSocket:** `/audio/chat/stream` sends `{"type":"error","code":"provider_unavailable",...}` for that turn and stays open. The realtime sockets send `{"type":"error","error":{"type":"server_error","code":"internal_error",...}}` and `response.done` with status `failed`, and stay open.
  - **A RAG search with generation off** still returns its results. The optional LLM stages it asked for (query classification, HyDE, gap analysis, LLM reranking and others) are skipped, and their entries in the response metadata say `"failure_code": "provider_unavailable"`.
  - **Shared machinery is not affected.** A refusal never opens the evaluations circuit breaker, is never scored 0.0 by an evaluator or a Prompt Studio evaluation (a benchmark run is checked once, before it starts: an admitted run completes even past the limit, and no item is refused mid-run), and never marks a chat provider unhealthy, including the auto-router's call on `/chat/completions`, which runs before that endpoint's own check.
  - **Claims verification is refused, not answered without the LLM:** a generated artifact whose claims cannot be checked reports the refusal instead of `claim_verification_failed`. Automatic character memory extraction after a character chat reply runs as part of that reply, which the boundary check already admitted.
  - **An MCP tool** returns a tool error with `reason_code` `llm_quota_exceeded`. On `/api/v1/tools/execute` that is HTTP 200 with `ok: true` and `result.isError: true`, not a 402. The module's circuit breaker does not count it, so other users keep the tool. A tool that an admitted `/chat/completions` request runs is not refused, and its LLM calls are recorded for the user.
- **An over-limit user on their own key.** `/chat/completions` and the Messages API (`/messages`, `/v1/messages`) let an over-limit user through when four things hold: BYOK is on, the request's provider bills per key and its base URL is the vendor's, the provider is on the BYOK allowlist, and the user has an active key for it. The request is not marked admitted, so each of its calls is checked where its key is known. A call on the user's own key runs. A call on any other key, a fallback provider's for example, is refused at the call. On `/chat/completions` the hosted billing plan's check is skipped for such a request. Every other boundary endpoint refuses an over-limit user before the key is known, even when the call would have used the user's own key: character chat, RAG generation, evaluations and benchmarks, flashcards and quizzes, chat document generation, watchlists and media analysis. So does a media ingest job's check when it starts.
- **How the cost keys compare.** A cost key refuses once today's or this month's spend has reached the limit. The token key refuses when this request's estimated tokens would take the month past it; outside `/chat/completions` the estimate is one token.
- **An admitted request runs to completion,** so a user can pass a limit by one request's worth of usage. A media batch or an evaluation batch can be large. So can each media ingest job admitted when it starts.
- **Local providers cost nothing by default:** llama.cpp, kobold, ooba, tabbyapi, vllm, local-llm, ollama, aphrodite and mlx. To give one a price, edit its `default` entry in `tldw_Server_API/Config_Files/model_pricing.json`, or set `PRICING_OVERRIDES` (a JSON string in the environment), which overrides that file. A custom OpenAI-compatible endpoint is priced at the unknown-model rate ($0.01 per 1K prompt tokens, $0.03 per 1K completion tokens) unless you give it a price. A virtual-key USD budget no longer counts local calls.
- **Prompt-cache tokens.** Anthropic cache reads and cache writes count as prompt tokens on every call recorded for a user: the Messages API and every caller of the Anthropic adapter (`/chat/completions`, RAG, summarization, workflows and the rest). So they count in full toward `limits.llm_tokens_per_month`, the org plan's `llm_tokens_month`, the virtual-key token budgets (`llm_budget_day_tokens`, `llm_budget_month_tokens`), the Resource Governor's token commit on `/chat/completions` and its daily token cap, and the `llm_tokens_used_total` metrics. Their cost uses the `cache_read`, `cache_write` and `cache_write_1h` rates of the model's entry in `model_pricing.json`. The Anthropic entries that carry them use Anthropic's cache-hit rate (0.1x input; 0.05x on Opus 5.5 and Sonnet 5.5, 0.025x on Fable 5.1 and Mythos 5.1), its 5-minute cache-write rate (1.25x) and its 1-hour cache-write rate (2x). The 1-hour share of a call's cache writes is `usage.cache_creation.ephemeral_1h_input_tokens`; the rest of the writes cost the 5-minute rate. OpenAI cached input (`prompt_tokens_details.cached_tokens`) costs the `cache_read` rate of the OpenAI entries that have one (the -pro models have none). Some models are priced by prompt length. A request whose whole prompt (cache reads and writes included) is over 100,000 tokens pays the higher `long_prompt` rates on Claude Haiku 5.5. The same holds above 272,000 tokens on gpt-5.5, gpt-5.4 and their -pro models. Two Anthropic request options multiply every token category of a call: fast mode (`speed: "fast"` in the usage block) costs 2x, and US-only inference (`inference_geo: "us"`) costs 1.1x. They stack with each other and with the cache rates. Fast mode trusts the usage block. US-only applies only to Claude 4.6 and later: a usage block that reports `inference_geo: "us"` for Claude Opus 4.5, Sonnet 4.5, Haiku 4.5 or an earlier model (for example in a workspace migrated from the legacy US-only opt-out) is costed at list price, as Anthropic bills it. Claude Mythos 5.1 and 5 are priced but hidden from model pickers (limited availability); a call to one needs the model listed in `config.txt` under `[API] anthropic_model` (a comma-separated list; add Mythos after the default model, do not replace it) when strict model selection is on. A dotted Anthropic model name (`claude-sonnet-4.5`) is treated as the dashed API ID (`claude-sonnet-4-5`) by the price lookup, the model-availability check, provider override and virtual-key model allowlists (including the model lists an override filters), and every request the server sends to Anthropic, including through a custom Anthropic base URL: a proxy that defines its own dotted alias receives the dashed name. An entry without cache rates costs every prompt token at its input rate. That includes an override in `PRICING_OVERRIDES` or in the file: it replaces the whole entry, so it must repeat `cache_read`, `cache_write`, `cache_write_1h`, `long_prompt`, `hidden` and `service_tiers` where the shipped entry has them. A missing `cache_write_1h` falls back to the `cache_write` rate, a missing `long_prompt` drops the tier, a missing `hidden` lists the model, and a missing `service_tiers` costs every service tier at the standard rates. A streamed reply through the Anthropic adapter (`/chat/completions` or any other caller) is also costed at the input rate, because its usage is estimated from the prompt; only the Messages API reads a streamed Anthropic reply's real usage.
- **Service tiers.** A call is costed at the service tier its provider reports, and nothing else selects a tier. OpenAI reports it beside the usage block as `service_tier`: `flex`, or `priority` for Fast (GPT-5.6 and earlier report `priority` even when `fast` is requested; a Fast call downgraded during a traffic ramp reports `default` and is billed standard). The `batch` rates apply to a usage block that reports `batch`, which no documented OpenAI response does today. A caller gets a tier by sending `service_tier` in `extra_body`, since the adapter never sets one. Its cost uses the `service_tiers` rates of the model's entry in `model_pricing.json`, copied per model from OpenAI's Batch, Flex and Fast tables: Batch and Flex are about half the standard price, Fast 1.7x to 2.5x. Anthropic reports the tier inside the usage block. `batch` costs half of every token category (the Batch API discount, which stacks with the cache rates, US-only inference and Haiku 5.5's prompt-length tier). `priority` costs the standard rates: Priority Tier is paid for by a capacity commitment, not per token. Any other tier costs the standard rates: `default`, `standard`, `scale`, a model with no row in that tier's table, or a tier the model's entry has no rates for. So does a prompt over 272,000 tokens on a tier whose table shows no long-context price (gpt-5.5 and gpt-5.4 Fast, gpt-5.5-pro Batch and Flex). The tier is kept in the row's `raw_usage_metadata_json`. No server code calls a Batch API, so a batch tier is costed only when a usage block reports it, for example a Messages API reply from a proxy. Fast mode on Anthropic is `speed`, not a tier (see above).
- **Gemini cache reads.** Gemini cached input (`cachedContentTokenCount`, from implicit caching or a `cachedContent` reference) costs the model's context-caching rate on gemini-3.1-pro-preview, gemini-3.1-flash-lite, gemini-3-flash-preview, gemini-2.5-pro, gemini-2.5-flash and gemini-2.5-flash-lite, and on the four -preview entries of 2.5 Flash and Flash-Lite, which are priced like their GA model. On gemini-3.1-pro-preview and gemini-2.5-pro, a prompt over 200,000 tokens pays the higher `long_prompt` rates. The 2.0 Flash entries are not on Google's pricing page and have no cache rate, so their cached tokens cost the input rate. The per-hour storage charge of an explicit cache is not costed: the cache is created outside the server and billed by the hour, not per call. Audio input, cached or not, costs the text rate. Thinking tokens are not costed yet: Google bills them as output, but the usage record counts only the reply's candidate tokens (`candidatesTokenCount`, not `thoughtsTokenCount`), so a Gemini 2.5 reply with thinking on (the default on 2.5 Pro and Flash) is under-billed.
- **OpenRouter.** An OpenRouter call is costed from the cost OpenRouter reports in its usage block (`usage.cost`, in dollars; OpenRouter always sends it, so no request flag is needed). With BYOK, the upstream provider's charge (`cost_details.upstream_inference_cost`) is added to it. A reply without a usable `cost` costs the model's catalogued rate, or the unknown-model rate when the model is not in the catalog. The cost is split between `prompt_cost_usd` and `completion_cost_usd` in the catalog's proportions.
- **Streamed replies.** A streamed reply is costed from the provider's last usage chunk when the provider sends one, on `/chat/completions` as on every other caller, so its service tier, cache rates and reported cost apply as they do to a reply that is not streamed. OpenRouter always sends one. OpenAI sends one because the server asks for it (`stream_options.include_usage`) on every stream to `api.openai.com` and OpenAI's data-residency hosts (such as `eu.api.openai.com`); an `openai` provider whose base URL points at another server is not asked, since that server may reject the field, so a caller that wants it there sets `stream_options` in `extra_body`.
- **Streams without a usage chunk, and router calls.** A stream without a usage chunk, or with one that counts no tokens, is costed from an estimate at the standard rate: the prompt estimate plus a quarter of the reply's characters (on `/chat/completions`, a tool-call-only reply counts no completion tokens). That includes every stream through the Anthropic and Google adapters, which pass no usage chunk on, and other OpenAI-compatible providers unless they send one unasked or `extra_body` asks for it. It also includes `/v1/messages` streams even with an OpenAI provider: that path stops reading at the finish chunk, before the usage chunk arrives, so the asking applies to `/chat/completions` streams and to other callers that read to the end. On `/chat/completions`, a usage chunk that counts only one side (prompt tokens only, say) takes the other side from that estimate, and the row is marked estimated. A `/chat/completions` stream that the client drops, or that fails after it starts, writes no usage row, and its Resource Governor reservation is refunded. An auto-router call (the model choice made before a `/chat/completions` or character chat reply) is recorded from the provider's token counts without its usage block, so it costs the standard rate.
- **Two settings defeat these limits, and the server warns at startup when quotas are on:** `LLM_USAGE_ENABLED` off (nothing is recorded, so nothing is refused), and `LLM_USAGE_LOG_RETENTION_DAYS` under 31 (the monthly counts lose rows).
- **Failures let requests through.** If a limit cannot be read or a counter fails, the request or call is admitted and a warning is logged. A check at the call that gets no answer within two seconds lets the call through, with a warning; at a media ingest job's start, it admits the whole job. A synchronous LLM call made on the server's event loop thread cannot be checked (waiting there would stall the server); it goes through, recorded, and the first one logs `A synchronous LLM call on the event loop's thread is not quota-checked`. A stream started there is checked when its first item is read.
- **Run workers inside the server.** A job worker started as its own process (`python -m ...`) has no accounting loop, so its synchronous LLM calls are neither checked nor recorded; the first one logs a warning. A media ingest job's check when it starts still runs, on that process's own loop. Workers run inside the server process by default.
- **What the check costs.** With quotas off, nothing. With quotas on and no LLM limit for the user, nothing once the user's limits are cached (for a minute). With a limit set, the counters are read for each call that a request boundary did not already admit, so a job that makes hundreds of calls makes hundreds of small indexed reads. While the user's limits cannot be read (the AuthNZ database is down), every call tries again and logs a warning.
- **The profile reports it.** `GET /api/v1/users/me/profile?sections=quotas` has an `llm` block with tokens used this month, spend today and this month, and each limit that is set. The figures are the ones the limits count, so they leave out calls on the user's own key.

### Concurrency limits

`limits.media_concurrent_jobs`, `limits.audio_concurrent_streams` and `limits.audio_concurrent_transcriptions` count requests running at once, not usage over time.

- Each admitted request holds one lease until it ends: on success, on error, when the client disconnects, and when the server shuts down gracefully. A refused request holds nothing.
- Leases live in the Resource Governor's lease store, chosen by `RG_BACKEND`. On `memory` (the default) a limit holds per worker process, so with N workers a user can run up to N times the limit. On `redis` it is exact across workers.
- `RG_ENABLED=false` does not turn these limits off; `USAGE_QUOTAS_ENABLED` does (ADR-076).
- A lease nobody releases, for example when a worker is killed mid-request, expires within 2 minutes. A crash can hold one of the user's slots for up to that long.
- `Retry-After` on a refusal is when the oldest held lease would expire if it stopped renewing, up to 2 minutes. A slot usually frees sooner, when one of the user's requests finishes, so a client may retry earlier.
- Lowering a limit does not stop running requests. New ones are refused until the user is below the new limit.
- If Redis is unreachable when a worker's lease store first connects, that worker counts on its own for the life of the process, as on `memory`. If Redis drops later, or rejects writes (a read-only replica, or out of memory), the worker counts on its own until Redis recovers, and a warning is logged (ADR-078). It does not see leases taken before the drop, a lease released during the outage frees its slot at once, and leases the worker could not release in Redis expire within 2 minutes. After a Redis restart, leases are counted as before.
- Once a Redis command and a PING right after it both fail (refused, reset or timed out), each limiter in the worker stops calling Redis for `RG_REDIS_UNREACHABLE_COOLDOWN_SEC` (10 seconds by default) and answers by the fail mode, then lets one command through to see whether Redis is back. A single failed command, such as one on a connection Redis closed while idle, does not start this. With a Redis that stops answering (a network partition, say), requests in the first 10 seconds wait up to 10 seconds each (two 5-second timeouts), then about one request every 20 seconds does, where every request used to wait 30 to 70 seconds. The worker keeps counting on its own for up to about 15 seconds after Redis returns (ADR-081).

Two other `limits.*` entries in the catalog are not part of this scheme:

- `limits.evaluations_per_minute` is listed in `user_profile_catalog.yaml` but nothing enforces it.
- The `limits.prompt_studio_*` keys are Prompt Studio's own limits and are unchanged.

`Docs/Operations/Rate_Limits_Troubleshooting.md` maps each refusal to the code that raises it.

## What is not a quota

These are unchanged by the switch and have no `limits.*` key:

- **Per-file caps**: `[Media-Processing] max_*_file_size_mb`, the 100 MB chatbook file cap, character-chat count caps.
- **Per-minute request rates**: the Resource Governor, and module limiters such as evaluations per minute.
- **Other limits that were already off by default**: the `JOBS_QUOTA_*` limits, the embeddings and ingest per-tenant limits, chat token daily caps, and the Prompt Studio limits.
- **Admin storage pools** keep their shared-pool meaning (see above).
- **Billing-plan limits** run only on the hosted product. They need a billing repository wired into the subscription service (nothing in this repository wires one) and the switch on. With a repository wired and the switch off, startup logs a warning once that plan limits are not enforced.

`CHATBOOKS_DISABLE_QUOTAS` and `WORKFLOWS_DISABLE_QUOTAS` remain as extra per-module off switches; see the Usage Quotas section of `Docs/Operations/Env_Vars.md`.

## Upgrade notes

- **Self-hosters have nothing to do.** Quotas you never configured stop applying.
- **A hosted deployment** turns quotas on with `USAGE_QUOTAS_ENABLED=true` (`LIMIT_ENFORCEMENT_ENABLED=true` also works, with a warning) and wires its billing repository.
- **Storage copy.** An AuthNZ migration copies each user's existing `users.storage_quota_mb` into a user-level `limits.storage_quota_mb` value and never replaces a value that already exists. It skips values equal to 5120 and to the `DEFAULT_STORAGE_QUOTA_MB` configured when the migration runs, because those cannot be told apart from "never set". Those users become unlimited until a value is set. If the default was changed over time, users still on an older default keep it as a real per-user value.
- **The column stays.** `users.storage_quota_mb` is kept (`NOT NULL DEFAULT 5120`) but is no longer read for enforcement.
- **Evaluations.** `limits.evaluations_per_day` values set before this change were never enforced; with the switch on, they become enforced daily caps. Evaluation tiers no longer drive daily caps.
- **Tiers are not carried over.** Audio, evaluations and chatbooks tier assignments are dropped.
- **Stored RG policies.** Operators on `RG_POLICY_STORE=db` whose stored `evals.*` policies carry a `daily_cap` keep that cap until they remove it from the stored policy.

## Where users see their limits

`null` means unlimited in all of these.

| Where | What it reports |
|---|---|
| `GET /api/v1/users/storage` | `storage_quota_mb`, used MB, available and percentage |
| `GET /api/v1/audio/stream/limits` | Daily and monthly minute limits, `used_today_minutes`, `used_month_minutes`, `remaining_minutes` and `remaining_month_minutes` (used figures come from the ledger). `limits.concurrent_streams` is the `limits.audio_concurrent_streams` value. `active_streams` stays `null` and `can_start_stream` stays `true`: this endpoint does not report open streams, and a stream over the limit is refused when it starts |
| `GET /api/v1/evaluations/rate-limits` | The resolved `limits.evaluations_per_day` and `limits.evaluation_tokens_per_day`, with usage and remaining. The daily `X-RateLimit-Daily-*` headers on evaluation responses are omitted when the cap is unlimited |
| `GET /api/v1/audio/jobs/admin/owner/{id}/processing` | An owner's processing count and concurrent-jobs limit (admin) |
| Profile `quotas` section and `limits.*` config | Storage, audio (daily and monthly), evaluations and Prompt Studio quotas, and, when set, the `limits.*` values (unset keys are omitted from `effective_config`) |

A storage quota of `0` shows as full, not as unlimited.

## Deprecated settings and APIs

These no longer set any limit:

- `AUDIO_TIER_LIMITS_JSON` and `[Audio-Quota] {tier}_*`: setting either logs a warning once and changes nothing. Use `limits.audio_daily_minutes`, `limits.transcription_minutes_per_month` and `limits.audio_concurrent_jobs`.
- The audio tier admin API, `GET`/`PUT /api/v1/audio/jobs/admin/tiers/{user_id}`: marked deprecated in the OpenAPI schema; it no longer affects limits.
- `DEFAULT_STORAGE_QUOTA_MB`: setting it logs a deprecation warning and sets no one's quota. Only the storage migration reads it, to skip the old default. Use `limits.storage_quota_mb`.
- `LIMIT_ENFORCEMENT_ENABLED`: the legacy spelling of the master switch; use `USAGE_QUOTAS_ENABLED`.
