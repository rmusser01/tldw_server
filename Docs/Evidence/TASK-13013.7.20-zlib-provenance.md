## Ubuntu source identity

The candidate Syft package record identifies source package `zlib`, amd64,
binary version `1:1.3.dfsg-3.1ubuntu2.2`, and library path
`/usr/lib/x86_64-linux-gnu/libz.so.1.3`. Its explicit `sourceVersion` field is
empty. The matching version's public
[Ubuntu source descriptor](https://archive.ubuntu.com/ubuntu/pool/main/z/zlib/zlib_1.3.dfsg-3.1ubuntu2.2.dsc)

| `zlib_1.3.dfsg-3.1ubuntu2.2.debian.tar.xz` | `de1c2d532ecb7caf99ccb905fb03c37fe0c8117fbdc79d05be4474b71e6398c2` |

Static archive inspection found upstream header version `1.3`. The source
archive has 109 regular files and packaging archive has 54. Neither contains
the literal `gz_vacate`; none of the eight listed patches targets `gzwrite.c`.
The newest packaging changelog entry addresses CVE-2026-27171 in CRC functions,
not CVE-2026-85091. No patches or packaging scripts were executed.

These facts narrow the question raised by the advisory's stated 1.3.1.2–1.3.2
range. They are not proof that an older branch is unaffected: token absence
does not rule out equivalent behavior, and this assessment does not establish
the complete source-to-binary build chain. The descriptor was fetched over
official HTTPS; its embedded OpenPGP signature was **not locally verified**.
The earlier signed-APT binary acquisition is separate evidence and does not
authenticate these newly downloaded source archives by itself.

Ubuntu still records Noble zlib as needing evaluation. Debian continues to
list older branches as vulnerable, and upstream issue 1310 remains open.
[Ubuntu](https://ubuntu.com/security/CVE-2026-85091),
[Debian](https://security-tracker.debian.org/tracker/CVE-2026-85091),
[upstream issue](https://github.com/madler/zlib/issues/1310).

## Node is a separate provenance question

All four retained native observations identify Node 24.20.0 with executable
SHA256 `89af8424dd53e560b1933f87ba650d8bf57c83ca5a04600eefb31f416aabbae7`.
Syft catalogs Node separately as `pkg:generic/node@24.20.0`; the 85091 matches
above are attached to the OS package. The observations do not record
`process.versions.zlib` or the executable's zlib build configuration.

The official Node release tag resolves through annotated tag object
`8392e555cbdef2145d2cd2a2a7d29204d88d4e15` to commit
`71b8b174857e25106d39b61a9e6f30d927da8b01`. GitHub reports the tag signature as
valid; local signature verification was not performed. Three files downloaded
by tag and immutable commit are byte-identical:

- [zlib.h](https://github.com/nodejs/node/blob/71b8b174857e25106d39b61a9e6f30d927da8b01/deps/zlib/zlib.h)
  declares `1.3.2.1-motley`.
- [zlib.gyp](https://github.com/nodejs/node/blob/71b8b174857e25106d39b61a9e6f30d927da8b01/deps/zlib/zlib.gyp)
  defaults to bundled static zlib, with an optional system-library branch.
- [BUILD.gn](https://github.com/nodejs/node/blob/71b8b174857e25106d39b61a9e6f30d927da8b01/deps/zlib/BUILD.gn)
  includes `gzwrite.c` in its zlib source list.

The [release notes](https://nodejs.org/en/blog/release/v24.20.0) also identify
the zlib dependency update. Build defaults alone do not prove the retained
binary's build flags, final linked functions or vulnerability status. An OS
package replacement cannot be assumed to remediate Node's bundled copy.
