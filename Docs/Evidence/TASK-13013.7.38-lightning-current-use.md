The ACL follow-up corrects an overly broad consumer hypothesis. Exact official
Debian coreutils 9.7-3 amd64 payloads import libattr copying and libacl setting
functions. Its compiled `qcopy_acl` path uses `attr_copy_fd` for regular-file
descriptors and `attr_copy_file` for pathname copies. It does not import
`acl_get_file` or `acl_get_fd`. Ordinary directory copying therefore cannot be
attributed to the libacl advisory merely because the program links libacl.
Debian's gnulib NFS ACL patch adds an unsupported-operation check without
switching this copy branch to the libacl getter/setter route.

A separate mode/ownership operation still matters to the investigation:
`copy.c` can call `set_owner` with descriptor -1 for a pre-existing directory
with different owner/group. In its mode-preservation branch, `qset_acl` then
reaches pathname `acl_set_file` through `set_permissions`. Explicit mode-setting
paths can also use pathname ACL operations. Thus a universal descriptor-only
exclusion is not established. This is a utility code path, not proof that a
deployed worker invokes it on attacker-controlled paths with useful privileges.
The [maintainer disclosure](https://openwall.com/lists/oss-security/2026/06/29/1)
and [follow-up](https://openwall.com/lists/oss-security/2026/06/29/2) distinguish
the existing pathname APIs from newly added interfaces; a library version
change alone does not demonstrate that callers use the latter.

These facts narrow the concern; they do not establish complete third-party
