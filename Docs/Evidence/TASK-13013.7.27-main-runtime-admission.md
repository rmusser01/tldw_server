## Identity, evidence and admission

The identity step authenticates the raw subject bytes against the build digest.
For OCI indexes and Docker manifest lists, it requires exactly one eligible
`linux/amd64` child, excluding attestation descriptors. A supported single-image
manifest is its own child. Unsupported subject media types, malformed child
digests and missing or ambiguous eligible children are rejected before outputs
are emitted.

The runtime step reuses the
[release backend implementation](TASK-13013.7.25-release-runtime-admission.md),
with the component fixed to `app`. It authenticates the selected child manifest,
pulls that immutable child, verifies the local repository digest and platform,
and runs the unchanged probe with `--pull never`. Network isolation, non-root
execution, dropped capabilities, read-only root, temporary scratch storage and
read-only probe/lock mounts match the release controls. Docker remains the
trusted pull/runtime boundary.

`runtime-image-app.json` retains the probe result with parent subject, platform
manifest and config digests. It and `platform-manifest-app.json` are included in
`SHA256SUMS-image-app`. Failed runtime checks allow scanning and evidence upload
to continue, but final admission requires both runtime and vulnerability-policy
outcomes to be `success`. A skipped runtime step cannot admit the image. Existing
GitHub success conditions also prevent promotion after checksum or upload failure.

A failed probe does not produce a successful runtime JSON record. Available
evidence is uploaded and failure diagnostics remain in the workflow log; this
follows the existing release behavior. The probe is an isolated runtime check,
not a full application-startup or arbitrary deployment assessment.
