# Embedded Chroma settings — TASK-13013.7.26

Prepared September 10, 2026 UTC from local base
`4134d3247d68d652842d2ec8d215bf9555e7ef3f` for PR
[#2869](https://github.com/rmusser01/tldw_server/pull/2869).

All six application-owned persistent Chroma client constructors now explicitly
select `chromadb.api.rust.RustBindingsAPI`. Previously their real Chroma Settings
objects inherited `CHROMA_API_IMPL`, so an environment value could select the
HTTP API even though the callers supplied local storage paths. This closes one
configuration gap in the conditional assessment from
[TASK-13013.7.23](TASK-13013.7.23-applicability-dispositions.md).

## Scope and compatibility

| Caller | Settings changed |
| --- | --- |
| `ChromaDBManager.__init__` | Internal persistent client |
| `EmbeddingShardManager._initialize_shards` | Initial shards |
| `EmbeddingShardManager._split_shard` | New split shard |
| `HealthChecker._check_database_health` | Database health client |
| `ChromaDBOptimizer.get_client` | New pooled client |
| `OptimizedChromaStore.__init__` | Optimized collection client |

The implementation adds six existing Settings keyword arguments and updates one
comment. Storage paths, telemetry, reset settings, persistent-client caching and
stub behavior are unchanged. Explicitly injected clients and factories retain
their prior behavior and are outside this internal-client guarantee. It does not
constrain arbitrary custom Python code or certify every Chroma environment option.

`pyproject.toml` now requires `chromadb>=1.5.9`, matching the version already
resolved in `uv.lock` and used for verification. The old `>=0.4.0` floor allowed
versions lacking the selected Rust API. Chroma's
[migration guide](https://docs.trychroma.com/docs/overview/migration) documents
the Rust in-process implementation introduced in 1.0.0; 1.5.9 is this project's
tested compatibility floor. Only the corresponding root requirement metadata
changes in the lock. Parsed comparison confirms every resolved package version,
dependency edge and artifact hash remains unchanged. The lock file's own hash
changes, so earlier artifact evidence remains historical.
