## Bounded implementation

The existing release identity step authenticates the built subject and selects
its sole `linux/amd64` child. The new runtime step uses the same child output:

1. Read the child manifest by immutable repository digest and verify its raw
   SHA-256 against the selected digest. Read a well-formed config digest from
   that authenticated manifest.
2. Pull that child, then require Docker inspection to report exactly one image,
   the same repository digest and the `linux/amd64` platform.
3. Run `runtime_probe.py probe --lock /probe/uv.lock` against the immutable child
   with `--pull never`. Preserve the PR probe's network isolation, dropped
   capabilities, non-root user, read-only root, no-new-privileges setting and
   temporary scratch storage. Mount only the existing probe and lock read-only.
4. Add the parent subject, selected child and config digests to the probe result.
   Retain the runtime JSON and raw child manifest in image checksums; existing
   release assembly includes every retained file in aggregate hashes.
5. Require both runtime and vulnerability-policy success for backend admission.
   A failed probe remains visible while scanning and artifact upload can proceed;
   neither a failed nor skipped probe can produce successful backend admission.

The implementation reuses the unchanged probe and existing workflow tools.
It does not add a dependency, helper framework, exception-schema field or release
manifest-schema field. Docker's documented
[digest pull](https://docs.docker.com/reference/cli/docker/image/pull/),
[image inspection](https://docs.docker.com/reference/cli/docker/image/inspect/)
and [raw manifest inspection](https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/)
interfaces support this flow. Docker remains the trusted boundary for pulling
and running digest-addressed content; the wrapper does not reimplement layer
verification or rely on a storage-driver-specific interpretation of image `Id`.
