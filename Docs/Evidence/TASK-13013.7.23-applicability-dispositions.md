Advisories:

Prior scoped implementation/evidence is recorded in TASK-13013.7.5.

These are strong supporting facts for the tested embedded profile. They do not
prove that arbitrary server configuration, external deployment, or every
application entry point is unaffected. The probe explicitly labels its scope
as isolated embedded-client testing, not application startup. The current
version-based policy does not enforce these configuration conditions.

Three integration gaps prevent treating these records as ready to activate:

1. `source-python-root` describes the locked dependency graph, not a deployment.
   A source exception cannot silently turn an embedded-profile assessment into
   a statement that every consumer of the package is unaffected.
2. `container-build-check.yml` runs the probe, but `publish-docker.yml` does not.
   A condition established for a PR image cannot authorize a newly built release
   image without evidence for that image.
3. The pinned dependency-review action accepts `allow-ghsas`, which is an
   advisory-level allowance. It has no package-version-component expiry contract
   equivalent to our canonical policy. A static list of four GHSAs is too broad.

The recommended next Chroma change is a separately reviewed, bounded extension
that enforces the embedded-profile evidence wherever its disposition is used.
Reusing `runtime_probe.py` is appropriate for the release-image checks; full
application/configuration assumptions still need explicit validation. The source
decision must remain distinct from the image disposition. Keep Chroma in place
while defining these controls; replacement is not justified by scanner counts.

## Minimal activation path for the five OS records

1. Obtain accountable human approval of the five exact draft records, owner,
   rationale, mitigation and dates on a repository PR or issue. Do not use a
   merely existing PR URL as evidence that approval occurred.
2. Copy only those five records into
   `.github/supply-chain/vulnerability-exceptions.json`, replacing `approval:null`
   with the actual repository approval reference. No evaluator/schema change is
   needed for these exact package/component exclusions. Preserve complete raw
   scan reports and the existing 7/30-day limits.
3. Replay the actual source and five image reports through the unchanged loader
   and evaluator. Expect exactly the middle column above, five excepted rows,
   no unmatched records and no raw-report changes. Verify version/component/
   severity changes do not match and expired records fail loading. Run the
   existing exception-policy contracts and scoped security checks.
4. Update the runbook's empty-policy statement and task evidence. Independently
   review the five-record change and its verification before a separate push.
   Fresh CI still reports the remaining findings; no merge or release follows.

Dependency review needs no change for these OS-only records because it examines
source dependency changes. For a future Chroma disposition, do not set
`warn-only`, disable vulnerability checks, or hard-code `allow-ghsas`. A shared
adapter should derive any advisory allowances from unexpired canonical records
and the complete dependency diff, require every affected added package/version
to have matching approved scope, and fail on missing/ambiguous data. Its precise
source/deployment contract must be approved together with the Chroma disposition.
The pinned action exposes `vulnerable-changes`, but an allowance cannot be
derived from that output after the same action has already evaluated its inputs;
use a prior complete API diff fetch or a separate enforcement step with retained
raw output. Do not add a second independently maintained allowlist.
