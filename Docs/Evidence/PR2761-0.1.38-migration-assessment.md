Date: 2026-09-10. Tracking: TASK-13013.3, release refresh Stage 4.3.

restore rehearsal. It does not establish which version, database backend,
schema, configuration, or topology any operator currently runs. The published
0.1.38 artifact is a verifiable comparison reference, **not an asserted deployed
baseline or an approved rollback image**.

Image provenance was inspected as registry metadata; this assessment does not
claim an independent cryptographic attestation verification. Neither the image
nor an operator database was started for this assessment. The numbered schema
values below are source-supported targets, not measurements of live databases.

**Conclusion:** treat an upgrade from this reference as a forward migration.
Switching an old binary onto migrated live databases is not a supported recovery
plan. Recover the whole matching pre-upgrade state, or retain the new schema and
forward-fix. Recovery to an earlier backup loses subsequent writes unless a
separate, validated recovery procedure preserves and reapplies them.

## Compatibility by subsystem

### AuthNZ and profile state

The [SQLite migration registry](../../tldw_Server_API/app/core/AuthNZ/migrations.py)
ends at 89 in the published source and at 98 in the inspected release source.
New entries 90–98 have no registered reverse migration:

- 90 seeds notification permissions and role memberships.
- 91 rebuilds/validates the durable `users.profile_version` anchor.
- 92 backfills and requires profile-candidate timestamps for organizations,
  teams, memberships, and configuration overrides. SQLite tables may be rebuilt;
  indexes/triggers are restored and foreign keys checked.
- 93 harmonizes legacy user-write columns.
- 94 creates canonical webhook tables; 96 adds delivery recovery and runtime
  heartbeat state.
- 95 seeds Notes graph suggestion permissions.
- 97 backfills missing user UUIDs without rebuilding `users` or removing its
  profile-version triggers; 98 adds/backfills session activity timestamps.

These changes include data backfills, new write invariants, and authorization
state, not just optional columns. An older writer cannot be assumed to honor
the new profile-version contract. Do not remove triggers, edit migration
versions, or use unrelated older `rollback_*` table-dropping helpers as a
release downgrade. PostgreSQL uses its own schema/bootstrap/readiness paths;
the SQLite version comparison is not proof of a PostgreSQL migration rehearsal.

Back up the actual AuthNZ database together with users, UUIDs, profile anchors,
memberships, grants, user/org/team overrides, provider-secret records, sessions,
and canonical webhook state. Preserve the separately managed keys/configuration
needed to interpret encrypted records. Validate representative identities and
permissions after restoration, not just row counts.

### Conversations, characters, and Buddy

[ChaChaNotes schema targets](../../tldw_Server_API/app/core/DB_Management/ChaChaNotes_DB.py)
advance from **51 to 66**, for SQLite and the current PostgreSQL target. The
database initializer rejects a schema newer than the code supports. An old
schema-51 binary must not be made to open schema 66 by rewriting its version row.

Relevant changes include recipient-owned shared-workspace chat threads and
durable request/replay receipts (61), staged workspace clone markers (62),
conversation behavior snapshots and resume state (65), and independent
principal-owned Buddy profiles/attachments (66). The Buddy migration explicitly
preserves Persona rows. A legacy character card is not a substitute for the
conversation's saved behavior snapshot or associated resume state.

Preserve the whole per-user conversation/Notes database and any externally
stored attachment bytes, along with ownership identities in AuthNZ. Check a
saved conversation with messages, character/resume state, shared-chat receipt,
and Buddy attachment where those features are used. A rollback to the earlier
backup omits any such state created after that backup.

### Notes organization, links, tasks, and Sync

The same schema 51→66 chain includes source review plans (52), EMQ metadata
(53), workspace source saved views (54), stable organization UUIDs (55),
WebClipper note rekeying (56), PostgreSQL organization tenancy (57), canonical
Notes links (58), attachment registry structures (59), a rebuilt scoped task
graph (60), scoped moodboard/placement/Studio authority storage (63), and graph
suggestion operation receipts (64).

Several transformations preclude treating this as an additive-only migration:

- WebClipper migration rekeys legacy note identities and references. It rejects
  collisions, unverifiable history, and already-published canonical history
  requiring explicit migration; do not bypass those checks.
- The task migration copies and verifies the graph, replaces the old tables,
  rebuilds indexes, and advances the version last. Restoring only old task rows
  into the new tables is not a supported reverse operation.
- PostgreSQL migrations validate owner/dataset authority and RLS and can block
  affected writers. [Notes link ADR](../ADR/037-canonical-notes-link-sync-and-derived-graph-projections.md),
  [attachment ADR](../ADR/038-canonical-notes-attachment-registry-and-blob-lifecycle.md),
  and [task ADR](../ADR/039-canonical-notes-task-sync-and-derived-checklist-projections.md)
  describe the separate schema, enrollment, and runtime authority boundaries.

Schema installation does not imply successful Sync bootstrap. Attachment schema
59 creates structures without importing legacy bytes. Runtime bootstrap is
resumable and source-verified and retains original files as non-authoritative
cleanup candidates. Once canonical attachment authority is initialized,
disabling its rollout flag does **not** restore mutable legacy files as the
authority. Preserve both until the documented retention workflow permits cleanup.

Restore must include the owning Note before a live attachment reference, plus
canonical metadata, immutable revision bindings, verified blob bytes, Sync
envelopes/heads, device acknowledgements, enrollment/bootstrap state, and
retention/quarantine/repair holds. Note trash intentionally does not delete its
attachment bindings or explicit links. Restoring the Notes database alone can
therefore leave missing bytes or mismatched history even if its integrity check
passes.

The default Sync database filename is `Sync_v2.db`; configured backend URLs may
change its location. [The blob factory](../../tldw_Server_API/app/core/Sync/v2/factory.py)
uses `SYNC_V2_BLOB_STORE_PATH` when set, otherwise the user database base directory's
`_sync_v2_blobs` directory. Inventory these actual locations rather than assuming
all bytes are inside one user's database directory. Stop Sync ingress, background
materializers, and retention/GC writers during snapshot/restore coordination.
Already-collected bytes cannot be recovered merely by restoring a tombstone or
reference; they must exist in the recovery set.

### Presentation storage

The release introduces authoritative [Slides schema-v2 migration](../../tldw_Server_API/app/core/Slides/slides_migrations.py):
content kind and standalone HTML metadata, generation provenance/job links,
version metadata, generation receipts, and retained input state. Structured
presentations retain their structured content kind.

The [deployment runbook](../Deployment/Standalone_HTML_Presentations.md)
explicitly declares this forward-only for old binaries. Back up **every per-user
`Slides.db` and the actual Jobs database** before migration. Keep standalone
generation and egress disabled until the documented schema, keyring, adapter,
and capability checks pass. Preserve the environment-only
`SLIDES_STANDALONE_HMAC_KEYS_JSON` and current-key identity in protected secret
backup; retiring keys have a minimum 32-day retention and fenced reference checks.

Disabling generation leaves saved standalone documents intact; use the new binary
for their supported read/edit/export paths. Full binary rollback requires a
pre-migration database restore. Restoring Jobs and Slides from inconsistent times
can disagree about receipts/completion. Provider calls are at-least-once, so
external calls or charges already made cannot be undone by database restoration.
The published 0.1.38 image's compatibility with the *current* deployment topology,
probes, and configuration must itself be checked on the isolated host.

### Personal Context

Current [Personalization database storage](../../tldw_Server_API/app/core/DB_Management/Personalization_DB.py)
adds canonical encrypted object versions/heads, wrapped profile keys, receipts,
publication batches, activation/device state, and purge-cleanup intents.
The [developer guide](../Code_Documentation/Personal_Context_Developer_Guide.md)
distinguishes this canonical per-user `Personalization.db` from Sync transport
history and the separate Companion/Persona system.

Back up the complete database and associated Sync state together. Preserve the
original `TLDW_PERSONAL_CONTEXT_MASTER_KEY` through protected secret custody:
the [key provider](../../tldw_Server_API/app/core/DB_Management/Personal_Context_Key_Store.py)
uses it to unwrap independent per-profile keys. Missing, changed, or orphaned key
material locks the profile; creating a replacement key does not recover ciphertext.
Peer-local at-rest keys are not synchronized. Preserve separately configured
Sync encryption/integrity key material as applicable.

The passphrase-protected recovery export is **not a complete backup**: it contains
current manifest/scopes/records and excludes proposals, runtime policies, local
workspace mappings, keys, receipts, and Sync operational state. The guide records
no supported server importer/restorer for that envelope. Do not substitute it
for a database-and-key restore. Do not infer a fully operational ongoing client
sync or distributed purge lifecycle from the presence of server schema alone.

### Canonical admin webhooks

The [migration runbook](../Admin_Webhooks_Migration_Runbook.md) handles both legacy
`admin_webhooks` rows and `system_ops.json` webhook fields. Schema installation
and legacy-data import are separate. Import requires all writers quiesced, a
reviewed dry-run mapping, an independently approved literal report digest, and
separate private encrypted-backup and rollback-key paths. Registrations import
inactive; the CLI flag asserts writer quiescence but cannot prove it.

The runbook's "before import" code-revert statement is scoped to this additive
webhook schema and does not override the other release downgrade restrictions.
After import, structural file recovery is conditional on retained artifacts,
the unexpired rollback window, and `legacy_file_restore_permitted=true`.
Default retention is seven days, configurable from one to 30 days. First canonical
mutation or delivery permanently closes legacy restoration; keep canonical mode
off and forward-fix instead of deleting migration state to reopen the window.

Preserve AuthNZ/canonical registrations, source mapping/report, migration state,
current `system_ops.json`, dedicated webhook keyring, encrypted source backup,
and its separate contextual rollback key. Extraction creates a new private
plaintext file; approved structural recovery merges only `webhooks` and
`webhook_deliveries` into the **current** object using the lock and atomic writer.
Whole-file replacement can discard unrelated newer operational state. Database
restore also cannot retract external deliveries or guarantee that replay will
have no downstream effects.

## Minimum coordinated recovery set

1. **Identity and configuration:** actual current/target/rollback image digests,
   source revisions, pinned Compose/proxy files and hashes, database backend
   versions, all relevant feature/enrollment flags, and protected secret/config
   backup. Record secret references and custody, never values.
2. **Databases:** actual AuthNZ, every affected per-user `ChaChaNotes.db`,
   `Media_DB_v2.db`, `Slides.db`, `Personalization.db`, `Sync_v2.db`, and the Jobs
   backend. Include other application databases in the full deployment snapshot;
   this selected-subsystem assessment is not an exhaustive data inventory.
3. **Bytes and operational state:** uploads/media originals, Notes/character/Buddy
   attachments, Sync blobs and retained legacy attachment files, external mounts
   or object storage, `system_ops.json`, webhook recovery artifacts, and applicable
   Redis state. Inventory configured paths outside normal app-data volumes.
4. **Consistency:** quiesce every API, worker, scheduler, Sync, GC, migration, and
   direct administrative writer. Use database-supported snapshots/backups; do not
   copy an active SQLite main file while ignoring WAL state. Preserve the schema,
   foreign keys, triggers, ownership/RLS metadata, and recovery position together.

For the reference PostgreSQL/Redis Compose topology,
[Production Reference Deployment](../Deployment/Production_Reference_Deployment.md)
and [production_deploy.py](../../Helper_Scripts/Deployment/production_deploy.py)
require a PostgreSQL custom dump, Redis RDB, and app-data tar in one checksummed
manifest. Rollback verifies the exact Compose hash and target/rollback image
inputs and restores artifacts before starting the prior image. Secrets/config
are intentionally outside that manifest. External storage or separate database
clusters need their own coordinated recovery evidence; the three manifest
artifacts do not establish their coverage automatically.

Archive inspection, `pg_restore --list`, and `redis-check-rdb` are necessary
artifact checks, not authenticated application-data proof. Use a disposable
host/project and recovery copies, verify the actual topology is isolated, then
follow the documented rollback flow with the matching manifest/configuration.
Do not repoint a development command at an unknown production installation.
