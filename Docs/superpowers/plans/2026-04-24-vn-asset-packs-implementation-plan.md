# VN Asset Packs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first offline VN Asset Packs feature: pack/slot/item metadata, approved-only manifests, Jobs-backed image generation, durable generated-file serving, and a thin `/vn-assets` WebUI workbench.

**Architecture:** Store VN pack metadata in each user's `ChaChaNotes.db` beside character cards and world books, while storing image bytes through AuthNZ generated-file storage. Backend services under `core/VN_Assets` own matrix expansion, prompt assembly, state transitions, manifest building, fanout, and worker orchestration. The frontend consumes the new `/api/v1/vn-assets` endpoints through a typed client and offers setup, generation monitoring, and review without VN playback.

**Tech Stack:** FastAPI, Pydantic v2, SQLite-backed `CharactersRAGDB`/ChaChaNotes, AuthNZ generated files, core Jobs, image-generation adapters, pytest, Bandit, Next.js, React, TypeScript, Ant Design, Vitest, Playwright.

---

## Source Spec

- Design: `Docs/superpowers/specs/2026-04-24-vn-asset-packs-design.md`
- Current status: Draft design accepted for implementation planning.
- Important constraints:
  - V1 is offline asset generation only, no VN playback.
  - V1 uses one `primary_character_id` per pack.
  - VN metadata lives in per-user `ChaChaNotes.db`.
  - Generated bytes and quota tracking live in AuthNZ generated-file storage.
  - Jobs use a parent fanout job, not direct API enqueue of hundreds of child jobs.
  - Local/GPU image generation defaults to one active VN generation at a time.
  - Physical file cleanup is explicit `POST /cleanup`, not `DELETE` query flags.
