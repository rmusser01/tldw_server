# TASK-15481 Implementation Plan: the hosted plan decides whether an own-key /chat/completions request may fail over

**Goal:** With provider fallback on, an own-key `/chat/completions` request from an org over its hosted plan gets no failover reply on another key (usually the server's), by any of the four failover paths, stream and non-stream; an org within its plan keeps failover.

**Architecture (recommended option, "check at the boundary"):** `/chat/completions` already asks `users_own_key_serves` once and, for an own-key request, enters no `LimitEnforcer` (ADR-083). The change asks the plan's pre-check one more question for such a request when fallback is on: would it refuse a server-key call of this request's size now? If yes, `allow_provider_fallback_for_request` is set False for the request. Every failover path reads that flag (`chat.py:5234` the pre-dispatch health switch, `:5651` and `:5955` the two executors' `enable_provider_fallback`, `:5855` the stream retry loop), so one flag at the boundary covers all four, with no change to the executors or their exception paths. Two module-level helpers in `chat.py` carry the plan's pre-check: `_enter_the_hosted_plans_enforcer` (the existing inline pre-check block, moved out of `create_chat_completion`, which is exactly at its function-size cap) and `_the_hosted_plan_refuses` (the same pre-check as a yes/no, nothing recorded). The hot cache is not touched for a within-plan failover reply: its row counts at the next billing cache refresh, as it does on `origin/dev`.

**Tech Stack:** FastAPI, pytest (`authenticated_client`, the credential runtime double and `_certified_pre_dispatch` from `tests/Chat/integration/test_chat_endpoint_simplified.py`, the `_PlanSpent` stub from `test_chat_llm_tokens_quota_402.py`).
