# Release 0.1.41 Design

Date: 2026-07-15
Status: Approved for planning
Owner: Codex release session
Backlog: TASK-12973

## Summary

Prepare and publish `0.1.41` from the frozen `dev` snapshot at
`4c2ad2070ed63992dac8a97a6c4cf3c7d75f6de8` (through PR #2744). The release
uses an isolated `codex/release-main-0.1.41` branch, updates the authoritative
project version and human-facing release documentation, merges the reviewed
release branch into `main`, tags the resulting `main` commit as `v0.1.41`,
publishes the GitHub Release, verifies publication, and then synchronizes
`main` back into `dev`.

All PRs still open against `dev` are outside this release. The user's dirty
primary checkout is also outside the release work and must remain untouched.

## Release Boundary

- Source snapshot: `origin/dev` at
  `4c2ad2070ed63992dac8a97a6c4cf3c7d75f6de8`.
- Last included merge: PR #2744.
- Target branch: `main`.
- Target version and tag: `0.1.41` / `v0.1.41`.
- Previous published GitHub Release: `v0.1.38`.
- Existing `0.1.39` and `0.1.40` metadata is treated as untagged release-train
  history; it will not be backfilled during this task.
- Open PRs, dependency updates not merged into the frozen source snapshot, and
  any later `dev` commits are excluded.

At the freeze point, GitHub reports `dev` 664 commits ahead of and 17 commits
behind `main`, with merge base `440478b6cbaf9cb66e759ef6e8cebb859c81b44e`.
The release PR must preserve both histories. If GitHub cannot merge the PR
cleanly, merge current `origin/main` into the release branch, resolve only the
resulting release conflicts, and rerun the release verification. Do not rebase
the release branch onto a moving `dev` head.

## Release Metadata And Documentation

The release changes only the authoritative project-wide surfaces:

- `pyproject.toml`: canonical package version `0.1.41`.
- `tldw_Server_API/app/main.py`: FastAPI application version `0.1.41`.
- `Docs/mkdocs.yml`: site version and copyright version `v0.1.41`.
- `CHANGELOG.md`: reset `Unreleased` and add a dated `0.1.41` section.
- `README.md`: current release line, `dev`/`main` status text, a new
  `0.1.41` What's New section, and the prior-release supersession note.
- `Docs/RELEASE_NOTES.md`: add the maintainer-facing `0.1.41` entry.
- `Docs/Published/RELEASE_NOTES.md`: add the published user-facing `0.1.41`
  entry while preserving the canonical release-process pointer.

Subproject versions such as the standalone MCP package, SDKs, browser
extension, macOS helper, mock server, and Backlog.md tooling are independent
package contracts and will not be bumped unless their own release metadata
explicitly tracks the root project version.

The release date is the actual merge/publication date. If CI or review pushes
publication to a later day, update the dated changelog and release-note headings
before merging.

## Preparation And Review Flow

1. Work only in the isolated release worktree and record progress in
   `TASK-12973`.
2. Confirm the branch still starts at the frozen SHA and that no later `dev`
   changes have entered the release branch.
3. Update the seven authoritative release surfaces listed above.
4. Run focused release helper/docs tests, metadata consistency checks, Markdown
   checks available in the repository, `git diff --check`, and Bandit on the
   touched Python file or record a documentation-only skip where applicable.
5. Review the complete `main...release-branch` diff for accidental files,
   secrets, generated outputs, and unsupported version bumps.
6. Commit and push the release branch, then open a non-draft PR against `main`
   with the frozen boundary, rollup summary, verification evidence, and a
   clearly marked human-owned `Change summary` requirement.
7. Do not merge until the required release PR checks are present and green.
   Although `main` currently has no GitHub branch-protection rule, this release
   voluntarily enforces the six names in `Docs/Development/CI_REQUIRED_GATES.md`:
   `backend-required`, `security-required`, `coverage-required`,
   `frontend-required`, `e2e-required`, and `container-build-check`.

The user has authorized the release operation, including merge, tag, and
publication, subject to the green-gate requirement. A failing or missing
required gate pauses the cut for diagnosis; it is never bypassed.

## Tagging And Publication

After the release PR merges:

1. Fetch `origin/main` and verify the merge contains the frozen release commit
   and reports `0.1.41` on every authoritative version surface.
2. Create annotated tag `v0.1.41` on the final `origin/main` merge commit.
3. Push only that tag and create the GitHub Release with the `0.1.41`
   changelog section as its body.
4. Verify the GitHub Release and tag resolve to the same commit.
5. Verify the release-triggered Docker and PyPI workflows and the main-snapshot
   workflows. Report any skipped publication path separately from failures.
6. Synchronize the released `main` history back into `dev` through a reviewed
   PR so `dev` carries the release metadata and tag ancestry before subsequent
   release work.

The existing `Helper_Scripts/release.py --bump patch` path is not invoked for
this cut. Once the release branch is pre-bumped to `0.1.41`, that helper would
compute `0.1.42`; using it would create the wrong release. This is a one-release
operator exception, not a redesign of the helper.

## Failure And Recovery Rules

- If the release PR conflicts with `main`, merge `origin/main` into the release
  branch, resolve deliberately, and rerun all release checks.
- If any required PR gate fails or remains missing, stop before merge and
  diagnose the gate. Do not use a force merge or bypass.
- If `origin/main` moves after approval but before merge, refresh PR mergeability
  and required checks before proceeding.
- If tag creation succeeds locally but tag push fails, verify the tag target and
  retry only the tag push; never recreate it on a different commit.
- If the remote tag exists but GitHub Release creation fails, reuse the existing
  tag and retry only GitHub Release creation.
- If the GitHub Release exists, treat publication as complete and verify remote
  artifacts instead of creating a second release.
- Never force-push `main`, `dev`, the release branch, or the release tag.

## Verification

Minimum local verification before the PR:

- focused release helper, Makefile target, and release-doc contract tests
- exact version search showing only intentional historical `0.1.40` references
- parsing/import check for the FastAPI version surface
- changelog structure and duplicate-bullet validation
- Markdown/docs validation available for the touched source documents
- `git diff --check`
- Bandit on `tldw_Server_API/app/main.py` because it is the only touched Python
  source file

Remote verification:

- required PR checks green on the final release PR head
- merged PR commit present on `origin/main`
- `v0.1.41` tag and GitHub Release target the final `main` commit
- release Docker workflow, PyPI workflow, and rolling main-snapshot workflows
  reach an expected terminal state
- post-release sync PR restores released `main` history to `dev`

## Non-Goals

- Including any open or post-freeze `dev` PR
- Backfilling `v0.1.39` or `v0.1.40`
- Refactoring the release helper or changing publication workflows
- Bumping independently versioned subprojects
- Broad code cleanup, feature changes, or unrelated documentation rewrites
- Force-merging around missing or failing CI

## Decision

Use the reviewed release-branch flow above. It is the smallest approach that
preserves the frozen `dev` boundary, gives release metadata full PR/CI coverage,
handles the existing branch divergence without losing history, and produces an
auditable `v0.1.41` release from the final `main` commit.
