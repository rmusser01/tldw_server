# Release 0.1.41 Zero-Warning Documentation Design

**Status:** Approved

**Task:** TASK-12973

**Release branch:** `codex/release-main-0.1.41`

**Frozen product source:** `origin/dev@4c2ad2070ed63992dac8a97a6c4cf3c7d75f6de8`

## Context

The original `0.1.41` release verification required a strict MkDocs build. The
checked-in `Docs/Published` snapshot aborts with 101 warnings. A frozen-source
comparison proved that those warnings predate the release metadata changes:
after normalizing only the output directory, the current and frozen logs have
the same SHA-256,
`d76e23890a0f71884f229e150910e91872fc24a4b4a8060ae6dc819eadd342b1`.

The repository's actual documentation pipeline first runs
`Helper_Scripts/refresh_docs_published.sh`. Running that refresh in a disposable
snapshot exposes 122 warnings: two invalid navigation paths and 120 invalid
document links. The larger count is expected because the checked-in generated
tree is stale and omits recently added canonical source pages.

The requester expanded the release scope on 2026-07-16: `0.1.41` must reduce
the real refresh-then-build pipeline to zero warnings. A baseline waiver is no
longer acceptable.

## Goals

- Make the checked-in curated documentation build successfully with
  `mkdocs build --strict -f Docs/mkdocs.yml` and zero warnings.
- Make the CI-equivalent sequence—refresh `Docs/Published`, then run the same
  strict build—succeed with zero warnings.
- Repair links at their canonical source so the refresh script reproduces the
  clean result.
- Preserve the existing OSS/public documentation boundary.
- Turn strict MkDocs validation back on in every workflow that refreshes and
  builds the public site, preventing the baseline from returning.
- Keep the release version, changelog, README, tagging, publication, and sync
  behavior from the approved `0.1.41` release design unchanged.

## Non-Goals

- Publishing hosted, commercial, private, WIP, or unrelated repository trees.
- Rewriting documentation content beyond what is necessary to repair link
  meaning and navigation.
- Adding placeholder pages solely to satisfy MkDocs.
- Ignoring or downgrading MkDocs validation messages.
- Validating remote URL availability during the build; strict MkDocs validates
  local site structure, while remote GitHub links remain ordinary external
  references.

## Chosen Approach

Use canonical-source repair followed by deterministic regeneration.

1. Fix navigation paths in `Docs/mkdocs.yml` so they match the layout produced
   by `refresh_docs_published.sh`.
2. Fix invalid links in canonical files under `Docs/`, using the link policy
   below.
3. Make the refresh script build a complete staging tree from an explicit
   canonical-input manifest, fail on copy errors, and replace
   `Docs/Published` through a rollback-safe directory swap. No output depends
   on files already present in the destination.
4. Run the refresh script and commit the resulting curated `Docs/Published`
   tree. Do not hand-edit generated mirrors.
5. Enable `--strict` in both documentation workflows that refresh and build
   the site.
6. Verify the checked-in snapshot, clean and stale-seeded regeneration, and
   the CI-equivalent refresh-then-build path.

This is preferred over expanding the published tree because copying every
referenced source would violate the documented curation boundary and expose
unreviewed material. It is preferred over warning suppression because a clean
exit obtained by ignoring broken links would not meet the request.

## Link Resolution Policy

Each warning is resolved according to the target's ownership:

| Target kind | Resolution |
| --- | --- |
| Page already included in the curated public site | Correct the relative site link to that page's generated location. |
| Canonical page in an approved source tree but missing from stale `Docs/Published` | Correct the source link if needed, then let the refresh script publish it. |
| Durable OSS/self-host source, code, or intentionally public documentation outside the curated site | After boundary review, use an absolute `https://github.com/rmusser01/tldw_server/blob/main/...` or `tree/main/...` link. |
| Obsolete or nonexistent target with a maintained replacement | Link to the closest authoritative replacement and preserve the surrounding meaning. |
| Obsolete target with no replacement | Remove the hyperlink while retaining useful explanatory text; do not invent a page. |

The implementation must inspect every changed link's destination. Mechanical
string replacement is allowed only when all occurrences have the same intended
target. WIP, hosted, commercial, internal-operations, and ambiguous targets
must not be externalized merely to silence MkDocs; use an approved public
replacement or plain text. Record every new GitHub target, verify its local
path exists at the frozen release source or in a reviewed release-owned change,
and review it against `Docs/Policies/OSS_Private_Boundary.md`.

## Generated Documentation Boundary

Canonical content remains outside `Docs/Published`; the latter is replaced
generated output. The refresh script uses this explicit manifest:

| Canonical input | Published output |
| --- | --- |
| `Docs/Site/index.md` | `index.md` |
| `Docs/Site/RELEASE_NOTES.md` | `RELEASE_NOTES.md` |
| `Docs/Wiki` | `Wiki` |
| `Docs/API-related` | `API-related` |
| `Docs/ADR` | `ADR` |
| `Docs/Code_Documentation` | `Code_Documentation` |
| `Docs/Deployment`, excluding `Monitoring` | `Deployment` |
| `Docs/Deployment/Monitoring` | `Monitoring` |
| `Docs/Evaluations`, with the existing `Docs/Evals` fallback | `Evaluations` |
| `Docs/Getting_Started` | `Getting_Started` |
| `Docs/User_Guides` | `User_Guides` |
| `Docs/Architecture.md` | `Architecture.md` |
| `Docs/Operations/Env_Vars.md` | `Env_Vars.md` |
| `Docs/Overview/Feature_Status.md` | `Overview/Feature_Status.md` |
| `Docs/Logo.png` | `assets/logo.png` and `assets/favicon.png` |

`Docs/Site/index.md` becomes the canonical source for the current generated
home page. The existing directly maintained feature-status page moves from
`Docs/Published/Overview/Feature_Status.md` to
`Docs/Overview/Feature_Status.md`. The concise public release-notes source moves
from `Docs/Published/RELEASE_NOTES.md` to `Docs/Site/RELEASE_NOTES.md`, while
the detailed maintainer-facing `Docs/RELEASE_NOTES.md` remains a separate
release surface. The public release notes and canonical environment-variable
reference are published through explicit copies rather than retained
destination state.

For a source directory that contains both `index.md` and `README.md`, the
refresh always publishes `index.md` and omits the colliding README. Otherwise,
the README remains a normal page. Missing required inputs and copy failures are
fatal; `2>/dev/null || true` is removed.

The script creates a sibling staging directory, populates only the manifest,
then swaps it into the destination with a backup/restore path so a failed swap
does not destroy the last complete tree. An optional destination override is
permitted solely as a test seam and uses the same generation path.

The cleanup may modify many generated files because the committed mirror is
stale. Review must distinguish deterministic refresh output from canonical
source edits. Tests compare output from an empty destination, a destination
seeded with unknown/stale files, and the committed snapshot. All three trees
must be identical, and an immediate second refresh must produce no diff.

`Docs/Code_Documentation/Docs_Site_Guide.md` is part of the canonical cleanup.
It will document the complete manifest above, include `Getting_Started`, make
strict local and external builds the required commands, and remove wording that
treats strict validation as future optional work. Its generated mirror is
updated only through refresh.

`Helper_Scripts/release.py` and its focused tests will update
`Docs/Site/RELEASE_NOTES.md` as the canonical concise public release surface.
The release workflow then regenerates `Docs/Published/RELEASE_NOTES.md` through
the same refresh path. The existing canonical release-process pointer remains
required in the concise public source and generated mirror.

## Navigation

Navigation entries must use paths relative to `Docs/Published`. In particular,
the monitoring tree is promoted to top-level `Monitoring`, and the generated
environment-variable reference is top-level `Env_Vars.md`. The implementation
must verify every configured nav target exists after refresh.

## CI Enforcement

Both `.github/workflows/mkdocs.yml` and
`.github/workflows/onboarding-docs-gate.yml` already refresh the curated tree
before building it. Their build commands will use `--strict`. The historical
TASK-12074 comment that permits a warning baseline will be removed or updated
to state that strict validation is restored by TASK-12973.

The pull-request workflow will run
`Helper_Scripts/docs/check_public_private_boundary.py`. Its pull-request and
push path filters will explicitly include
`Helper_Scripts/refresh_docs_published.sh` and `.github/workflows/mkdocs.yml`,
in addition to the paths it already monitors, so a refresh-script or deploy-
workflow-only change cannot bypass the strict/boundary gate.

No `validation` setting, warning filter, shell exception, or conditional bypass
may convert warnings into success. A strict-build failure remains a release
blocker.

## Verification

The zero-warning slice is complete only when all of the following pass from the
project virtual environment:

1. Refresh the curated tree, then run strict MkDocs. The command exits zero and
   emits no `WARNING` lines.
2. Run regeneration tests from independently empty and stale-seeded
   destinations. Their file lists and content hashes match each other and the
   committed `Docs/Published` tree; no seeded unknown file survives.
3. Run the refresh script again. `git status --short` remains unchanged,
   proving the committed tree is current and idempotent.
4. Build the checked-in tree strictly in an exported clean snapshot without a
   refresh. It also exits zero with no warnings.
5. Run existing docs link-hygiene, public/private-boundary, audience-wiki,
   onboarding, and release-doc contract tests that cover changed areas, plus a
   focused regression test for empty/stale generation and the
   index-over-README rule.
6. Validate both workflow files and assert their exact strict build commands,
   the PR boundary-check step, and the refresh/deploy-workflow trigger paths.
7. Run `git diff --check`, inspect the complete canonical and generated diff,
   and scan changed content for secrets, private/hosted material, accidental
   files, and unrelated rewrites.
8. Apply the repository Bandit policy to any changed Python; otherwise record a
   docs/YAML/shell-only Bandit skip. If the refresh shell script changes, run
   `bash -n` and the relevant script tests.
9. Rerun the complete `0.1.41` release verification after this slice is merged
   into the release branch.

## Failure Handling

- If refresh creates a warning not present in the checked-in snapshot, fix its
  canonical source rather than patching only the generated copy.
- If staging-tree creation or the destination swap fails, return nonzero,
  remove the incomplete staging tree, and restore the prior complete
  destination when it was moved.
- If a target's public/private status is unclear, stop that link change and
  review it against `Docs/Policies/OSS_Private_Boundary.md`.
- If zero warnings would require publishing a new directory, treat that as a
  design change requiring requester approval; do not expand curation silently.
- If a remote repository target does not exist on the frozen release branch,
  use a maintained replacement or plain text rather than a knowingly broken
  GitHub URL.

## Release Integration

Before implementation begins, the existing release implementation plan must be
amended or supplemented. It must replace the original seven-file-only and
"no generated output" assumptions with an explicit file map and commit
boundaries for canonical docs, generated output, refresh script/tests,
release-helper contract/tests, workflows, changelog, plan, and Backlog evidence.
Its frozen-diff allowlist, checked-in and refresh-then-build strict checks,
regeneration tests, workflow checks, and complete patch audit must match this
design.

The documentation cleanup is part of the `0.1.41` release PR, not a separate
post-release follow-up. Its commits remain after the frozen product SHA as
reviewed release-owned changes. `CHANGELOG.md` and the release PR description
will identify strict public-documentation cleanup and deterministic publication
as release preparation. The amended plan must preserve Task 4's two
CI-capacity sweeps and human-authored Change summary gate, and Task 5's
merge/tag/publication/main-to-dev sync flow without weakening them.
