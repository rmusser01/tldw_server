# Release 0.1.41 Zero-Warning Documentation Design

**Status:** Approved direction; pending written-spec review

**Task:** TASK-12973

**Release branch:** `codex/release-main-0.1.41`

**Frozen product source:** `origin/dev@4c2ad2070ed63992dac8a97a6c4cf3c7d75f6de8`

## Context

The original `0.1.41` release verification required a strict MkDocs build. The
checked-in `Docs/Published` snapshot aborts with 101 warnings. A frozen-source
comparison proved that those warnings predate the release metadata changes:
after normalizing only the output directory, the current and frozen logs have
the same SHA-256,
`d76e23890a0f71884f229e150910e91872fc24a4b4a8060ae6dc819eadd342b1`.

The repository's actual documentation pipeline first runs
`Helper_Scripts/refresh_docs_published.sh`. Running that refresh in a disposable
snapshot exposes 122 warnings: two invalid navigation paths and 120 invalid
document links. The larger count is expected because the checked-in generated
tree is stale and omits recently added canonical source pages.

The requester expanded the release scope on 2026-07-16: `0.1.41` must reduce
the real refresh-then-build pipeline to zero warnings. A baseline waiver is no
longer acceptable.

## Goals

- Make the checked-in curated documentation build successfully with
  `mkdocs build --strict -f Docs/mkdocs.yml` and zero warnings.
- Make the CI-equivalent sequence—refresh `Docs/Published`, then run the same
  strict build—succeed with zero warnings.
- Repair links at their canonical source so the refresh script reproduces the
  clean result.
- Preserve the existing OSS/public documentation boundary.
- Turn strict MkDocs validation back on in every workflow that refreshes and
  builds the public site, preventing the baseline from returning.
- Keep the release version, changelog, README, tagging, publication, and sync
  behavior from the approved `0.1.41` release design unchanged.

## Non-Goals

- Publishing hosted, commercial, private, WIP, or unrelated repository trees.
- Rewriting documentation content beyond what is necessary to repair link
  meaning and navigation.
- Adding placeholder pages solely to satisfy MkDocs.
- Ignoring or downgrading MkDocs validation messages.
- Validating remote URL availability during the build; strict MkDocs validates
  local site structure, while remote GitHub links remain ordinary external
  references.

## Chosen Approach

Use canonical-source repair followed by deterministic regeneration.

1. Fix navigation paths in `Docs/mkdocs.yml` so they match the layout produced
   by `refresh_docs_published.sh`.
2. Fix invalid links in canonical files under `Docs/`, using the link policy
   below.
3. Run the existing refresh script and commit the resulting curated
   `Docs/Published` tree. Do not hand-edit generated mirrors.
4. Enable `--strict` in both documentation workflows that refresh and build
   the site.
5. Verify both the checked-in snapshot and a clean refresh-then-build path.

This is preferred over expanding the published tree because copying every
referenced source would violate the documented curation boundary and expose
unreviewed material. It is preferred over warning suppression because a clean
exit obtained by ignoring broken links would not meet the request.

## Link Resolution Policy

Each warning is resolved according to the target's ownership:

| Target kind | Resolution |
| --- | --- |
| Page already included in the curated public site | Correct the relative site link to that page's generated location. |
| Canonical page in an approved source tree but missing from stale `Docs/Published` | Correct the source link if needed, then let the refresh script publish it. |
| Repository file or document intentionally outside the curated site | Use an absolute `https://github.com/rmusser01/tldw_server/blob/main/...` or `tree/main/...` link. |
| Obsolete or nonexistent target with a maintained replacement | Link to the closest authoritative replacement and preserve the surrounding meaning. |
| Obsolete target with no replacement | Remove the hyperlink while retaining useful explanatory text; do not invent a page. |

The implementation must inspect every changed link's destination. Mechanical
string replacement is allowed only when all occurrences have the same intended
target.

## Generated Documentation Boundary

Canonical content remains under the approved source directories documented in
`Docs/Code_Documentation/Docs_Site_Guide.md`. `Docs/Published` remains generated
output. The refresh script already removes the
`Code_Documentation/README.md`/`index.md` collision; committing a fresh generated
tree removes that warning without a new special case.

The cleanup may modify many generated files because the committed mirror is
stale. Review must distinguish deterministic refresh output from canonical
source edits. A second refresh after the first must produce no diff.

## Navigation

Navigation entries must use paths relative to `Docs/Published`. In particular,
the monitoring tree is promoted to top-level `Monitoring`, and the generated
environment-variable reference is top-level `Env_Vars.md`. The implementation
must verify every configured nav target exists after refresh.

## CI Enforcement

Both `.github/workflows/mkdocs.yml` and
`.github/workflows/onboarding-docs-gate.yml` already refresh the curated tree
before building it. Their build commands will use `--strict`. The historical
TASK-12074 comment that permits a warning baseline will be removed or updated
to state that strict validation is restored by TASK-12973.

No `validation` setting, warning filter, shell exception, or conditional bypass
may convert warnings into success. A strict-build failure remains a release
blocker.

## Verification

The zero-warning slice is complete only when all of the following pass from the
project virtual environment:

1. Refresh the curated tree, then run strict MkDocs. The command exits zero and
   emits no `WARNING` lines.
2. Run the refresh script again. `git status --short` remains unchanged,
   proving deterministic generated output.
3. Build the checked-in tree strictly in an exported clean snapshot without a
   refresh. It also exits zero with no warnings.
4. Run existing docs link-hygiene, public/private-boundary, audience-wiki,
   onboarding, and release-doc contract tests that cover changed areas.
5. Validate both workflow files and their exact strict build commands.
6. Run `git diff --check`, inspect the complete canonical and generated diff,
   and scan changed content for secrets, private/hosted material, accidental
   files, and unrelated rewrites.
7. Apply the repository Bandit policy to any changed Python; otherwise record a
   docs/YAML/shell-only Bandit skip. If the refresh shell script changes, run
   `bash -n` and the relevant script tests.
8. Rerun the complete `0.1.41` release verification after this slice is merged
   into the release branch.

## Failure Handling

- If refresh creates a warning not present in the checked-in snapshot, fix its
  canonical source rather than patching only the generated copy.
- If a target's public/private status is unclear, stop that link change and
  review it against `Docs/Policies/OSS_Private_Boundary.md`.
- If zero warnings would require publishing a new directory, treat that as a
  design change requiring requester approval; do not expand curation silently.
- If a remote repository target does not exist on the frozen release branch,
  use a maintained replacement or plain text rather than a knowingly broken
  GitHub URL.

## Release Integration

The documentation cleanup is part of the `0.1.41` release PR, not a separate
post-release follow-up. Its commits remain after the frozen product SHA as
reviewed release-owned changes. The release PR description and changelog will
identify strict public-documentation cleanup as release preparation. Required
release checks, the human-authored Change summary gate, CI-capacity focus rule,
merge strategy, annotated tag, publication verification, and main-to-dev sync
remain governed by the existing release design and implementation plan.
