# Release 0.1.42 Reviewed Metadata Design

## Goal

Make pull request #2761 the complete, reviewable `0.1.42` release candidate.
The pull request must contain the release changelog, public release notes, and
all visible version metadata before it is merged to `main`.

## Release contents

The frozen inputs are:

- `origin/dev=0f3983788c413e0d17ffe7eabe8cff4a9f6ae723`
- `origin/main=d9c245ac14c40df855d1ab6cd19b3c137b16b47b`

Both inputs must remain ancestors of the final PR head. The release entry covers
the work merged after the frozen `0.1.41` source through that `dev` commit, plus
the trusted license-gate bootstrap already on `main`. The concise rollup will
cover:

- shared server-side provider credentials for Chat, RAG, embeddings, and audio;
- the inline embeddings workflow facade and related CI/runtime hardening;
- the frontend source-available licensing boundary and trusted license gate;
- preparation for license-first CI sequencing; and
- Jobs admission, quota, idempotency, and transaction hardening.

The pull request will update `CHANGELOG.md`, maintainer and public release
notes, `README.md`, `pyproject.toml`, the FastAPI application version, and the
MkDocs version surfaces to `0.1.42`. Published documentation will be regenerated
from its canonical source rather than edited independently.

## Merge and publication

PR #2761 remains draft until its exact head passes the trusted
`frontend-license-policy/trusted/main` gate and the requester supplies the
required human-written Change summary. The requester previously authorized
admin bypass only for the deliberately cancelled ordinary PR checks; it does
not bypass the trusted license gate or the human-summary gate. After normal or
that narrowly authorized admin merge, the reviewed `main` merge commit becomes
the immutable release target.

The existing `release-patch` helper must not be run for this cut: once the PR
contains `0.1.42`, that helper would calculate `0.1.43`. After merge, read PR
#2761's `mergeCommit.oid`, fetch again, and require `origin/main` to equal that
exact SHA. Create the annotated `v0.1.42` tag explicitly on that SHA, verify the
local tag target, push it, and create the GitHub Release with `--verify-tag`
using notes extracted from the tagged `CHANGELOG.md`.

Because the reviewed PR changes `pyproject.toml`, merging it to `main`
automatically triggers `publish-pypi.yml`. Do not dispatch a second PyPI run;
verify the automatic `0.1.42` publication instead. Publishing the GitHub Release
triggers the Docker release workflow for the versioned `app`, `worker`, and
`audio-worker` images.

After publication, merge released `main` back into `dev` and prove
`origin/main` is an ancestor of `origin/dev` before resuming TASK-12986.

## Verification and rollback

Before push, run focused release-helper, version-surface, documentation,
workflow, and license-gate tests; Actionlint; Bandit on touched executable
Python; and `git diff --check`. Regenerate canonical documentation into
`Docs/Published`, run the refresh a second time to prove idempotence, and strict
build the checked-in result. If the intended release date slips before merge,
update every dated release surface in the PR.

Before tagging, recheck that `v0.1.42` and its GitHub Release do not already
exist and that local `main` exactly matches PR #2761's merge SHA. After
publication, verify the GitHub Release, automatic PyPI run, three Docker release
matrix jobs, versioned GHCR tags, and build-provenance attestations.

If the metadata PR is wrong, update it before merge. If publication fails after
the tag is pushed, keep the immutable tag and retry only the missing GitHub
Release publication; do not cut a second version.
