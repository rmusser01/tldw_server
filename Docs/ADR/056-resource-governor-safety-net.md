# ADR-056: Resource Governor ingress safety net

**Status:** Accepted
**Date:** 2026-09-29
**Backfilled from:** `Docs/Design/2026-09-29-rg-ingress-safety-net-design.md`, implemented in PRs #3066 and #3068 (merged before this record) and #3070
**Decision owner:** repository owner (@rmusser01), via the brainstorming session that produced the spec
**Task:** TASK-13405 (closes TASK-13395)
**Related spec/plan:** `Docs/Design/2026-09-29-rg-ingress-safety-net-design.md`, `Docs/superpowers/plans/2026-09-29-rg-ingress-safety-net.md`
**Amends:** ADR-018 and ADR-044

## Decision

Resource Governor ingress (`RGSimpleMiddleware`) resolves a policy for every request through one resolver — `route_map.by_path` glob, then the innermost matching `route_map.by_tag` from the served-route index, then a catch-all `default` policy for any other `/api/` path, otherwise ungoverned. Every policy is a per-entity safety net: buckets key on the validated principal (`user:<id>` or `api_key:<id>`), or on `ip:<addr>` for anonymous or invalid credentials, or on `tenant:<id>` when tenant scoping is enabled and the validated principal belongs to a tenant (the tenant header only selects among the principal's own orgs). `global` (one bucket shared by the whole server) survives only on the three request policies that send email — `authnz.forgot_password`, `authnz.resend_verification`, `authnz.magic_link.request` — because mail capacity and sender reputation are shared resources. No configuration can produce a permanent 429: an unknown or undefined policy ID falls back to `default`, then to a policy compiled into the code; a policy that doesn't list the caller's entity scope still gets its own per-entity bucket instead of being denied; an over-large token reservation is admitted once the bucket is full rather than denied forever. One switch, `RG_ENABLED` (env) or `[ResourceGovernor] enabled` (`config.txt`), turns off every RG-governed enforcement path at once, including the ingress middleware's lazy governor attach, the diagnostics endpoints' governor construction, and the `auth_deps.py` general ingress fallback (`check_rate_limit`); policies still load so diagnostics can report state. One deliberate exception: `auth_deps.py`'s `check_auth_rate_limit` — a 30/min brute-force floor on auth endpoints, not RG enforcement — keeps enforcing even with the switch off.

## Context

Self-hosters were being rate limited during ordinary single-person use. Three problems compounded: fourteen policies charged one `global` bucket shared by every user and every anonymous client at per-user rates (`core.default` covered ~40 route families at 120 rpm, `global`); `route_map.by_tag` never matched because the resolver ran before FastAPI routing, so ~57 tag-only routes and ~659 unmapped routes were ungoverned and miscounted as covered by the startup/coverage audits; and several code paths produced a request that could never be admitted — an unknown policy ID denied at `rpm 0`, a scope not listed on a policy meant no bucket existed at all (the ADR-044 bug class: an anonymous request to a `[user, api_key]` policy got 429 instead of 401), and a token reservation larger than a bucket's capacity could never fit. Identity also collapsed behind the reverse proxy: ingress ran before authentication and keyed cookie-session traffic by client IP, so every WebUI user behind the same proxy shared one bucket; ADR-044 only fixed this for single-user cookie sessions on policies with no `ip`/`global` fallback. `RG_ENABLED=false` did not disable governance either — the governor was still built, and several call sites (auth reservations, media job concurrency, the embeddings and evaluations rate limiters) called it regardless, with two of them (`auth_deps.py`, `Evaluations/config_validator.py`) reading `RG_ENABLED` from the environment directly, bypassing `config.txt`. UAT hit these limits five times, and each time the fix landed in the frontend while "preserving backend governance." See `Docs/Design/2026-09-29-rg-ingress-safety-net-design.md` for the full survey and the WebUI-replay acceptance test.

## Decisions in detail

- **One resolver, one truth.** `Resource_Governance/policy_resolver.py` (`resolve_policy` / `get_policy_resolver().resolve()`) is the only place that decides a request's policy. The ingress middleware (`middleware_simple.py::_derive_policy_id`), the coverage audit, the startup audit, and the RG diagnostics endpoints all call it, so what they report is what is enforced. Resolution order: `by_path` glob (first match, YAML order) → the served route's merged tags, innermost router first, first tag present in `by_tag` wins → `default` for any other `/api/` path → `None` (ungoverned) for everything else, including docs, static files and the frontend.
- **Identity: charge the validated principal, never the proxy.**
  - A multi-user bearer token that looks like a JWT (two `.` separators, not single-user mode) is keyed by its signature-verified `sub` claim (`jwt_service.decode_access_token`; no database access, no revocation check — the route's own auth still enforces revocation, so a revoked-but-correctly-signed token only ever spends its own user's bucket).
  - Everything else that carries a credential — API keys, non-JWT bearer tokens, and the single-user session cookie — resolves through `auth_principal_resolver.get_auth_principal(request)`. That call caches its `AuthContext` on request state, so endpoint auth reuses the same lookup instead of repeating it. A JWT-shaped bearer that fails verification while an `X-API-KEY` is present also falls through to this path, as route auth does.
  - **API-key and cookie resolutions are budgeted per client IP.** They are the costly path (a DB lookup and a key derivation), so each RG client IP gets `_IDENTITY_RESOLVE_BUDGET_PER_MIN` = 120 uncached resolutions per 60 s window. Past that, the request is charged to the IP without validation and nothing is cached, so rotating fake secrets cost at most about two key derivations per second per IP. JWTs (signature-only) and cache hits never spend the budget. Ceiling: once an IP's budget is spent, its uncached API-key and cookie callers share that IP's bucket, which the flood also drains, until the window rolls over.
  - Absent or invalid credentials are **not** rejected by the middleware. `_principal_entity` returns `None` on any resolution failure, `_derive_entity` already computed the `ip:<addr>` fallback (honoring `RG_TRUSTED_PROXIES` / `RG_CLIENT_IP_HEADER`), and the request proceeds to the route, whose own auth dependency returns the canonical 401/403. The middleware never answers 401 itself.
  - **The resolved identity is cached per middleware instance** (`_identity_cache`, an `OrderedDict` capped at `_IDENTITY_CACHE_MAX` = 4096 entries, LRU-evicted). The key is `sha256` of the client IP (both RG's and AuthNZ's `resolve_client_ip`, since per-key `allowed_ips` checks the latter) plus every credential present on the request (`Authorization`, `X-API-KEY`, the single-user session cookie) — raw values are never stored. A successful resolution is cached for `_IDENTITY_TTL_SEC` = 60 s; a failed resolution is now cached too, for `_IDENTITY_NEGATIVE_TTL_SEC` = 30 s, as "no principal" (charged to the IP), so repeated bad credentials still share the IP bucket without re-running validation on every request. One consequence: a credential revoked mid-window can keep charging its former principal's RG bucket for up to 60 s after revocation — route auth still rejects the request every time; only which bucket absorbs the charge is stale (`middleware_simple.py::_principal_entity`).
  - **A tenant comes only from a validated principal** (TASK-13402). When tenant scoping is enabled, ingress still resolves the principal first (same cache and budget), then charges `tenant:<id>` instead of the principal: the org the tenant header (`X-TLDW-Tenant` by default) names if the principal belongs to it, otherwise the principal's active org, otherwise the principal's own `user:`/`api_key:` entity. A principal's orgs are `AuthPrincipal.org_ids` / `active_org_id` for API keys and the session cookie, and the signature-verified `org_ids` / `active_org_id` claims for a JWT; they are cached with the identity, so a cache hit still checks each request's header. Anonymous and invalid-credential requests ignore the header and pay their IP, so rotating it on one IP shares one bucket. Tenant precedence over the principal is unchanged for members: two users of one org share its `tenant:` bucket. The same rule applies to endpoint-level reservations: `deps.derive_entity_key` honors the header only when it names an org of the principal on request state (`tenant.get_tenant_id(member_of=...)`).
  - This closes a bypass: previously an unvalidated bearer or `X-API-KEY` value was hashed straight into an `api_key:` entity, so rotating fake tokens bought a fresh bucket each time. Identity now comes only from credentials that validate.
- **op_id is always server-generated.** The ingress reservation's idempotency key is `str(uuid.uuid4())`, never the client's `X-Request-ID` — a client-supplied, repeatable op_id would let a replayed header return the cached (already-charged) decision without spending another unit. The same holds for every other governor reservation: auth-endpoint reservations (`auth-rg-<policy_id>-<time_ns>`), audio job/stream reservations (`audio-job:`/`audio-stream:` plus `uuid4().hex`), and daily-cap ledger consumption (`consume_daily_cap`, keyed `<policy_id>:<reserve_op_id>:<category>`) all build their op_id server-side.
- **No permanent 429s** (`Resource_Governance/policy_eval.py`, `governor.py`, `governor_redis.py`):
  - An unknown or undefined policy ID resolves to `default`; if `default` itself is missing from a DB-backed store seeded before this change, a `BUILTIN_DEFAULT_POLICY` compiled into `policy_eval.py` is used, so a self-hoster's YAML/DB edit can never stop request admission.
  - A policy whose scopes don't list the caller's entity kind still gets a dedicated per-entity bucket (`entity` semantics) instead of "no bucket exists, deny." A policy's scopes decide which bucket *kinds* exist, never whether a request can pass at all.
  - An MCP tool category with no dedicated policy falls back to `mcp.default` (`MCP_unified/auth/rate_limiter.py`).
  - A token reservation larger than the bucket's capacity is admitted once the bucket is full (draining it to zero) rather than denied forever.
  - A fractional `requests.rpm` (below one request per minute) would otherwise create a bucket that can never hold a single request; `policy_eval.effective_policy` raises `burst` until `rpm * burst >= 1`, so the bucket always has room for at least one request.
  - A policy with no `scopes` list charges only the caller's own entity bucket. A server-wide `global` bucket is opt-in — it exists only when `scopes` lists `global` — and is never implied by omitting `scopes` (`policy_eval.scope_pairs`).
  - Idle, fully-refilled memory buckets are evicted after 10 minutes so an internet-exposed `default` policy governing all `/api/` traffic doesn't grow unbounded per-IP state. The Redis backend's in-process maps (deny floors, backoffs, acceptance-window trackers, stub lease buckets) are dropped once expired by the same bounded, rotating sweep (`governor_redis.py::_maybe_evict_idle`); an expired entry changes no decision, so eviction is lossless.
- **Auth double-charge is closed, not doubled.** `_reserve_auth_rg_requests` (`endpoints/auth.py`) skips its own reservation only when the ingress-resolved policy matches this call's `policy_id` (`request.state.rg_policy_id`), ingress recorded an entity (`request.state.rg_ingress_entity`, set only on an *allowed* ingress reservation), and the auth-side entity equals the ingress entity exactly. A broader rule (skip an `ip:` auth reservation whenever ingress charged any validated principal) was tried and reverted: a client rotating several valid accounts from one IP would then never be charged the per-IP bucket on entity-scoped sensitive policies (reset-password, MFA). Known costs of the exact rule: a logged-in caller of forgot-password or resend-verification is charged those policies' `global` bucket twice, and when AuthNZ's trusted-proxy resolution (`ip_allowlist.resolve_client_ip`) and RG's (`deps.derive_client_ip`, `RG_TRUSTED_PROXIES`) disagree on the address, an anonymous caller is charged both IP buckets (TASK-13144). Reservations keyed on something else — per-email throttles, per-user MFA limits — still apply regardless.
- **Redis token windows are quantized, and requests are rounded up.** `governor_redis.py::_window_members` packs `quantum = max(1, per_min // 1000)` tokens per ZSET member, bounding a per-minute token window to about 1,000 members regardless of how large `per_min` is (chat's token policy runs at 1,000,000/min). Separately, from 1 rpm up the Redis backend's requests category enforces `max(1, ceil(rpm))` per rolling minute and does not apply the policy's `burst` (burst only widens the memory backend's `rpm * burst` capacity), so the same policy admits fewer requests per window on Redis than on the memory backend; this difference is deliberate. Below 1 rpm, Redis holds `floor(rpm * burst)` requests per rolling `60 * floor(rpm * burst) / rpm` seconds (`policy_eval.requests_window`), the memory bucket's whole-request immediate burst and its long-run average (`authnz.magic_link.email`, `rpm 0.3, burst 10`: 3 per 600 s on both; `rpm 0.5, burst 3`: 1 per 120 s). Both backends' decisions, and the ingress middleware's header fallback, report that `requests_window` limit, so `X-RateLimit-Limit` is never 0 for a fractional policy.
- **The single switch.** `config.rg_enabled()` (env `RG_ENABLED`, then `config.txt` `[ResourceGovernor] enabled`, default `true`) is the only switch every RG-governed enforcement path reads: ingress, auth reservations, chat/embeddings token reservations, MCP admission, evaluations and audio concurrency, the workflows daily cap, and media job concurrency/bytes-per-day all call it directly now (the two direct `os.getenv("RG_ENABLED")` reads in `auth_deps.py` and `Evaluations/config_validator.py` are gone). When it is `false`:
  - the ingress middleware never lazily attaches a governor to `app.state` (`middleware_simple.py.__call__`), so no other call site can find one there either;
  - the RG diagnostics endpoint (`endpoints/resource_governor.py::_get_or_init_governor`) may still construct a `MemoryResourceGovernor` for the one diagnostic call it's answering, but does not persist it to `app.state`, so it stays invisible to every other code path;
  - policy loading still happens, so `GET /api/v1/resource-governor/policy` and friends keep reporting what *would* be enforced.
  - **auth_deps.py's local fallback limiters are not RG, but one of them honors the switch anyway.** `check_rate_limit` and `check_auth_rate_limit` apply an in-process fallback rate limit to requests RG ingress did not govern (`request.state.rg_policy_id` unset) — a route outside `/api/`, or any route while RG is off — via `_enforce_auth_deps_ingress_guard`. That guard skips enforcement only when the request already resolved an already-authenticated single-user principal (`is_single_user_principal(request.state.auth.principal)`) or is running in test mode; an *anonymous* request in single-user mode — `POST /auth/login`, `/auth/register`, `/auth/single-user/session` before the API key is checked — is not skipped and is floored like any multi-user request. `check_rate_limit`'s 120/min general fallback takes an explicit `honor_rg_switch=True` and returns without enforcing when `rg_enabled()` is false, so disabling RG doesn't leave a hidden cap behind. `check_auth_rate_limit`'s 30/min auth-endpoint floor is a deliberate exception — it is a brute-force guard, not RG enforcement — and keeps enforcing regardless of the switch.
- **Safety-net defaults.** `global` was removed from every policy except the three email-sending policies above; a new `default` policy (`requests: rpm 600, burst 2.0`, scopes `[user, api_key, ip]`) now catches every previously-unmapped `/api/` route. Per-entity limits across the board moved well above normal single-person WebUI/extension/chat use (see the before/after table in the design spec, §3); the numbers are starting points validated by a WebUI-replay regression test, not hard architecture.
- **Config hygiene.** The policy loader accepts only `version`, `policies`, `tenant`, `route_map`, `templates`, `schema_version` at the top level and `by_path`/`by_tag` inside `route_map`; every other key logs a warning instead of being silently ignored (`policy_loader.py`). `Helper_Scripts/ci/rg_route_map_lint.py`, with its allowlist `Helper_Scripts/ci/rg_route_map_lint_allowlist.txt`, fails CI when a `by_path` pattern is dead or fully shadowed by an earlier one, or a `by_tag` key matches no served route.
- **DB policy store upgrade step.** Installs running `RG_POLICY_STORE=db` keep whatever limits and `global` scopes are already in their `rg_policies` table until an operator re-seeds (`python -m tldw_Server_API.app.core.Resource_Governance.seed_db_from_yaml --all`; without `--all` it seeds only the policies `route_map` references, so endpoint-only policies such as `authnz.*` keep their old limits) or edits the DB policies directly; the built-in `default` fallback keeps resolution safe in the meantime.

## Alternatives considered

| Option | Why rejected |
| --- | --- |
| Keep `global` scope on every policy and just raise the shared limit | A single high shared bucket still lets one busy user or one flood starve every other tenant; it does not fix per-user isolation, only delays it. |
| Fix tag-policy matching by hardcoding more path prefixes (as `chat`/`audio` already were) | Doesn't scale to ~57 tag-only routes and drifts from the actual route table; the route index resolves tags generically from what FastAPI actually serves. |
| Deny requests when a policy's scopes don't cover the caller's entity (status quo) | This is the ADR-044 bug class generalized: any scope/entity mismatch becomes a permanent, unfixable-without-restart 429. |
| Compare ingress and auth-side client IPs directly to detect double-charging | AuthNZ and RG resolve trusted-proxy chains independently and can legitimately disagree; a direct string comparison would just never match and silently double-charge every auth-sensitive request. |
| Authenticate every ingress request fully (routed scope checks included) before deriving identity | Needs the matched route, which isn't available before routing; for virtual keys the scoped-token check always fails pre-routing and logs a security warning on every request. |
| Turn `RG_ENABLED=false` into "governor object still exists, just skip `.reserve()` calls" everywhere | Leaves an easy-to-miss call site (as `auth_deps.py`/`Evaluations/config_validator.py` were) that keeps enforcing after the operator turned governance off; the fix instead makes "no governor reachable" the enforced invariant at the two build sites. |

## Consequences

About 716 previously-ungoverned or server-wide-bucketed routes (about 57 through tags, about 659 through `default`) are now governed by generous per-entity limits; this is a safety net, not a new constraint, and is guarded by the WebUI-replay regression test. The aggregate server-wide request cap is gone except for the three email-sending policies — a distributed flood across many entities is no longer bounded in aggregate by RG itself; that remains the reverse proxy's job. Turning `RG_ENABLED=false` off now also disables media, workflows, auth-reservation, and the `auth_deps.py` general fallback (`check_rate_limit`) enforcement that previously stayed on regardless of the switch — this is intentional (the switch is now honest) but means "off" is more consequential than before. The one deliberate exception is `check_auth_rate_limit`'s 30/min auth-endpoint brute-force floor, which is not RG enforcement and stays on either way. Memory-backend buckets remain per uvicorn worker process (compose files default to 2–4 workers), so effective limits are that many times higher and less even under the memory backend; operators who need exact limits should use `RG_BACKEND=redis`. Invalid credentials on a governed route now reach the route's own 401/403 instead of an early middleware response; this is deliberate and tested (`test_middleware_cookie_owner.py`). The ingress identity cache (60 s on success, 30 s on failure) means a revoked credential can keep charging its former principal's bucket for up to 60 s after revocation; route auth still rejects the request throughout. DB-backed policy-store installs must re-run the seeding step (or edit their DB policies) to pick up the new limits and the `global` removal — they are not upgraded automatically.
