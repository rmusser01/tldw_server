# Native frontend runtime candidates — TASK-13013.7.15

## Purpose and authority

Continue the user's approved remediation and continuous subagent-driven execution.
This is candidate-only qualification, not production adoption. The evidence in
`Docs/Evidence/TASK-13013.7.14-frontend-base-evaluation.md` motivates an Ubuntu
runtime: vendor-fixed glibc preserves Node's supported GNU/Linux platform, and
the exact zlib backport addresses CVE-2026-27171. CVE-2026-85091 remains unresolved;
lower vendor severity must never be described as a fix.

## Design

Generate temporary Dockerfiles from the two canonical frontend Dockerfiles.
Preserve their builder stages byte-for-byte and their existing runtime remainder.
Replace only the known Node Bookworm runtime FROM with pinned Ubuntu, copy the
same Node executable, CA certificates, license and Docker entrypoint from the
unchanged builder, and install the exact vendor zlib backport using signed apt
metadata. Retain acquisition evidence inside a non-public candidate evidence
directory. Do not edit production Dockerfiles or dependency locks.

Reject an unexpected canonical runtime FROM, missing builder or duplicate runtime
marker rather than silently generating a different design. This small generator
avoids maintaining duplicate frontend builder recipes. Its output is explicitly
marked not admitted; only the candidate workflow consumes it.

Use a native amd64 GitHub Actions job for each frontend. Build baseline and
candidate from the same commit/build arguments, preserving frozen dependencies.
Load their exact OCI subjects into the native containerd image store. Compare
runtime configuration and Node, UID/GID/home, CA bundle and sharp behavior. Run
both actual standalone applications with a controlled backend-health stub,
testing positive/negative readiness and public liveness where those routes exist.
The stub is not a real-backend end-to-end qualification claim.

Exercise real GNU sharp image transformation, the configured Docker healthcheck,
startup and SIGTERM shutdown. Do not enable Admin real-backend-E2E mode, which
disables standalone output. Use private Docker networks without published ports,
non-root users, read-only rootfs, dropped capabilities, resource limits and only
the writable tmp/cache locations necessary for the existing applications.

Scan baseline and candidate with the same fresh pinned Trivy database and the
same pinned Syft/Grype database. Preserve complete reports, tool/DB metadata,
source/OCI/config/container identities and invocation logs even on failure.
Check known package fixes independently from counts; report all severity changes.
No production gate is changed and no candidate is published or admitted.

## Non-goals and limits

No change to production recipes, release workflows, scanner severity settings,
custom ignores, exceptions, locks, user-facing source or another task's work.
No FFmpeg source/history review. No registry publication or merge. No claim that
baseline findings that disappear from a different distribution's feed were fixed.
Native qualification may expose compatibility issues; fix confirmed candidate
issues within this design and retain failures rather than weakening checks.

Package acquisition uses the signed distribution indexes and an exact version,
not a snapshot-reproducibility claim. Retain the package hash and signed index
identities; missing versions or failed signatures fail the build. Release adoption
and a durable reproducible supplier strategy remain later decisions.
