# TASK-13013.7.18: schema-field compatibility decision

Status: draft; no application or dependency change applied. Checked at code
commit `0c1b7deb58` on 2026-09-09 UTC. The requester is reviewing the choices.

## Recommendation

Retain the current Python model contracts and the two non-blocking warnings
until a deliberate API migration is accepted. The smallest warning-free draft
preserves default JSON serialization but changes Python model behavior. It does
not satisfy the existing full-compatibility criterion and is not presented as
a drop-in fix.

The alternative draft renames both Python fields from `schema` to
`schema_definition`, uses `alias="schema"` and `serialize_by_alias=True`, and
raises the root Pydantic declaration from `>=2.0.0` to the tested `>=2.11.7`.
It changes only the root requirement metadata in `uv.lock`; resolved versions,
artifacts, and hashes remain identical by parsed lock comparison. This is a
separate compatibility decision from the previously approved ConfigDict change.

## Existing behavior and draft differences

Source-only probes load just the selected class definitions, without importing
the application. Existing behavior matches on Pydantic 2.11.7 and 2.13.5.
Both existing schema classes fail definition on 2.0 with a field-shadowing
NameError; this differs from the warning on newer versions. The approved
workflow **base models** still pass their separate 2.0 checks. Also, installed
FastAPI 0.136.3 already requires Pydantic >=2.9.0, so the root's >=2.0.0 line is
not by itself the effective minimum for the full server dependency set.

| Operation | Current model | Alias draft |
| --- | --- | --- |
| Input JSON key | `schema` | `schema` |
| Default nested dumps, JSON output, schema metadata | `schema` | Preserved in tested cases |
| Instance `.schema` | Schema dictionary | Inherited Pydantic method; data moves to `.schema_definition` |
| `model_fields` | Contains `schema` | Contains `schema_definition` |
| `include={"schema"}` and nested selections | Select schema data | No longer select the renamed field |
| `exclude={"schema"}` | Excludes schema data | No longer excludes the renamed field |
| `model_dump(by_alias=False)` and legacy `.dict()` | Emit `schema` | Emit `schema_definition` |
| Response spec `model_copy(update={"schema": ...})` | Updates serialized schema | Does not update the renamed field |

The extra-allowing workflow model happens to retain the observed copied output
in that last case via its extras behavior; that is not equivalent field-update
semantics and is not a compatibility guarantee.

Prior alias/wrap-serializer and dataclass approaches failed other Python
contracts. This draft explicitly exposes the trade-off rather than adding
another compatibility wrapper. Pydantic introduced `serialize_by_alias` in
2.11; aliases do not rename the Python fields used for selection and updates.
[Pydantic configuration](https://docs.pydantic.dev/latest/api/config/#pydantic.config.ConfigDict.serialize_by_alias),
[serialization options](https://docs.pydantic.dev/latest/concepts/serialization/).
