# TASK-13013.7.18: schema-field compatibility decision

Status: approved and applied on 2026-09-09 UTC, following the requester's
`aproved` response to this concrete proposal. Implementation starts from
`388644a98f`; the original investigation used `0c1b7deb58`.

## Approved decision

The requester accepted the smallest warning-free migration and its disclosed
Python API and dependency-floor changes. Normal application JSON contracts are
preserved in the verified cases; this is not complete Python compatibility.
The original recommendation to retain the warnings was superseded by approval.

The applied migration renames both Python fields from `schema` to
`schema_definition`, uses `alias="schema"` and `serialize_by_alias=True`, and
raises the root Pydantic declaration from `>=2.0.0` to the tested `>=2.11.7`.
It changes only the root requirement metadata in `uv.lock`; resolved versions,
artifacts, and hashes remain identical by parsed lock comparison. This is a
separate compatibility decision from the previously approved ConfigDict change.

Approved proposal patch:
`/private/tmp/task-13013-7-18-schema-contract.UKTsN3/schema-wire-migration-proposal.patch`.
Affected files are `chat_request_schemas.py`, workflow text `_config.py`,
`pyproject.toml`, and root requirement metadata in `uv.lock`.

## Observed application boundaries

| Consumer | Required behavior |
| --- | --- |
| `Chat/chat_service.py:2744` | Dumps the request with top-level exclusions and `exclude_none=True`; the nested schema must remain in the outbound payload. |
| `Chat/chat_orchestrator.py:1126` and `:1605` | Dumps ResponseFormat with default options before provider calls. |

| Workflow text `transform.py:123` | Reads raw `config.get("schema")` before JSON validation. |

Scoped caller searches found no application access to either target model's
`.schema` attribute. That does not establish that external Python consumers do
not use it. Existing tests cover request acceptance/rejection and raw workflow
validation, but do not define every public Pydantic operation as an application
contract.

## Previous behavior and accepted differences

Source-only probes load just the selected class definitions, without importing
the application. Existing behavior matches on Pydantic 2.11.7 and 2.13.5.
Both existing schema classes fail definition on 2.0 with a field-shadowing
NameError; this differs from the warning on newer versions. The approved
workflow **base models** still pass their separate 2.0 checks. Also, installed
FastAPI 0.136.3 already requires Pydantic >=2.9.0, so the root's >=2.0.0 line is
not by itself the effective minimum for the full server dependency set.

| Operation | Before migration | Applied alias migration |
| --- | --- | --- |
| Input JSON key | `schema` | `schema` |
| Default nested dumps, JSON output, schema metadata | `schema` | Preserved in tested cases |
| Instance `.schema` | Schema dictionary | Inherited Pydantic method; data moves to `.schema_definition` |
| `model_fields` | Contains `schema` | Contains `schema_definition` |
| `include={"schema"}` and nested selections | Select schema data | No longer select the renamed field |
| `exclude={"schema"}` | Excludes schema data | No longer excludes the renamed field |
| `model_dump(by_alias=False)` and legacy `.dict()` | Emit `schema` | Emit `schema_definition` |
| Response spec `model_copy(update={"schema": ...})` | Updates serialized schema | Does not update the renamed field |

The extra-allowing workflow model happens to retain the observed copied output
in that last case via its extras behavior; that is not equivalent field-update
semantics and is not a compatibility guarantee.

Prior alias/wrap-serializer and dataclass approaches failed other Python
contracts. This migration explicitly exposes the trade-off rather than adding
another compatibility wrapper. Pydantic introduced `serialize_by_alias` in
2.11; aliases do not rename the Python fields used for selection and updates.
[Pydantic configuration](https://docs.pydantic.dev/latest/api/config/#pydantic.config.ConfigDict.serialize_by_alias),
[serialization options](https://docs.pydantic.dev/latest/concepts/serialization/).

## Verification and scope boundary

The proposal passed **30 source-only wire/schema comparisons on each of 2.11.7
and 2.13.5**, with neither target warning. Applied-source comparisons against
captured HEAD definitions repeat those checks at both versions. They cover
normal, exclude-none/defaults/unset, explicit alias output, nested ResponseFormat
output, and generated JSON schema, while separately recording the accepted
Python differences above. These do not prove parity for every possible input.

One additional review limitation: direct
`JSONValidateConfig.model_validate_json()` with both `schema` and an extra
`schema_definition` key drops that extra key on locked Pydantic 2.13.5 after
the migration. Pydantic 2.11.7 and dictionary validation retain it; the actual
schema remains intact at both versions. No affected
application caller was found. Treat `schema_definition` as the Python field
name, not a second JSON input key. Ordinary unrelated extras remain supported.

The original scratch offline lock check passed for 650 universal packages.
Applied `uv lock` initially lacked cached html5lib metadata offline, then
succeeded with network access. Parsed comparisons confirm only the root
Pydantic requirement changes in both pyproject and lock; package versions,
artifacts and hashes remain identical. Resolution selected Python 3.13.6 and
is not an application runtime check on that Python version.

Approval covers these two models, focused regressions, dependency-floor/lock
metadata and supporting records. Password implementation, production images,
release admission and remote actions remain outside this change. Detailed
results are recorded in the [implementation evidence](../Evidence/TASK-13013.7.18-schema-migration.md).
