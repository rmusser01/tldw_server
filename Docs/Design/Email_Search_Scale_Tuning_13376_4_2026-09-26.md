# Scale query tuning (TASK-13376.4)

The actual million-message SQLite query plan shows a participant filter scanning all tenant messages and executing a participant lookup once per message. Native `from`/`to`/`cc`/`bcc` and label filters can instead materialize matching message IDs from normalized relations once and use a semi-join. Keep case-insensitive contains matching on address/display name and label key/name; bind the resolved tenant in the subquery, retain the outer tenant and Media deletion checks, and preserve NOT/OR composition. Add a reverse covering participant index (participant_id, role, email_message_id) so matching participant rows drive link lookup. Existing label reverse index already supports this pattern. This does not introduce exact-match-only semantics or cache query totals.

Verify operator results and cross-tenant mismatched graph rows, negation, OR, date/cursor and deleted-media behavior, and assert the SQLite plan avoids the per-message correlated participant subquery. Capture actual one-million-message latency before/after and run real PostgreSQL isolation regressions before considering the change complete.

Broad labels need different count and page plans. The count materializes IDs through the reverse label index and uses compact identity/Media visibility covering indexes on SQLite; page selection checks membership lazily in date order to avoid sorting a million IDs. Both plans share the same predicate values and logical grouping. The SQLite count index includes subject text; PostgreSQL uses a variant without unbounded subject text, avoiding PostgreSQL's B-tree tuple-size limit. No predicate or result semantics change.

The documented protocol uses aggregate warm-pass p50/p95 as its NFR gate. All ten operator classes must have populated results; per-case latency remains a separately reported diagnostic. Older six-case/per-case gate documentation is reconciled with this explicit protocol. The negation workload uses the sender of the observed subject example so it actually removes matching messages.

## Broad-label reassessment

Three measured approaches missed the target: materializing labels for page selection required sorting one million IDs (~6.8s); lazy label membership with the tenant/date count scan reduced that to ~0.94s but missed aggregate p95; separate reverse-label count materialization measured ~1.33s. Stop changing query shape and inspect the count/page boundary: the actual plan and timings show 1.29–1.37s entirely in COUNT, while the page takes ~0.5ms. The reverse label index covers only label_id, forcing a table lookup for every returned message ID. Compare with the covering participant reverse index and existing composite label primary key. Add the missing (label_id, email_message_id) covering index, preserving the predicates and measured page plan, then remeasure. This fixes a demonstrated data-access cost without caching totals, changing substring matching, or assuming Inbox is universal.

The covering index alone reached ~942ms; compact identity-order membership ~984ms. Direct COUNT(DISTINCT em.id) joins still reached ~1089ms because the inspected planner chose to scan every email and inspect all of its labels to avoid the DISTINCT temp index. The selected correction fixes join order only for a single positive label predicate: start with matched labels, traverse covering reverse links, then email and Media visibility indexes; COUNT DISTINCT retains correctness for multiple matched labels. Negative, mixed and OR predicates keep their existing count composition. The page still checks memberships lazily in date order. [SQLite's optimizer documentation](https://www.sqlite.org/optoverview.html#manual_control_of_query_plans_using_cross_join) confirms CROSS JOIN fixes nested-loop order; this workaround follows actual plans after ANALYZE rather than assumed selectivity.

With label-first order, DISTINCT still materialized one million IDs (~1052ms). A cheap count of matching label rows inside the same transaction proves that zero or one label cannot duplicate a message because the link primary key is (email_message_id,label_id). Use COUNT(*) in that case, DISTINCT when multiple label rows match. No hardcoded Inbox assumption and no cached counts. The next two-run diagnostic reached aggregate warm p50 213.57ms / p95 747.74ms; this is tuning evidence, not the final 20-run certificate.

## Legacy media search parity at sustained archive size

The authenticated SQLite upload probe produced 7,900 real messages before the full-ID legacy/native parity pass exposed two separate quadratic reads. Read-only `SQLiteBackend.execute` inspection of the generated database showed the legacy count using `idx_media_deleted`, then restarting `media_fts MATCH` with a rowid constraint for each Media row. The exact count took 1,184.27 ms. Holding all visibility, deletion, type and keyword conditions constant, FTS-first `CROSS JOIN` completed the same count of 7,900 in 5.03 ms. The SQLite repository now fixes that nested-loop order and resets its base relation to Media in both existing FTS error fallbacks.

The page query already selected FTS first, but materialized every latest document version and scanned that metadata relation for each matching media row. Its 100-result page took 3,917.42 ms. An equivalent per-media lookup of the newest nondeleted document-version ID, followed by a primary-key LEFT JOIN, completed in 38.46 ms using the existing media/version unique index. No new index, cached total, result restriction or pagination shortcut is introduced. The PostgreSQL metadata join retains its existing window-function shape.

Focused regressions inspect actual SQLite count/page plans and verify newest live metadata, deleted versions, missing versions, relevance, pagination and caller scope. INFO and higher legacy-search logs now emit static messages with bounded error types and counts instead of query text, FTS/LIKE parameters, titles, exception strings or traceback locals. Six sentinel cases cover FTS, LIKE, both fallback boundaries and database/unexpected failures. These diagnostic timings identify the remedy; they are not substitutes for the final rerun of authenticated HTTP release checks.

## PostgreSQL forced-RLS plan tuning

The first retained synthetic one-million-message PostgreSQL run missed the aggregate warm target (p50 510.89ms, p95 1841.72ms). Exact scoped, non-admin EXPLAIN ANALYZE plans estimated only 522 visible Media rows per parallel worker against 333,333 actual rows. Broad counts therefore performed one million primary-key joins. Existing count/link indexes had zero heap fetches, so visibility-map maintenance was not the missing remedy.

The selected database changes preserve the original seven independent COALESCE/ILIKE predicates, exact substring behavior, negative terms, OR groups, tenant filters, and complete forced-RLS predicates. Fixed expression statistics expose visibility/owner and native text selectivity. A single multicolumn pg_trgm GIN indexes those exact seven text expressions, including unbounded native subjects without a B-tree tuple-size restriction. The optional statistics/extension/index groups each use a savepoint: denied optional DDL rolls back only its group and leaves ordinary ILIKE search and bootstrap usable. ANALYZE remains explicit post-load maintenance. [PostgreSQL pg_trgm documentation](https://www.postgresql.org/docs/18/pgtrgm.html) documents GIN support for LIKE/ILIKE.

Session-setting reads in RLS are uncorrelated scalar subqueries, evaluated as statement InitPlans; every statement still reads the scope installed on that pooled connection. Owner, team, organization, administrator, deletion and clone predicates are otherwise unchanged. [PostgreSQL EXPLAIN documentation](https://www.postgresql.org/docs/18/using-explain.html) describes once-per-statement InitPlan evaluation. Label substring matching resolves the small matching label-ID set inside the existing search transaction, then binds those IDs to count and page membership predicates. The planner can use actual label-ID frequencies rather than assuming a tiny Inbox result from a label-name join. Duplicate matched labels still return/count each email once. This fixes a label set for the two search statements; it does not add a new repeatable-read API guarantee.

Rejected measured alternatives include materializing all visible Media IDs (slower counts), a concatenated text candidate index (extra string/recheck cost, unnecessary predicates), and a covering Media B-tree containing unbounded policy identities (unsafe tuple size). RLS InitPlans alone did not repair missing cardinality estimates. Statistics and InitPlans together plus lazy date-ordered pages and exact-expression GIN were retained.

The local PostgreSQL 18.6 reference service has shared_buffers=128MB and hash_mem_multiplier=2. Its default work_mem=4MB caused broad hash joins to use eight batches and write 3,028 temporary blocks at the hash node; the mixed-text count selected a full native scan and took 916.14ms. A scoped work_mem=64MB budget produced single-batch hash joins with zero temporary blocks and exact bitmap scans (31,003 exact heap blocks, zero lossy blocks or index rechecks for the mixed-text count), reducing that count to 360.54ms. No planner path was disabled and no global/role setting was changed.

A short serialized production-code diagnostic (three repetitions of all ten operator classes) measured aggregate warm p50/p95 248.01/962.52ms at 4MB and 191.71/516.82ms at 64MB. These are tuning diagnostics, not the final certificate. The final reference run must explicitly use PGOPTIONS='-c work_mem=64MB'; a fresh guarded generated-role connection confirmed 64MB, shared_buffers=128MB, hash_mem_multiplier=2 and row_security=on. This is a single-worker reference resource budget, not a universal production concurrency recommendation.

Retained-fixture maintenance took 19.002s to ensure the statistics/index/RLS recipe and 34.988s to ANALYZE Media, native messages, label links and labels. Credential-free resource-bound maintenance is recorded in /tmp/email_pg_tuning_maintenance_13376.json; full diagnostic plans/settings are in /tmp/email_pg_production_memory_13376.json. Both guarded diagnostics recorded zero outbound and model attempts. New live PostgreSQL regressions cover exact substring and cross-field boundaries, participant display names, duplicate/multiple/missing labels, negative/OR combinations, pooled owner/team/org/admin/missing scope, a 16,384-byte native subject, and actual PostgreSQL transaction-abort recovery for denied optional DDL.

## Full parity verification memory bound

The first full run of the tuned code stopped before timing. The complete body/version parity join used two parallel hash joins and exceeded the existing Docker container's 64 MiB POSIX shared-memory segment limit (SQLSTATE 53100). This was a verification-resource failure; no fixture or security check was removed and no new latency result was claimed.

Fixture inspection now runs its initial verification transaction with `SET LOCAL max_parallel_workers_per_gather=0`. The complete joins run serially using process memory. That setting ends with the verification transaction, and the subsequent owner-scope readback records the actual timed profile: two parallel workers and 64 MB work memory. One expected red regression reproduced the missing protection; eleven settings/fixture tests then passed, including actual transaction restoration. Timed native search queries retain their normal planner and resource settings.

## Repeated parameterized search planning

The next full run passed complete inspection but failed during repeated label timing. A bounded reproduction on one pooled connection failed the `label:Inbox` count on iteration 11 with SQLSTATE 53100 while all first ten calls succeeded. The same connection then passed all 23 repetitions with transaction-local `plan_cache_mode=force_custom_plan`, preserving the exact one-million count and 50-row page. Native PostgreSQL search now requests custom planning only inside its existing transaction. This adds planning cost to each search, which the complete latency certificate must include. It changes neither global database settings nor available planner paths. Live regression coverage observes the actual count's planning mode over 23 repeated searches and verifies restoration on pooled reuse.
