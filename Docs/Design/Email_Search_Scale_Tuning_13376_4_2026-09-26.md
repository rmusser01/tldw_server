# Scale query tuning (TASK-13376.4)

The actual million-message SQLite query plan shows a participant filter scanning all tenant messages and executing a participant lookup once per message. Native `from`/`to`/`cc`/`bcc` and label filters can instead materialize matching message IDs from normalized relations once and use a semi-join. Keep case-insensitive contains matching on address/display name and label key/name; bind the resolved tenant in the subquery, retain the outer tenant and Media deletion checks, and preserve NOT/OR composition. Add a reverse covering participant index (participant_id, role, email_message_id) so matching participant rows drive link lookup. Existing label reverse index already supports this pattern. This does not introduce exact-match-only semantics or cache query totals.

Verify operator results and cross-tenant mismatched graph rows, negation, OR, date/cursor and deleted-media behavior, and assert the SQLite plan avoids the per-message correlated participant subquery. Capture actual one-million-message latency before/after and run real PostgreSQL isolation regressions before considering the change complete.

Broad labels need different count and page plans. The count materializes IDs through the reverse label index and uses compact identity/Media visibility covering indexes on SQLite; page selection checks membership lazily in date order to avoid sorting a million IDs. Both plans share the same predicate values and logical grouping. The SQLite count index includes subject text; PostgreSQL uses a variant without unbounded subject text, avoiding PostgreSQL's B-tree tuple-size limit. No predicate or result semantics change.

The documented protocol uses aggregate warm-pass p50/p95 as its NFR gate. All ten operator classes must have populated results; per-case latency remains a separately reported diagnostic. Older six-case/per-case gate documentation is reconciled with this explicit protocol. The negation workload uses the sender of the observed subject example so it actually removes matching messages.

## Broad-label reassessment

Three measured approaches missed the target: materializing labels for page selection required sorting one million IDs (~6.8s); lazy label membership with the tenant/date count scan reduced that to ~0.94s but missed aggregate p95; separate reverse-label count materialization measured ~1.33s. Stop changing query shape and inspect the count/page boundary: the actual plan and timings show 1.29–1.37s entirely in COUNT, while the page takes ~0.5ms. The reverse label index covers only label_id, forcing a table lookup for every returned message ID. Compare with the covering participant reverse index and existing composite label primary key. Add the missing (label_id, email_message_id) covering index, preserving the predicates and measured page plan, then remeasure. This fixes a demonstrated data-access cost without caching totals, changing substring matching, or assuming Inbox is universal.

The covering index alone reached ~942ms; compact identity-order membership ~984ms. Direct COUNT(DISTINCT em.id) joins still reached ~1089ms because the inspected planner chose to scan every email and inspect all of its labels to avoid the DISTINCT temp index. The selected correction fixes join order only for a single positive label predicate: start with matched labels, traverse covering reverse links, then email and Media visibility indexes; COUNT DISTINCT retains correctness for multiple matched labels. Negative, mixed and OR predicates keep their existing count composition. The page still checks memberships lazily in date order. [SQLite's optimizer documentation](https://www.sqlite.org/optoverview.html#manual_control_of_query_plans_using_cross_join) confirms CROSS JOIN fixes nested-loop order; this workaround follows actual plans after ANALYZE rather than assumed selectivity.

With label-first order, DISTINCT still materialized one million IDs (~1052ms). A cheap count of matching label rows inside the same transaction proves that zero or one label cannot duplicate a message because the link primary key is (email_message_id,label_id). Use COUNT(*) in that case, DISTINCT when multiple label rows match. No hardcoded Inbox assumption and no cached counts. The next two-run diagnostic reached aggregate warm p50 213.57ms / p95 747.74ms; this is tuning evidence, not the final 20-run certificate.

## Legacy media search parity at sustained archive size

The authenticated SQLite upload probe produced 7,900 real messages before the full-ID legacy/native parity pass exposed two separate quadratic reads. Read-only `SQLiteBackend.execute` inspection of the generated database showed the legacy count using `idx_media_deleted`, then restarting `media_fts MATCH` with a rowid constraint for each Media row. The exact count took 1,184.27 ms. Holding all visibility, deletion, type and keyword conditions constant, FTS-first `CROSS JOIN` completed the same count of 7,900 in 5.03 ms. The SQLite repository now fixes that nested-loop order and resets its base relation to Media in both existing FTS error fallbacks.

The page query already selected FTS first, but materialized every latest document version and scanned that metadata relation for each matching media row. Its 100-result page took 3,917.42 ms. An equivalent per-media lookup of the newest nondeleted document-version ID, followed by a primary-key LEFT JOIN, completed in 38.46 ms using the existing media/version unique index. No new index, cached total, result restriction or pagination shortcut is introduced. The PostgreSQL metadata join retains its existing window-function shape.

Focused regressions inspect actual SQLite count/page plans and verify newest live metadata, deleted versions, missing versions, relevance, pagination and caller scope. INFO and higher legacy-search logs now emit static messages with bounded error types and counts instead of query text, FTS/LIKE parameters, titles, exception strings or traceback locals. Six sentinel cases cover FTS, LIKE, both fallback boundaries and database/unexpected failures. These diagnostic timings identify the remedy; they are not substitutes for the final rerun of authenticated HTTP release checks.

## Fresh-fixture statistics regression

The complete fresh SQLite fixture passed all one-million-row body/index/identity checks but initially measured warm p50 698.82ms / p95 2615.85ms. Exact plans scanned one million role-index links for each participant subquery and selected an unsuitable attachment/date index for free-text counts. The earlier tuned fixture had ANALYZE statistics. On identical data, ANALYZE took 3.77s and selected matching participant rows followed by the covering reverse index; sender/recipient queries fell to 64.03/27.18ms and negation to 717.61ms with unchanged 5000/2000/165000 counts. Post-load ANALYZE is now an explicit bounded fixture setup step on both backends, included separately in setup duration. This is database maintenance, not cached totals or an ingestion-speed claim. The final guarded certificate reuses the fully validated generated fixture after statistics collection; a fresh run automatically performs the same maintenance.
