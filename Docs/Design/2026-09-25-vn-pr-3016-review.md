# VN Generation Durability Review Follow-up

Backlog: TASK-13369. PR: #3016. Supersedes the affected recovery details in
`2026-09-25-vn-generation-durability.md`.

## Guarantees and limits

Jobs remains the authority for queue delivery, lease ownership, and retries.
The per-user VN database stores an execution fence and a stable hidden item
reservation for each V1 variant. Only the holder of the current fence may
attach storage metadata or complete an outcome. A replacement worker may take
over only when its Jobs lease is current and different from the stored lease.
If a prior process continues after losing its lease, it may finish an external
model call, but cannot publish its result. Exactly-once external model calls
cannot be promised without provider support.

Claim replacement compares the previously observed attempt token while holding
the VN write lock, then validates the authoritative Jobs lease. Storage
attachment, publication, and failure admission also validate that lease inside
the protected VN transition. This is an admission boundary, not a distributed
transaction across the VN and Jobs databases: cancellation or lease replacement
that precedes admission blocks the transition; a Jobs change after admission
does not retroactively undo a committed VN transition. VN batch cancellation
itself is serialized with publication in the same metadata database.

The generated-file handoff must be idempotent by owner and item source
reference. A concurrent loser must not leave a second live registered file or
visible asset; its temporary file must be cleaned up. Historical duplicate
source references must not make the migration fail or silently delete files
referenced by existing items.

For VN registration, resolve a valid live source-reference replay before applying
new-file quota checks. Registration and applicable user, organization, and team
usage deltas commit together; a failed transaction must leave neither a live row
nor a charge. Preserve user profile-version accounting through the existing
write gateway. Never delete bytes referenced by a committed live file record.
An existing record with missing bytes is not a successful replay and must be
repaired transactionally or rejected without discarding replacement bytes.

## Submission and replay

Batch and receipt links continue to commit together. Failure to create the
parent Job records `enqueue_error` but leaves the linked batch queued, so a
same-key request retries the deterministic Jobs key. Successful recovery
clears the error and records the parent Job ID. A batch that failed during
variant execution is never reopened by submission recovery.

For V1 variants, reserve the hidden item and claim the recipe before calling
the image adapter. A duplicate delivery with the same live lease does not
generate again. A delivery holding a newer Jobs lease may atomically replace
the stale claim and reconcile an existing generated file before generating.
Publication checks the claim in the same VN database transaction as the
outcome transition. Storage and database handoff failures leave the outcome
retryable; definitive adapter failures may be recorded as failed only by the
currently authorized attempt. Replay first looks up the stable source reference and
attaches already registered bytes before considering a new model call.

## Cancellation

Cancelling a V1 batch atomically marks all uncompleted recipe outcomes
cancelled, updates `cancelled_count`, and preserves completed/failed counters.
Cancelled reservations remain hidden and do not consume future generation
capacity. Stale workers cannot change cancelled outcomes to failed or
completed. Legacy V0 cancellation keeps its existing behavior.

## Cleanup and browser recovery

Removing a terminal V1 item must preserve its recipe outcome and historical
batch counters without retaining a foreign key that prevents deletion. Active
reservations remain protected. This behavior must work on existing recipe
tables as well as fresh databases; changing only the CREATE TABLE definition
is insufficient. Completed-V1 cleanup must be exercised through the service,
including file metadata and usage cleanup.

Before publishing a planned replay, validate the owned live file, item source
reference, contained path, and byte-size consistency. Validate both a recovered
source-reference record and an item whose file metadata was already attached.
Missing or truncated bytes must not become a completed draft or trigger
duplicate generation. Filesystem checks stay off the event loop; already
completed replay must preserve review decisions.

Replay also verifies SHA-256 when a checksum is persisted, including same-size
corruption. Historical rows without checksums retain size validation; hashing
uses bounded reads off the event loop. Definitive absence, invalid metadata,
or corruption is nonretryable. An unfinished fenced recipe fails once and
releases its reservation capacity; a completed outcome and its approval remain
unchanged. Transient filesystem errors remain retryable. Explicit regeneration
creates a new draft through the existing API, never silently replacing bytes
under a historical approval or resetting a completed outcome.

The browser keeps its request key after ambiguous submission failures. A
definitive rejection such as a missing slot must clear that pending operation
so refresh/reload cannot retry a permanently invalid target indefinitely or
block future generation. Network failure, timeout, throttling, and ambiguous
server errors retain the same key rather than starting a duplicate request.

## API and quality

Keep existing machine-readable VN error codes. A VN-specific `ValueError`
subclass may carry batch, slot, variant, item, and operation context for logs
without changing public error details. Add concise docstrings to new helpers,
type the test fixture, and offload filesystem metadata checks from the async
worker event loop.

Claim/recovery/response persistence decisions belong to the core service; HTTP
helpers only validate response models and translate errors. New VN generated
file lock and lookup queries live in DB_Management on the caller-owned AuthNZ
connection, preserving transaction admission and user/org/team accounting.
PostgreSQL durability tests delegate lifecycle to isolated_test_environment.
Cleanup logs bind operation and file correlation fields with stack frames,
without raw exception messages or diagnostic locals that could reveal secrets.
