# VN Generation Durability Review Follow-up

## Fresh Exact-Head Review Contracts

Async worker outcome observation must not block the event loop. Offload a
complete synchronous read operation without moving a live cursor or transaction
between threads; preserve the repository's connection/resource ownership.
Private-memory and already-active caller transaction compatibility may retain
an explicitly documented owner-thread fallback. Normal file-backed worker
reads are offloaded; this does not promise universally asynchronous DB access.

Async missing-recipe worker paths await a complete thread-owned integrity
write/reconciliation operation; no live connection or caller transaction moves
between threads. Synchronous fanout retains its synchronous boundary. Private
memory and active caller transactions retain documented owner-thread fallback.
The boundary preserves legacy Jobs activity and inline display semantics and
closes only resources it owns, including on rollback or cancellation.

V1 ledger integrity failures must atomically fail surviving unfinished recipes,
release their reservation capacity, increment failed counters once and reconcile
affected slots. Completed approvals/bytes and historical terminal counters are
unchanged; cancellation and sibling activity retain precedence. Missing ledger
rows do not authorize invented outcomes or deletion of published bytes.

Jobs retry-index admission failures use a central Jobs-specific RuntimeError
subclass, retaining safe messages and unmodified native database propagation.
PR-added executable tests have exactly one accepted tier; real database tests
are integration tests, while async metadata is not a tier. New test-double
classes and methods have concise immediate docstrings.

Successful browser cancellation abandons only the matching pending operation
for its owner/pack and in-memory key. Capture identity before the request and
compare before clearing; failed cancellation or a newer receipt retains its key.
An ambiguous submit followed by confirmed cancel must permit a fresh next
generation and must not replay the cancelled batch after reload.

## Guarantees and limits

Jobs remains the authority for queue delivery, lease ownership, and retries.
The per-user VN database stores an execution fence and a stable hidden item
reservation for each V1 variant. Only the holder of the current fence may
attach storage metadata or complete an outcome. A replacement worker may take
over only when its Jobs lease is current and different from the stored lease.
If a prior process continues after losing its lease, it may finish an external
model call, but cannot publish its result. Exactly-once external model calls
cannot be promised without provider support.

Claim replacement compares the previously observed attempt token while holding
the VN write lock, then validates the authoritative Jobs lease. Storage
attachment, publication, and failure admission also validate that lease inside
the protected VN transition. This is an admission boundary, not a distributed
transaction across the VN and Jobs databases: cancellation or lease replacement
that precedes admission blocks the transition; a Jobs change after admission
does not retroactively undo a committed VN transition. VN batch cancellation
itself is serialized with publication in the same metadata database.

The generated-file handoff must be idempotent by owner and item source
reference. A concurrent loser must not leave a second live registered file or
visible asset; its temporary file must be cleaned up. Historical duplicate
source references must not make the migration fail or silently delete files
referenced by existing items.

For VN registration, resolve a valid live source-reference replay before applying
new-file quota checks. Registration and applicable user, organization, and team
usage deltas commit together; a failed transaction must leave neither a live row
nor a charge. Preserve user profile-version accounting through the existing
write gateway. Never delete bytes referenced by a committed live file record.
An existing record with missing bytes is not a successful replay and must be
repaired transactionally or rejected without discarding replacement bytes.

## Submission and replay

Batch and receipt links continue to commit together. Failure to create the
parent Job records `enqueue_error` but leaves the linked batch queued, so a
same-key request retries the deterministic Jobs key. Successful recovery
clears the error and records the parent Job ID. A batch that failed during
variant execution is never reopened by submission recovery.

For V1 variants, reserve the hidden item and claim the recipe before calling
the image adapter. A duplicate delivery with the same live lease does not
generate again. A delivery holding a newer Jobs lease may atomically replace
the stale claim and reconcile an existing generated file before generating.
Publication checks the claim in the same VN database transaction as the
outcome transition. Storage and database handoff failures leave the outcome
retryable; definitive adapter failures may be recorded as failed only by the
currently authorized attempt. Replay first looks up the stable source reference and
attaches already registered bytes before considering a new model call.

## Cancellation

Cancelling a V1 batch atomically marks all uncompleted recipe outcomes
cancelled, updates `cancelled_count`, and preserves completed/failed counters.
Cancelled reservations remain hidden and do not consume future generation
capacity. Stale workers cannot change cancelled outcomes to failed or
completed. Legacy V0 cancellation keeps its existing behavior.

## Cleanup and browser recovery

Removing a terminal V1 item must preserve its recipe outcome and historical
batch counters without retaining a foreign key that prevents deletion. Active
reservations remain protected. This behavior must work on existing recipe
tables as well as fresh databases; changing only the CREATE TABLE definition
is insufficient. Completed-V1 cleanup must be exercised through the service,
including file metadata and usage cleanup.

Before publishing a planned replay, validate the owned live file, item source
reference, contained path, and byte-size consistency. Validate both a recovered
source-reference record and an item whose file metadata was already attached.
Missing or truncated bytes must not become a completed draft or trigger
duplicate generation. Filesystem checks stay off the event loop; already
completed replay must preserve review decisions.

Replay also verifies SHA-256 when a checksum is persisted, including same-size
corruption. Historical rows without checksums retain size validation; hashing
uses bounded reads off the event loop. Definitive absence, invalid metadata,
or corruption is nonretryable. An unfinished fenced recipe fails once and
releases its reservation capacity; a completed outcome and its approval remain
unchanged. Transient filesystem errors remain retryable. Explicit regeneration
creates a new draft through the existing API, never silently replacing bytes
under a historical approval or resetting a completed outcome.

The browser keeps its request key after ambiguous submission failures. A
definitive rejection such as a missing slot must clear that pending operation
so refresh/reload cannot retry a permanently invalid target indefinitely or
block future generation. Network failure, timeout, throttling, and ambiguous
server errors retain the same key rather than starting a duplicate request.

## API and quality

Keep existing machine-readable VN error codes. A VN-specific `ValueError`
subclass may carry batch, slot, variant, item, and operation context for logs
without changing public error details. Add concise docstrings to new helpers,
type the test fixture, and offload filesystem metadata checks from the async
worker event loop.

Claim/recovery/response persistence decisions belong to the core service; HTTP
helpers only validate response models and translate errors. New VN generated
file lock and lookup queries live in DB_Management on the caller-owned AuthNZ
connection, preserving transaction admission and user/org/team accounting.
PostgreSQL durability tests delegate lifecycle to isolated_test_environment.
Cleanup logs bind operation and file correlation fields with stack frames,
without raw exception messages or diagnostic locals that could reveal secrets.

## Full Review Follow-Up: Shared State and Parent Health

Slot status is shared by variants and batches. V1 cancellation, completion and
failure must reconcile it transactionally from all remaining active recipes
and published items. Active work takes precedence over terminal/review display;
ending one variant or batch cannot hide a sibling's active work. Generating
admission requires the current claim and Jobs authority under the write lock,
so an obsolete delivery cannot regress a review-ready slot. Preserve V0 behavior
and existing approval/readiness precedence. Document unpublished-item access.

Unfinished receipt recovery must consult the stored parent Job, not equate a
nonempty ID with health. Recover incomplete active fanout through supported Jobs
create/retry operations, preserving owner/type/queue identity, quotas and admin
controls. Missing or retry-exhausted parents must not strand the original batch;
healthy completed full fanout and terminal VN batches must not be reopened.
Failed recovery remains unfinished; completed receipt response snapshots remain
immutable. Persist the recovered authoritative parent ID before completion.

Normal creation and explicit failed-parent re-admission share submission-rate
accounting. A partial event index by domain, owner and creation time for
job.retry_admitted must bound the added history lookup on both backends,
including upgraded databases; do not scan global historical events per create.
PostgreSQL concurrent builds may leave an invalid index after interruption.
Verify this migration's exact table/definition and catalog readiness before
accepting ensure; coordinate repair of its own invalid index with the existing
advisory-lock convention. Foreign collisions and failed repair fail closed.
Use separate autocommit advisory try-lock queries rather than a blocking query
snapshot that can deadlock with a concurrent partial-index build. Bound waiting
by the minimum positive configured lock/statement timeout, or 30 seconds when
both are disabled, and release only the acquired session lock.

Processing status alone is insufficient parent health: its Jobs lease must
still be live without cancellation requested. Expired or malformed processing
parents leave an unfinished receipt pending until supported Jobs reconciliation
allows recovery. Use Jobs-owned clock/health semantics, not a VN reaper or
second lease authority. Shared receipt completion must preserve the first
committed response for its exact owner/scope/resource/key and payload hash,
including when an original submit finishes after a recovery caller.

Executable embedded test helpers require explicit annotations, while shared
PostgreSQL fixture ownership is unchanged. Persisted frontend retry slot IDs
must be positive safe integers; invalid records are removed before API calls.

## Mixed Legacy Slot Display Ruling

V0 batches lack per-variant recipe state. Aggregate counters cannot distinguish
running legacy work from queued work for a specific slot. Shared-slot
reconciliation must therefore use an injected, owner-scoped Jobs-read callback
for queued legacy deliveries, validating exact child identity and live lease
when reporting generating. Jobs remains the only queued execution authority.
The core service and worker wire this callback; no new queue, lease table or
persisted display authority is introduced. Reads occur after VN write admission
and failures remain observable rather than manufacturing readiness.

Inline legacy helper execution may use a narrowly scoped display marker with
finally cleanup, not an execution lease or admission mechanism. Its local
scope and cross-repository/process limitations must be explicit. Legacy model,
publication, counter and terminal contracts remain unchanged. Cover both V1
cancellation while a V0 adapter is blocked and V0 termination while V1 runs.

Legacy final display reconciliation excludes its exact completed execution,
not a replacement lease or live sibling. Display-only failures after an outcome
has committed preserve the original generation return/error classification and
are reported with safe structured context and stack frames, not secret-bearing
exception messages or locals. They cannot trigger another legacy model call.
Transient display state may await normal reconciliation; this is not a second
execution authority or a claim of atomicity across Jobs and VN metadata.
Sanitize display-only exceptions within the final VN transaction body before
the existing rollback logger receives them. Preserve internal type/traceback
for safe worker diagnostics; do not log their raw messages or source literals.
This does not change unrelated transaction entrance/commit logging.

A published V0 candidate alone cannot settle a live replacement delivery of
the same variant. New legacy publication records an opaque delivery fingerprint
in existing item provenance, never a raw Jobs lease token. Exclude settled
activity only when it identifies the exact current canonical Jobs delivery;
unknown historical provenance or a different delivery cannot hide live work.
This provenance identifies an outcome, not lease health or execution authority.

## Terminal Fallback and Public Contracts

Legacy display fallback may fill an otherwise empty terminal display, but
cannot override published review precedence, skipped state or stronger derived
failure. Ending legacy work on a slot with approved V1 candidates must preserve
approval and required-pack readiness. Active and queued work retain priority;
review state, counters and bytes are not mutated by display reconciliation.

Display-only exception types belong in core/exceptions.py; moving their import
boundary must preserve the safe rollback string and internal original type and
traceback used only for frames-only diagnostics. Public retry-admission helper
documentation must accurately state executor/backend, connection/transaction
ownership, shapes, return values, side effects and actual failure propagation.

Legacy PostgreSQL upgrade claims require a real old-schema test through the
current production ensure entry point. Its base DDL creates job_events before
retry-index validation. Do not substitute historic DDL during ensure just to
manufacture a failure or change successful migration behavior unnecessarily.
