# Outbound destination inventory and privacy regression checks

**Status:** Approved for Increment 1 planning
**Backlog:** TASK-15646
**ADR check:** Required. [ADR-097](../ADR/097-reviewed-outbound-destinations-and-privacy-modes.md) proposes the new release and runtime policy. [ADR-026](../ADR/026-security-outbound-egress-and-ssrf-policy.md), [ADR-030](../ADR/030-configured-local-llm-egress-policy.md), and [ADR-090](../ADR/090-configured-searx-egress-policy.md) continue to govern URL safety and narrowly scoped local endpoints. The gate fits the existing required contexts and the proposed CI tiers in [ADR-096](../ADR/096-tiered-development-and-release-ci.md).

## Goal and scope

A contributor can run the same outbound checks locally and in CI. The checks flag newly introduced or undeclared app-controlled destinations and assets in covered flows. Operators can see which remote services and downloads the product expects, which are optional, and what their deployment has observed.

Cover the production API, its workers and app-invoked setup installers, the shipped setup page, the Next.js server and WebUI, and the browser extension. Include optional provider calls, model and asset downloads, app-invoked package and Git operations, telemetry exporters when configured, and user-directed outbound features. The extension scope covers traffic it initiates or injects into a page. Ordinary page browsing and browser-owned services are outside the product inventory. CI dependencies, developer package installation, and image and tool downloads before the app runs are outside scope. An app-invoked install during setup remains in scope even when it uses the same tooling.

Roll out in three increments. The first ships the CI and local check and a scoped product inventory. The second expands runtime coverage and may ship audit reporting with explicit coverage status. The third offers deployment-wide strict modes once the supported deployment profiles meet the release criteria below.

## Product inventory and local approvals

Version the inventory alongside the product. Each built-in entry identifies a capability, owning component, purpose, setup or runtime phase, enabling condition, protocol and exact normalized destination, and reviewed asset identity where applicable. For HTTP use scheme, normalized hostname, and effective port. For other supported protocols use a typed endpoint identifier and protocol-specific validation. Separate exact configured infrastructure destinations from public integration destinations. Prefer exact origins and list redirect or CDN origins per capability. A suffix exception needs a documented reason, owner, and review.

A downloadable resource uses a stable ID tied to the identity used by the real installer, such as a model repository and file or snapshot, a package and its source, or a versioned browser worker. Check the declared version, immutable revision, or digest wherever the installer uses one. The same ID and origin cannot silently authorize a different built-in resource. Reuse production catalogs as the source of resource identities and join policy metadata to them. Keep reviewed build-time references distinct from runtime fetches and ignore docs links and explicit open-in-browser actions in automated request assertions.

Declare user-directed capabilities such as media ingest, webhooks, and custom provider or MCP connections. User input does not create product declarations. Platform administrators and deployment operators can grant or revoke deployment-wide approvals in the instance-local overlay. If the deployment delegates tenant approvals, only an administrator of the affected tenant can grant or revoke them, and those approvals apply only to that tenant's activity. Each approval records an exact destination, capability, scope, approver, timestamp, and optional expiry. Resolve scope from trusted request or job ownership. Unknown ownership grants no tenant approval. Approval cannot override a denylist, tenant restriction, credential rule, or existing address-safety check. Feature configuration and consent still control when declared capabilities may run.

## Increment 1 · required CI and local regression check

- Use one documented local entry point to run the same selected checks as CI. Reuse the existing required contexts and direct-HTTP usage guard. Extend required path detection for manifest-only edits and affected app, shared UI, extension, setup helper, and check code changes. Keep dependency acquisition outside the guarded run. A required scenario that fails to start, is skipped, or produces no coverage result fails its check.
- Check declared endpoint and asset identities against the actual catalogs and dispatch inputs for the covered flows. Reject duplicates and inconsistent or undeclared declarations. Keep named, reviewed exceptions for existing ungoverned call sites with an owner and follow-up. Report new paths and changes to an exception separately from destination declarations. Literal discovery is a review aid for code and build artifacts.
- Run a fresh backend process through its normal entry point. Install the recording network guard before configuration or app import. Use a temporary home, cache, database, and copy of shipped first-run defaults with exclusive dotenv handling and synthetic credentials. Strip ambient developer settings, proxy variables, and CI-only settings that alter app behavior. The scenario must demonstrate normal startup, a first-run setup action and its resulting state, and a representative local-only runtime operation. Wait for relevant deferred work and shutdown before checking recorded DNS and dial attempts.
- Permit only the exact local fixture endpoints named for each default smoke scenario. Use loopback literals or test-owned static mappings for fixture names. The machine hostname and ambient test database settings grant no permission. Any other DNS or dial attempt in the guarded boundary fails the scenario, including a request to a declared external origin or an unlisted loopback port. Prove that a valid fixture request succeeds and that a synthetic blocked attempt fails the run even if caught by the app.
- Exercise at least one opt-in setup download and one real provider adapter dispatch in separate fixture-backed scenarios. Check the declared asset identity at installer dispatch. For the selected download, observe the SDK request after it selects a destination, serve the response locally at that boundary, and check the selected origin and each redirect hop without contacting external services. Use the recording transport to confirm that the provider adapter selects its declared origin. Add negative cases for a new origin, a changed asset on a known origin, and a redirect to an undeclared origin. Calls checked only through installer arguments can verify asset identity. Report their destinations as declared and unverified.
- Navigate to the API server's shipped `/setup` wizard in a fresh browser with the guard active before navigation. Wait for its JavaScript to load, complete one local-only action through the rendered wizard, and verify the resulting setup state and the absence of unexpected requests.
- Check a focused production WebUI flow and packaged Chrome extension flow using local fixtures and existing browser harnesses. Cover first navigation, setup or login, a representative app action, and an extension background request with a fresh profile. Apply the network boundary before browser launch. Observe Next.js server requests independently of browser requests. Test content-script activity on a known local page and inspect the pristine extension manifest before any fixture-specific permissions are added. Check unexpected requests, including a passive asset request, alongside evidence that the flows still work. Replace the automatic Google favicon request in Research Workspace search results with a bundled icon and cover rendering results in the regression check.
- Emit redacted diagnostics with the scenario, component, capability or source hint, and decision. Report coverage for each run. The Python guard covers its instrumented DNS and socket paths. Browser and extension results cover their exercised flows. Document untouched native, subprocess, protocol, and platform coverage in the report.

## Increment 2 · coverage and audit reporting

Maintain a coverage list by transport and process. Identify each boundary as governed, disabled under the strict deployment profile, or unverified. Include sync and async HTTP and their alternate transports, WebSockets, database and cache connections, SMTP, configured Sentry and OTLP, setup package and Git child processes, model SDKs, media download libraries, Next.js server fetches, browser fetches and passive subresources, extension workers, and app-injected page traffic. Exercise cold-cache first use as well as normal setup. Move fixed browser assets into the bundle where practical. A feature-specific server fetch still uses the managed egress path and its own resource and content rules.

Add coverage where a connection actually leaves an app component. Keep static checks, browser policies, and extension permission checks as complementary controls. Validate DNS, retries, redirects, and observable transport outcomes. Test successful local-only operation as well as policy denials. Use OS/container network isolation to verify the claimed boundary for each strict deployment profile. A network-disabled container run can prove a scenario works under containment. Use attempt instrumentation to detect blocked attempts even when the scenario succeeds. State what was exercised and which processes were contained.

The instance-local ledger aggregates observed outcomes for governed activity. Distinguish a policy block from a transport attempt and a confirmed contact using the evidence each transport provides. Validation alone cannot create a contact record. Aggregate by trusted ownership scope, destination or opaque endpoint ID, capability, phase, and outcome. Retain first and last observation and a count. Apply the same access check to reads and exports. Reserve platform-scope access for platform administrators and deployment operators. Where tenant access is delegated, require an administrator role in the affected tenant. Keep events with missing ownership unattributed. Only platform administrators and deployment operators can view or export them, and reports retain the unattributed label. Test that ordinary members and administrators of other tenants cannot read or export scoped entries.

Bound ledger retention and cardinality. Preserve existing opaque endpoint IDs and use an opaque label for sensitive or unapproved user-supplied destinations. Exclude URL paths, queries, credentials, headers, payloads, user content, and raw exceptions. Export capability and reason codes only in metrics. The ledger stays local and does not feed configured telemetry exporters. Report degradation or dropped ledger entries without granting network access on the strength of a failed audit write.

## Increment 3 · runtime modes and release criteria

Use `audit` when no mode is configured on a fresh or upgraded deployment. Strict modes require explicit operator selection.

| Mode | Behaviour |
| --- | --- |
| `audit` | Preserve existing authorization and network safety. Warn on undeclared governed destinations and record observed outcomes. Show the coverage status for this deployment. |
| `allowlisted` | Also require a matching product declaration or authorized local approval for each external destination and capability. Apply existing security rules and independently validate redirects and retries. Exact trusted infrastructure approvals can support LAN providers and sibling services. |
| `offline` | Permit only loopback connections and local Unix sockets within the strict profile. Refuse other destinations before DNS. Ambient DNS cannot establish that an arbitrary hostname is local. Configure trusted local names with non-network mappings, or use loopback literals. |

Set policy before app imports and startup preflight can trigger a network operation. An invalid mode or unusable strict-mode policy must stop startup before probes run. Reject strict-mode destinations before DNS when the mode or declaration already rules them out. Apply the existing checks for schemes, ports, tenant and global restrictions, DNS and private or reserved addresses. Use the checked transport to bind the approved decision to the actual connection. Re-evaluate redirects and retries, including same-host changes to scheme or port. Treat proxies and downstream relays as separate network boundaries. Opaque SDKs, child processes, and background exporters may perform network work only if their boundary enforces the selected mode. Verified no-network containment can support cache-only work.

Preflight names incompatible settings before any reachability probe. Loopback-only offline does not support Compose profiles whose app depends on sibling Postgres or Redis, or a LAN model provider. Those deployments can use allowlisted mode with exact service approvals. An offline setup that lacks a required asset reports how to supply its local package or model. Policy decisions should expose stable, redacted reason codes.

In `allowlisted` mode, each participating worker must reject new requests or application messages once an approval expires or its revocation takes effect, including sends on an already-open session. Recheck authority on subsequent hops and retries. A worker without current policy must stop affected sends. A revocation is effective once workers have applied the change or been fenced from sending on the old approval. Return success only after that point. Close affected long-lived sessions and cancel remaining outbound application writes on in-flight streams. Data already sent can still reach the destination. Release tests must revoke an approval with a connection still open and verify that a subsequent send on it is refused. Exercise expiry and a stale worker as separate cases.

Release a deployment-wide strict mode only when each enabled outbound path in its advertised profiles is governed or contained by the selected mode's destination policy. Ungoverned network-dependent features fail closed. Include default and opt-in setup, cold-cache runtime, WebUI and extension flows, opaque child or native paths, and unsupported configuration cases in the release evidence. For denials determined before DNS, assert that neither DNS lookup nor connection was attempted. Scope any operating-system guarantee to the tested profile, including participating processes and relays. The first CI increment can ship independently.
