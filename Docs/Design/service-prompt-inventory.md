This document preserves the broad prompt-discovery work completed before the Service Prompts design was reduced to an incremental self-service feature. It is research material for selecting later vertical slices; it is not a runtime registry, implementation plan, or migration commitment.

## Eligibility rubric

A candidate is `eligible` only when it is a user-visible content-generation or content-analysis instruction and editing it cannot control authorization, security policy, service routing, tool permissions, or an unenforced machine protocol. Structured-output prompts are eligible only when the output contract is enforced independently of prompt wording.

A candidate is `excluded` when it controls authentication or authorization; safety or moderation policy; provider/model routing or tool selection; tool or MCP permissions; evaluation, judging, grading, or security review; a machine protocol without independent enforcement; or hidden provider/deployment-sensitive enforcement.

A content-facing candidate is `deferred` when eligibility depends on a missing prerequisite, such as independent output enforcement, atomic multipart consumption, or a finite prompt requirement set for queued work. The row must name that prerequisite.

Rows and stable IDs below are historical candidates. The current runtime registry remains the only allowlist, and missing inventory rows do not block a vertical slice.

## Historical contract analysis

The following contract index records the rejected broad-rollout analysis. It is non-normative: its limits, topology requirements, validators, and counts must not be used as current release or implementation gates. A future vertical slice may reuse source and consumer evidence, but it must follow the current design instead.

### Contract notation and inherited budgets

- `E` means editable and visible; `LV` means locked and visible; `LH` means locked and hidden/server-managed. Every named part includes one of those flags.
- `L` means literal: braces are not parsed. `T` means constrained template: only the placeholders listed in braces are declared. `→` concatenates parts, without an implicit separator, within one provider message or one sequential stage. `⇒` separates provider roles/messages or sequential provider stages. `?` marks a source-conditional part.
- The approved **authored-content** limits are **65,536 UTF-8 bytes per authored part** and **262,144 UTF-8 bytes per authored definition**. These storage/authoring limits do not describe current runtime source behavior.
- The runtime limits in this index are an **approved, compatibility-affecting security policy**: each expanded `G` variable and each rendered text part is limited to **65,536 UTF-8 bytes**, the final ordered rendered bundle is limited to **262,144 UTF-8 bytes**, and overflow is rejected unless the index names an existing deterministic truncation before rendering. Legacy consumers can currently accept values above these new ceilings; compatibility above them is explicitly not guaranteed. Non-text image/audio components remain locked and use their existing upload/reference limits; textual references and labels count toward the approved text ceilings.
- Placeholder repetition is source-grounded: each declared placeholder may occur **once per named template part**, matching the current eligible defaults. A definition that needs another occurrence must receive a separately approved contract revision; rendered-part and bundle ceilings still apply. Literal explicit-request fields retain their current no-parsing semantics even when their text contains braces.
- Every `G` in the variable column means the approved 65,536-byte runtime variable ceiling with reject-on-overflow; it never asserts an existing source cap. `C<n>→G` means the cited consumer first performs its existing deterministic truncation to `<n>` source characters/code units, then the approved UTF-8 ceiling is enforced. Finite enums, booleans, and bounded numbers use the current schema/selector bounds and are not free-text expansions.
- `A` means the cited consumer already receives or constructs all named parts at one boundary, so a future resolver can supply one immutable atomic bundle without a partial save or a lower-loop lookup. `S` means a single editable part; locked carrier parts are still authenticated with the bundle.
- Direct/request-local async functions are not queued work. Jobs/WorkerSDK and core Scheduler paths are listed separately below. A definition reachable through both direct and queued execution must satisfy the queued topology before rollout.
- Candidate-row and contract-index Goldens require byte-equivalent provider messages only for authored parts and runtime values that are within the approved budgets. Human approval on 2026-07-13 explicitly accepted the new runtime rejection behavior and the absence of a legacy-compatibility guarantee above the cap. Every generated domain plan must add exact at-limit and over-limit tests for authored parts, variables, rendered parts, and rendered bundles, including the API's `413` response or the cited stable non-HTTP execution error; it may not silently truncate an overflow that the matrix marks reject.
