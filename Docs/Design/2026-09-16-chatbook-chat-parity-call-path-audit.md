# Chatbook chat parity: call paths, concrete gaps, and port design

Date: 2026-09-16. Tracking: TASK-13261. Status: reviewed proposal; application implementation has not started. The [closure addendum](2026-09-16-chatbook-chat-parity-review-closure.md) records current binding decisions and review-loop status. The [first review](2026-09-16-chatbook-chat-parity-design-review.md) and [second review](2026-09-16-chatbook-chat-parity-design-review-2.md) retain their historical findings.

This report replaces filename matching as the basis for the [90-behavior inventory](2026-09-16-chatbook-console-parity-matrix.md). It records reachable behavior, the persisted state involved, what actually differs, and the smallest useful change. It does not award full parity from unit tests or claim that every browser/device/deployment combination has been exercised.

## Baseline and scope

Remote `dev` heads were checked with `git ls-remote` and rechecked before finalization; both still match these pins. Chatbook advanced during this investigation; the second pass uses **24094f23d59c7a9d3cfac964c19fd263bc0393b2**, including backup/recovery PR #2642. Server remains **59049e094e0845a4611ea725ae19b7c1754ea709**. The earlier Chatbook 657f70ff snapshot is superseded. All code links below pin these commits. Inspection and tests use archived source in a temporary directory, excluding unrelated changes in either working tree.

The target is equivalent chat functionality in the shared WebUI and full-page extension, with a compact sidepanel that expands into the extension's own full page. Existing browser capabilities such as comparison, capture, document tools, and dynamic UI remain useful.

Independent local chat operation and optional synchronization are conversation requirements. Chatbook already supplies the reference behavior and Sync v2 foundation. Browser persistence, server persistence, model routing, and execution location need explicit, separate settings and state.

**`tldw-agent` executes actions in an OS environment on behalf of the server.** Its relevant scope is runner transport, workspace/filesystem/Git/terminal tools, downstream agents, and their execution lifecycle. It has no Chatbook conversation-store, runtime-hosting, or synchronization role. No ordinary chat milestone below depends on inventing such a role.

## E1. Exact-message forks: identity, lineage, and mode-specific persistence

The destination action is reachable: `PlaygroundChat` passes `createChatBranch(block.index)` through the shared message actions. Its server path requires `character_id`, creates the child first, and posts a displayed-history prefix as `{role, content}`. It omits the exact fork boundary and rich message state. On failure, when local fallback is allowed, it can create a local branch even if a server commit succeeded but its response was lost. An atomic endpoint alone would not fix that ambiguity. [Mounted action](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/PlaygroundChat.tsx#L1371), [server-copy handler](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/handlers/messageHandlers.ts#L406), [fallback](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/handlers/messageHandlers.ts#L508).

The local Dexie implementation is also a repair location, not a fidelity baseline. It spreads source conversation/message objects and replaces local IDs, retaining possible server mutation IDs and old message parents. Rendering preserves those IDs, and deletion calls the server whenever `serverMessageId` exists. A copied child can therefore retain the ability to mutate its source. Its file copy changes `history_id`, although `sessionFiles` is keyed by `sessionId`; settings are stored separately in Plasmo storage. [Local copy](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/db/dexie/branch.ts#L27), [retained IDs](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/db/dexie/helpers.ts#L298), [delete routing](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/chat/useChatActions.ts#L4436), [file key](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/db/dexie/schema.ts#L376), [settings owner](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/services/chat-settings.ts#L622).

The server's direct DB path can persist parent/root/exact-boundary metadata and accepts message parents and one base64 image. The cited message endpoint does not provide general document attachment copying. With active Sync v2, the conversation payload/materializer omit parent conversation and fork boundary, and the message route rejects binary images. These are concrete mode-specific gaps. Character reopen also requires a valid accepted behavior snapshot and matching settings digest; ordinary character creation resolves current sources and can seed a greeting. Copying a settings dictionary or invoking normal creation unchanged does not establish a faithful character fork. [Session paths](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/endpoints/character_chat_sessions.py#L4590), [message schema](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/schemas/chat_session_schemas.py#L400), [sync payload](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/endpoints/character_chat_sessions.py#L832), [image rejection](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/endpoints/character_messages.py#L455), [resume requirements](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/DB_Management/chacha/conversation_resume_store.py#L549), [character creation](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Character_Chat/character_conversation_factory.py#L2391).

Chatbook freezes the selected path, rejects stale confirmation, commits through its persistence service, and provides explicit ambiguous-commit resolution. These are the reference transitions. [Source admission](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/UI/Console_Modules/session.py#L2150), [source transaction](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/chat_persistence_service.py#L1647), [commit resolution](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/chat_persistence_service.py#L1758).

**Port:** retain the action and existing stores, but first define authoritative path selection, owner-scoped fresh identities, independent history/settings fences, an explicit copy/remap/drop projection, and an idempotent result receipt. Revalidate authorization and source state inside the owning transaction. Keep local/temporary ownership explicit. Resolve unknown server outcomes before permitting another fork; never silently change owners as error recovery. Define the actual transaction boundary separately from settings caches, blob transfer, and Sync publication. The reviewed contract and delivery gates below replace the earlier blanket “one transaction” promise. Covers B01–B03 and relevant C13/F04/F07 boundaries.

## E2. Edit, continue, variants, and rewind need one history model

The browser's mounted edit-and-resend action updates the selected row, slices the displayed history, and calls the local helper that deletes descendants. That is a destructive tail replacement. The inspected action does not use the existing server message-edit endpoint. Chatbook instead creates an edited user sibling and a new assistant sibling, preserving the prior continuation. [Browser edit](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/handlers/messageHandlers.ts#L168), [local tail deletion](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/db/dexie/helpers.ts#L473), [source sibling creation](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/console_chat_controller.py#L19736).

Browser Continue passes no selected message ID and operates on the last response, seeding its text and replacing the last history entry. Chatbook `continue_from_message` works from a selected boundary and appends another assistant message. A button with the same label therefore does not establish equivalent behavior. [Browser continue mode](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/chat-modes/continueChatMode.ts#L42), [source selected continuation](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/console_chat_controller.py#L18503).

Regenerate has a similar targeting issue: mounted messages receive `regenerateLastMessage`, whose handler searches for the latest assistant/user, rather than receiving the clicked message ID. The variant pager changes displayed `messages`, while generation reads the separately stored `memory || history`; its inspected selection handler updates neither provider history nor a server selection. Chatbook creates a selected-message sibling and restores the selected branch's descendants. This is a request-history correctness gap, not merely a missing pager. The server already supports `continuation_spec`, including `assistant_prefill` and `from_message_id`, in `chat_service.py`; reuse that capability when correcting the mounted browser continuation path. [Latest-message handler](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/handlers/messageHandlers.ts#L61), [display-only variant selection](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/PlaygroundChat.tsx#L1149), [request history input](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/chat/useChatActions.ts#L3325), [existing continuation contract](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Chat/chat_service.py#L4035).

**Port:** define stable message, attempt, sibling, selected-leaf, and draft-restoration behavior across existing local/server history owners. The minimum selected-path contract is a prerequisite for exact-message fork, not later work. The server distinguishes conversation `version`, `history_version`, and `settings_version`. Existing character user-message writes can omit parents, and resume selects the latest timestamp tail; a parent walk alone would omit earlier legacy turns. D1 of the [closure addendum](2026-09-16-chatbook-chat-parity-review-closure.md#d1-history-selection-is-client-scoped-accepted-context-is-immutable) chooses client-scoped tagged cursors and immutable accepted projections. It specifies complete-snapshot legacy ordering/review and versioned adaptation without inventing branch ancestry. Use the same selected path for normal provider request assembly and fork; comparison mode has a separate history projection and needs its own fixtures. [History version](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/DB_Management/chacha/message_store.py#L65), [coherent resume state](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/DB_Management/chacha/conversation_resume_store.py#L482), [parentless user payload](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/chat/useChatActions.ts#L2130).

Keep text-only editing distinct from edit-and-resend. Rewind should select the state before a prompt and restore the complete unsent draft; variant selection should restore that variant's descendants. Full edit/rewind, Canvas, annotations, compaction memory, and trace provenance build on this selection contract. Covers C01/C11, B04–B07, and D03/D06.

## E3. Queues and saving temporary chats have specific transition gaps

The shared browser queue supports editing/reordering, model/prompt/tool/OCR snapshots, and a blocked head when dispatch throws. Full Playground converts failed/skipped submit results into that failure path. Sidepanel instead drops the chat mode's structured result in `useMessage.onSubmit`, and its queue sender also discards the returned result; a failed/stopped queued turn can therefore look successful and be removed. For an ordinary directly submitted turn, Stop only aborts the request, and neither surface has the explicit queue-pause transition needed to prevent idle auto-drain. These are distinct cases. Chatbook pauses on Stop and failed/stopped accepted turns; successful completion admits the next item. [Full-page outcome guard](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/hooks/usePlaygroundQueueManagement.ts#L435), [sidepanel submit](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/useMessage.tsx#L2901), [sidepanel queue sender](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Sidepanel/Chat/form.tsx#L2630), [queue result handling](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/chat/useQueuedRequests.ts#L159), [auto-drain](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Chat/composer/hooks/useComposerQueue.ts#L263), [source pause](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/console_prompt_queue_coordinator.py#L369).

A successful turn is not sufficient to admit the next queued prompt if its effective context changed. Chatbook also pauses on a changed context epoch and requires a revision-checked “use current context and resume” action. Its epoch deliberately excludes ordinary linear appends, streaming, terminal status and persistence bookkeeping. The browser queue captures settings but no equivalent context token; dispatch uses the current context snapshot. Branch selection, editing/rewind, compaction or source/policy changes can therefore change a waiting prompt's meaning. [Source gate](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/console_prompt_queue_coordinator.py#L692), [reviewed adoption](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/console_prompt_queue_coordinator.py#L1008), [epoch semantics](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/console_chat_store.py#L21454), [browser snapshot](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/utils/chat-request-queue.ts#L5), [dispatch context](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/hooks/usePlaygroundQueueManagement.ts#L435).

For temporary chats, the browser refuses changing the temporary setting after history exists, and `handleSaveChatToServer` independently returns early when `temporaryChat` is true. There is no rescue through that Save handler. Chatbook's mounted F5 save promotes the existing ephemeral session through `promote_ephemeral_session` and the atomic `promote_console_conversation_bundle`, preserving the existing session. [Browser guards](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/hooks/usePlaygroundPersistence.tsx#L149), [source promotion action](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/UI/Console_Modules/session.py#L3738), [source promotion owner](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Chat/console_chat_store.py#L18681).

Tabs and drafts also exist, with lifecycle differences. Sidepanel tab selection explicitly stops streaming before changing the active tab; its draft key is per-tab. Full Playground's composer instead uses the single key `tldw:playgroundChatDraft`. Chatbook changes the viewed session without stopping another session's stream and saves/restores per-session draft and undo history. [Sidepanel switch](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/routes/sidepanel-chat.tsx#L1286), [full-page draft key](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/hooks/useComposerInput.tsx#L104), [source draft switch](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/UI/Console_Modules/session.py#L4461).

**Port:** preserve Playground's blocked-head behavior, propagate terminal outcomes through both sidepanel layers, and add explicit pause/resume plus context-change admission to the existing queue. Bind the queue baseline to the owning conversation's effective context. Success drains only while that baseline remains valid; ordinary linear responses do not invalidate it. Changed context pauses pending items without sending, and resuming adopts a reviewed current context only if its token and the queue revision still match. Treat this token separately from history_version and from a frozen queued model/settings snapshot. Test Stop/failure for direct and queued turns, context changes during a pending item, and a second change while the resume review is open. Add temporary promotion and per-session draft/stream ownership as separate deliveries. D3 assigns accepted browser attempts to a shared host outside views; sidepanel expansion attaches without cancelling/reissuing the request. Covers C02/C04/C05/C10 and A02/A04.

## E4. Preserve the sync foundation and resolve the actual chat contract mismatch

Chatbook has a committed-intent outbox with source-proof checks, local push/pull/apply, durable outgoing work, and receipts. The server has Sync v2 storage, conflict handling, and production chat materializers. These are useful foundations, but their pinned chat contracts do not directly interoperate. [Committed producer](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Sync_Interop/chat_outbox_producer.py#L82), [local service](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Sync_Interop/local_first_sync_service.py#L408), [production registry](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Sync/v2/factory.py#L129).

| Boundary | Pinned implementation | Required alignment |
|---|---|---|
| Chatbook outgoing chat | Legacy `chat` domain, `upsert/delete`, role-based encrypted content; API serializes its model directly. | Adapt domain, operation, payload, identities, base versions/hashes, and conversation/message dependencies together. |
| Server public chat | `chat.conversation/upsert`, `chat.message/append`, `tombstone`; M1 requires `server_trusted_v1`. | Use these registered public domain identities as the integration target and explicitly version missing chat fields. A name-only alias cannot reconcile encrypted payload semantics. |
| Chatbook incoming chat | Local apply registry includes legacy `chat`, not the two server chat domains. | Add the matching reverse projection and demonstrate a round trip through public schemas and actual owners. |

[Outgoing contract](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Sync_Interop/envelope_builder.py#L329), [HTTP serialization](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/tldw_api/client.py#L16453), [server operations](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Sync/v2/models.py#L111), [public validation](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/schemas/sync_v2_models.py#L1951), [incoming registry](https://github.com/rmusser01/tldw_chatbook/blob/24094f23d59c7a9d3cfac964c19fd263bc0393b2/tldw_chatbook/Sync_Interop/envelope_applier.py#L76). A review-time schema probe accepted the M1 control and rejected four incompatible domain/operation/encryption cases; it did not exercise a full push/pull journey.

The mounted browser uses a separate auto-save/mirroring path. Server readiness can upload a non-temporary local chat, and Save assigns `serverChatId` before individually copying role/content rows. Existing completion mirroring suppresses duplicate writes when the server already persisted the turn; retain that guard. Neither mirroring nor timestamp-based settings reconciliation establishes Sync v2 conflict semantics. Server-side activation is also currently user-wide: a default personal Chatbook dataset selects active server-origin sync, rather than a per-conversation opt-in. Enrolling sync can therefore change native endpoint behavior. [Browser persistence](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/hooks/usePlaygroundPersistence.tsx#L275), [auto-save](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/hooks/usePlaygroundPersistence.tsx#L341), [write guard](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/hooks/chat/useChatActions.ts#L1087), [settings reconciliation](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/services/chat-settings.ts#L665), [server activation](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Sync/v2/server_origin.py#L293).

Active-sync conversation projection omits exact fork ancestry/settings; message creation rejects binary images, message edits are rejected, and streamed character-completion persistence is unsupported through the inspected route. Sync storage and the chat DB are separate owners; atomic envelope append is followed by individual materializations that can stop after a later failure. Synced fork completion requires a versioned retained-field contract and a recoverable publication boundary, not bypassing the sync path with direct DB writes. [Conversation projection](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Sync/v2/materializers/chat.py#L68), [image restriction](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/endpoints/character_messages.py#L455), [edit restriction](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/endpoints/character_messages.py#L988), [stream restriction](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/api/v1/endpoints/character_chat_sessions.py#L8205), [separate stores](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Sync/v2/factory.py#L433), [batch materialization](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Sync/v2/server_origin_batch.py#L917).

Independent local generation requires a separate implementation delivery. The normal browser model factory constructs `ChatTldw`, which streams through `tldwClient`; disconnected submission queues on server readiness. Dexie retention alone cannot supply generation without that server. D3 of the [closure addendum](2026-09-16-chatbook-chat-parity-review-closure.md#d3-local-operation-has-a-concrete-model-route-and-browser-execution-owner) selects an independent existing-server model connection with stateless requests and model-scoped credentials/admission, plus an explicitly installed WebUI shell for cold reopen. A local server/model deployment is the initial all-local configuration; direct providers are a later adapter extension. Neither is supplied by `tldw-agent`. A remote model may remain a network dependency even when conversation storage is local. ## Recommended delivery structure

Extend the shared UI and existing server/domain owners in complete user workflows. Three approaches were considered:

| Approach | Useful property | Cost and decision |
|---|---|---|
| Complete one shared chat behavior through UI, owner, persistence, and applicable sync | The same interaction serves both full-page clients and can be tested at the actual failure boundary | Recommended. Requires explicit local/server adapters but reuses today's architecture. |
| Extract a reusable headless Chatbook domain engine for server use | Can reuse sophisticated Python history/compaction logic directly | Extraction and coupling work is substantial; browser-local operation still needs its own owner. Evaluate for a bounded domain, not as a prerequisite for all chat. |
| Finish shared backend contracts in larger batches before exposing controls | Can consolidate closely related history/schema changes | Useful for the atomic history transaction only; broad batches defer the user-flow checks that revealed the current gaps. |

Use five workstreams, with independently reviewable deliveries inside them:

1. **Conversation actions and history:** fix fork identity/failure recovery and establish selected-path semantics before faithful exact-message copying. Complete reversible edit/variants/rewind, temporary promotion, and save/reopen/export against that model. Queue cancellation is an independent correctness repair and need not wait for fork.
2. **Context and knowledge:** next-send assembly, Personal Context injection/review, source staging/citations, Research/Workflow/Watchlist handoffs, then durable compaction and Lesson actions. Profile and broken workflow handoff can proceed independently; revision-bound context depends on stable history.
3. **Agent and workspace interaction:** repair the full Python/Go ACP control path and common budget admission before building richer fleet/steer/question interactions on them. Verify explicitly selected server/external execution for the features that use it.
4. **Rich conversation:** selection side chats/feedback, versioned Canvas, voice continuity, generated media, roleplay details. Canvas and annotations depend on history/revision identity; existing image/voice controls remain useful.
5. **Compatibility and inspection in each delivery:** independent local operation, explicit sync enrollment, versioned retained fields, imports, assets, traces, usage, and recovery. A feature remains incomplete in an unsupported required mode; a limited release must name that limitation.

### Revised history proposal: establish selection and ownership before completing fork

The original “exact-message fork first, variants later” sequence hid a real dependency. The first history specification must define the selected path, legacy-history interpretation, owner binding, and retry receipt. It can reuse existing DB transaction and resume helpers; it does not require implementing all edit/rewind behavior or replacing chat storage.

The following contract applies to the eventual complete fork. D1–D6 of the [closure addendum](2026-09-16-chatbook-chat-parity-review-closure.md) resolve its selection, receipt, publication, model, trust and runtime choices; these are no longer alternatives left to implementation.

Common fork fixtures must include a non-last boundary, selected assistant variant with different descendants, duplicate-content messages with distinct identities, a selected image/document, source/history/settings changes during confirmation, an active or partially committed generation, failure before commit, lost response after commit, reopen, and deletion of the child without source mutation. Reject transitions while the selected source cannot provide a settled coherent snapshot; do not copy an in-flight run. Scope fixtures to actual supported modes and keep unmet matrix cells open.

Specification gates apply to the delivery being implemented. H1 implements D1 selection/legacy semantics and safe local field projection; H2 implements D2 native transaction, receipt, asset and character binding; H3 adds browser/temporary commit and cache recovery; H4 implements D2/D4 sync projection, negotiated trust modes and consent lifecycle. Independent generation and WebUI cold availability are F02's own required work. Queue and ACP repairs do not wait for unrelated provider or sync decisions. Encode these resolved contracts in the applicable focused specification before that delivery's implementation plan; neither this review nor a partial release counts as approval or complete parity.
