Status: design and implementation plan; Task 1.1 projection is qualified, with no complete H2 runtime qualification. ## 1. Outcome and boundaries

A native server conversation can be copied at an accepted settled history boundary into one independently owned, usable child. A lost response resolves to that same child; retry never produces a second child. Both the WebUI and extension full-page UI expose the same behavior. The compact extension sidepanel expands into the extension's own full page when the review needs space.

H2 covers native ordinary chats and accepted single-character snapshots, including their supported rich preset/worldbook/memory/exemplar/author-note/pin settings, embedded images, and typed native document/generated-image attachments. Source or child deletion cannot delete the other owner's state or retained bytes. A copied character remains usable after the original card is changed or hard-deleted. No new greeting, provider call, tool call, ingestion job or summary generation occurs merely because of forking.

This is a bounded delivery within parity, not all of B01–B03. H3 owns browser/temporary commits and canonical cache recovery; H4 owns enrolled Sync creation/publication; F02 owns independent local models and cold WebUI availability. Persona-primary, multi-participant routing, rich overlay/research adapters and comparison fork modes unsupported by native accepted snapshots remain explicitly gated dependencies of broader parity. Their presence is never silently downgraded into an ordinary chat. Workspace scope is supported by the common owner API; separate `WorkspaceChatPanel` UI qualification remains open unless included in the final evidence.

`tldw-agent` has no role in chat storage, browser execution, model hosting or synchronization. It remains the server-directed executor for external OS/tool environments.

## 2. Chosen approach

Use a small native operation store, pure retained-state projectors, existing connection-aware conversation/message/snapshot stores, and a native asset adapter over existing validated upload and immutable byte-store machinery. Bound external preparation by existing destination ingestion/storage limits, then perform one short ChaCha transaction. The API call is synchronous; a timeout becomes same-operation recovery. No new Jobs workflow or distributed transaction coordinator is introduced.

Alternatives considered:

| Approach | Decision |
|---|---|
| Wrap the current create-chat/N-create-message HTTP sequence in client retries | Rejected: neither rollback nor exactly one child can be guaranteed after a lost response. |
| Create a hidden cloned character card | Rejected: adds a second mutable behavior authority and delete/picker lifecycle, while still requiring a frozen next-send composer. |
| Adopt MediaFiles/export URLs after a final cross-store authorization read | Rejected: that read cannot serialize external revocation/deletion with the chat commit; source cleaners do not know chat references. |
| Explicitly retain external/browser bytes under native ownership before accepting a fork capture | Chosen: the user submits a new owned copy through existing ingestion validation. The fork then authorizes native claims in its own transaction. |

Explicit retention is a separate visible action, **“Retain attachments on server”**, offered only for a native source selected by the user. It never runs as a hidden side effect of selecting Fork, and it never silently uploads a browser-local conversation. After successful native retention the client recaptures the source and presents the new fork review. This refines D2's source-asset boundary without weakening atomic admission.

## 3. Authority, namespace and wire contract

The server derives `owner_key` using `native_history_owner_key(request, authenticated_user_id)`. The per-user ChaCha dataset plus authenticated `client_id`, `operation_kind` and random UUID `operation_id` uniquely identify an operation. Scope is the canonical pair `["global", null]` or `["workspace", workspace_id]`; source and destination scopes must match in H2. Server/account/base-path and scope are frozen in the request digest and stored operation. Browser profile identity stays in the browser dispatch record; it cannot grant server authority.

Lookup checks authenticated namespace, expected-user guard, stored owner key and scope before returning any operation state. A changed server alias/base path or wrong account does not reinterpret an old key as a new operation. The unique key does not include the request digest: different input on an accepted key conflicts. UUID syntax is not authorization. Limits, token scopes and rate limits use the existing API dependencies.

New versioned API, rooted at `/api/v1/chat`:

| Method/path | Request and response |
|---|---|
| `GET /fork-capabilities` | Authenticated/scoped `NativeForkCapabilitiesV1`: protocol `native_atomic_v1`, projection `native-fork-v1`, enabled behavior/asset representation versions and effective existing limits. Old-server absence is decided here, never from a failed mutation. |
| `POST /conversations/{id}/fork-capture` | `NativeForkCaptureRequestV1`: H1 view cursor/interpretation plus fidelity choice. Returns coherent selected revisions, fork-purpose retained-context digest, typed asset manifest and missing/unsupported reasons. Read-only; no retention, child or operation allocation. |
| `POST /fork-operations` | `NativeForkRequestV1`; first admission returns 201 committed, replay 200 committed, a concurrent owned preparation 202 pending, or a typed rejection. All commits return the existing committed result shape plus protocol/projection version. |
| `POST /fork-operations/{operation_id}/resolve` | Frozen owner/scope and request digest; resolves without requiring the source to exist. Unknown key is `not_recorded`, distinct from retryable preparation, expired, gone and denial. It is not permission to mint a new key. |
| `POST /conversations/{id}/retained-assets` | Multipart through the existing upload sink, with a versioned representation/selection manifest, distinct `native_asset_retention_v1` operation ID/digest and source attachment revision. Commits native source claims only after verified bytes exist. Reuses the operation namespace/recovery mechanism with a different kind. |
| `POST /retained-asset-operations/{operation_id}/resolve` | Same authenticated original-owner recovery; returns committed native asset IDs/revisions or pending/terminal outcome, not an arbitrary upload path. |
| `GET /conversations/{id}/retained-assets` | Current canonical ordered context/reference manifest and `asset_manifest_revision`, authenticated/scoped/projection-gated; used to reconcile a lost context update response. |
| `GET /conversations/{id}/retained-assets/{asset_id}` | Owner/scoped metadata or bounded download of exact immutable revision, using existing download response safety. No source URL fallback. |
| `PATCH /conversations/{id}/retained-assets/context` | `NativeAssetContextUpdateV1`: expected manifest revision, `target_reference_id`, expected reference and asset revisions, and `remove_from_context`, `replace` or `restore`. Replacement names an already retained live claim/revision in this same native conversation. Returns the canonical manifest/revision; conflict is 409 with no writes. |

These paths require precise method/path allowlisting in both transports and `require_expected_user`. No route accepts a filesystem path, export URL or external file ID as byte authority. The multipart endpoint reuses `save_uploaded_files`, `FileValidator` and existing MIME/content preflight; it is a native destination adapter, not a second parser/upload pipeline.

`NativeForkRequestV1` has strict/frozen fields: `protocol`, `projection_version`, `operation_id`, `owner_key`, `scope`, `source_conversation_id`, `input` (normal H1 selection with purpose fork), `retained_context_digest`, ordered `asset_manifest`, `fidelity`, `child_title`, `request_digest`. Unknown fields fail. The server returns the canonical request skeleton at capture except for operation ID/title/digest. Operation results retain H1's `state`, `operation_id`, `owner_key`, `child_id` and `message_map` names for committed results; add protocol/projection explicitly rather than inventing another child/status field. No credentials or prompt bodies need to be echoed in the operation result.

The scope wire object is `{kind:"global"}` or `{kind:"workspace", workspace_id}`, with a canonical nonempty workspace ID; global scope rejects a workspace ID. The digest uses the pair defined above. Fidelity is `strict` (default) or explicit `allow_unavailable`; entry disposition is `retained` or `unavailable`. Unavailable entries use `unavailable_v1` with a null hash and require `allow_unavailable`. The finite asset roles are `message_image`, `document_context`, `generated_image` and `reference_image`; validate each against its representation. Role and exact reference identity are separate from byte representation. `message_map` remains the H1 JSON object from source message ID to child message ID, with immutable internal storage.

Operation-kind tags are `native_fork_v1` and `native_asset_retention_v1`. Asset hashes are lowercase 64-hex SHA-256; accepted behavior snapshot digests retain their existing `sha256:` prefix. Wire identifiers are bounded to 256 characters, owner keys to 1024, and child titles to the existing chat limit of 200; preserve exact validated text. The internal projected snapshot schema string is `"1"`, while the canonical accepted snapshot payload keeps integer `schema_version: 1`.

Define the cross-language digest over this fixed tuple, compact UTF-8 JSON and SHA-256, with no floats or object-key ordering dependence:

```text
["tldw-native-fork", 1, operation_id, owner_key, scope_tuple,
 source_conversation_id, projection_version,
 [interpretation_kind, legacy_projection_id_or_null],
 [cursor_kind, cursor_message_id_or_null],
 [[selected_message_id, retained_message_revision], ...],
 retained_context_digest,
 [[reference_id, reference_revision, asset_id, revision, representation,
   role, context_enabled, hash_or_null, fidelity_disposition], ...],
 fidelity, child_title]
```

Message and asset order is the canonical captured order. Strings use their exact validated Unicode content; no client-only title trimming or normalization after digest. Limits reject invalid title/identifier lengths before digest. Shared Python/TypeScript fixtures cover Unicode, empty boundaries, missing markers and order. View revision, volatile fence counters and excluded source memory are recapture hints, not semantic copy inputs. All effectful source selection, destination, title and fidelity choices are covered. The server recomputes the digest, then re-resolves membership and retained content; an internally consistent client hash is not evidence of valid source content.

## 4. Operation store, replay and deletion

Add `native_chat_operations` under ChaCha. Its primary key is `(client_id, operation_kind, operation_id)`. Store original owner/scope, canonical request/digest, protocol/projection, state, attempt generation, lease expiry, timestamps, terminal reason and immutable committed result. Store no source/child cascading FK. PostgreSQL RLS is direct authenticated-owner matching, not a live-conversation predicate. At-rest operation inputs follow chat confidentiality; never log canonical request bodies or asset bytes.

States are `preparing`, `committed`, `rejected`, `expired`, and `gone`. Attempt generation/lease is internal; a `preparing` operation may receive a new attempt only through locked CAS under the **same** key and identical request. Lease expiry alone does not prove failure: inspect receipt/claim state first. No background task creates a child. A new HTTP attempt explicitly resumes bounded preparation after reconciliation; a live attempt returns pending with retry guidance.

| Observed state | Same-key behavior |
|---|---|
| No row | Authenticate, validate request, reserve once. Resolve alone returns `not_recorded`; resubmission of the exact frozen request may reserve it. |
| Preparing, active attempt | Return pending; no second executor or independent namespace claim. |
| Preparing, abandoned attempt | Fence the old generation, reconcile prepared rows, resume same request if still authorized/fresh. A stale worker cannot publish a child. |
| Committed | Resolve receipt **before source lookup/freshness and current source Sync routing**. Reauthorize current child access and scope before revealing IDs/map. |
| Rejected/expired/gone | Return terminal outcome without preparation or recreation. Different digest always conflicts before outcome data disclosure. |

Full receipts remain until explicit retention maintenance. Compaction may replace them with a minimal permanent accepted-key tombstone containing owner/scope/key/digest/terminal state; it cannot free the key. The initial release does not automatically prune accepted keys. Preparation expiry may burn a key after reconciliation; it does not authorize a new request ID automatically. A deliberate new reviewed fork uses a new ID. Guarantees require the same durable owner database, including receipt/tombstone backups; destroying/restoring only part of that database is not supported recovery.

Soft/hard/bulk child deletion changes its creation receipt to `gone` in the same native transaction. Soft delete, including bulk/workspace trash, denies ordinary access but keeps recoverable asset claims/bytes and their storage charge. Cleanup cannot reclaim them while the conversation is restorable. Only hard purge or an explicit irreversible asset-retention action releases claims. The map need not remain disclosed. Explicit chat restore reactivates the retained chat/assets but does not make this creation operation replayable again. Source deletion after commit leaves the receipt valid. Lookup of a committed receipt with an unexpectedly missing/deleted child returns gone and conservatively records that terminal state; it never calls creation.

For deletion, first discover the child's protected creation-operation key without row locks, then lock that operation before the child conversation and verify the binding again. Creation/resolve uses operation then relevant conversation. Bulk operations sort operation keys then conversation IDs. Do not add old-message row locks after a conversation lock. Direct database migrations/admin purge paths must use the same tombstoning adapter or preserve burned keys; application API deletion tests alone are insufficient.

### Workspace lifecycle admission

The [workspace lifecycle review](../Reviews/CHATBOOK_H2_NATIVE_WORKSPACE_LIFECYCLE_REVIEW_2026_09_18.md) identified W1/P2: existing workspace deletion enumerates chats before its final transition, allowing a concurrent native child to be missed or detached by `ON DELETE SET NULL`. Add protected `workspaces.native_chat_admission_closed`, default false, independently of the existing clone `system_operation_state`. An ordinary visible workspace uses the existing `system_operation_state IS NULL` condition; this adds no publication state.

Before soft or hard workspace deletion enumerates chats, begin a short outermost transaction, lock the owned ordinary workspace row and close native admission idempotently. Soft deletion requires an active row and rechecks the supplied public expected version; hard purge accepts an owned active or deleted row, preserves its current versionless signature and absent-row idempotence, and validates any explicitly supplied future version. Keep closure outside the public version counter. Commit and release this workspace lock before the existing cascade. Reject an enclosing transaction before any mutation: nested repository transactions cannot provide this commit boundary, and the method must not commit unrelated caller work or use another connection to evade it.

Final native fork/retention admission locks `operation → workspace → conversation → native claims/references/candidates`, with deterministic ordering within each level. Under the workspace lock require the authenticated owner, an active ordinary workspace and open admission; hold it through native commit. Asset context mutations and protected chat restore also acquire workspace before conversation. Global scope needs no workspace lock. Never acquire workspace after conversation. Workspace begin-close holds only its workspace lock; the later receipt-aware cascade uses operation-before-conversation without holding or reacquiring that workspace lock. Closed admission still permits deletion, tombstoning and candidate cleanup.

A failed cascade or final workspace CAS leaves admission closed and returns a retryable lifecycle error such as `workspace_delete_incomplete`. Keep an undeleted owned workspace discoverable so the user can retry deletion with its current public version; retries re-enumerate remaining chats. No timeout, metadata edit, import, Sync or ordinary upsert reopens admission. Before the final workspace transition, reacquire only the workspace lock, revalidate owner/closure/version, and check protected rows: soft delete requires no live protected conversation; hard purge requires none, including trash. Neutral native children and typed-retention sources count. If any remain, abort and release this transaction with the lifecycle error; do not wait for their operation locks while holding workspace. This prevents FK scope detachment without redesigning unrelated legacy concurrent creation.

There is currently no workspace restore/reopen API; H2 adds none. Individual protected chat restore requires its original workspace to remain owned, ordinary, active and admission-open, and never revives a gone creation receipt. Generic settings/identity/import/Sync paths cannot reparent or revive protected rows, strip native protection or clear closure. Receipt lookup remains before source admission: a still-existing committed child in a closing workspace returns lifecycle denial without exposing its map, while the stored receipt remains committed. Only actual child deletion/missing-child evidence yields `gone`. Existing terminal keys remain owner/scope/digest-resolvable even after the workspace disappears. Preparing operations that lose to closure cannot publish and reconcile the same key and unadopted candidates outside the commit.

## 5. Preparation and atomic commit

1. Client writes the immutable `native_atomic_v1` request into its original owner/profile/scope dispatch record before sending. If durable write fails, no request is sent.
2. Server authenticates, recomputes request digest and looks up the operation. Return terminal/replayed result first. For a new/resumed operation, check current native owner routing, reserve attempt, and capture authorized source/native asset revisions.
3. Reserve each external byte candidate in `native_chat_asset_candidates` before I/O: operation key, attempt generation, random namespace/upload token, expected hash/size/MIME/representation and source native asset revision. Embedded DB images need no staging.
4. Outside the chat transaction, reserve the candidate's logical retained-byte charge through the existing quota authority as specified in §8, then copy exact native owned bytes through the guarded verified blob mechanics into the candidate namespace and mark prepared by generation CAS. Enforce existing destination limits and quota preflight. No model, regeneration or one-shot download occurs.
5. Start one repository transaction. Lock operation, check same attempt/digest and replay again if committed. For workspace scope, lock and validate open workspace admission as above before locking source conversation; recheck current owner/scope/native routing, selected settled membership and the fork-specific retained projection. Lock/verify relevant native asset claims/candidates in deterministic ID order. A source/workspace deletion or required-asset revision change winning this admission produces no child. A coherent snapshot admitted before a concurrent existing row writer completes may validly copy that older committed state.
6. Allocate child/message/tool-replay/reference IDs. Insert independent child graph, projected settings/snapshot/binding, copied embedded images and adopted native claims; remap selected references. Insert fresh child-owned graph/settlement provenance, never source admission authority. Install immutable source-to-child map and committed result on the operation; the child is ready in this same commit.
7. Only after commit return the receipt. An exception before commit rolls back every child row/claim/receipt; candidate bytes remain operation-owned for reconciliation. Losing response or client result-cache failure never changes the committed outcome.

No network, filesystem transfer, provider, ingestion or live behavior lookup occurs inside step 5–6. Reuse the coherent selected-content read on the caller connection; do not paginate/truncate a selected branch or hold a snapshot across separate API reads. Data needed after commit is immutable detached data. Recheck source account/workspace authorization through the same native ownership fields, not browser labels. Existing request authentication/ACL checks remain required; there is no promise to undo a committed copy after later account/workspace access loss.

## 6. Retained projection and exact child state

Use a separate `project_native_fork_context` and a fork-purpose snapshot adapter. Do not change H1 send-purpose raw settings digest/validation. Re-read on any fence change; compare the canonical retained projection, so an excluded-only summary update or JSON formatting change can pass while a changed accepted prompt/asset cannot. Required malformed state differs from absent neutral state.

| Source state | Child projection |
|---|---|
| Selected settled complete/stopped/failed messages | Exact retained text/order and fresh IDs/parent links. Selected active rows reject. Empty and before-first boundaries create an empty ready child without greeting seeding. |
| Tool replay/citation metadata | Closed supported call/result groups, fresh/remapped replay IDs, bounded historical excerpts/labels. Do not execute replay or copy live approvals, continuations or source credentials. An incomplete/unknown required group rejects with a specific unsupported projection reason. |
| Historical usage/diagnostics | Optional inert provenance linked to retained rows, excluded from new-child usage/billing totals. No source execution handle is callable. |
| Settings/sampling/declarative policies | Validated independent canonical record. Preserve supported effective provider/model/sampling, preset/worldbook policy, authored memory, author note and summary/greeting policy. No ambient defaults or provider inventory resolution during copy. |
| Existing summary/compaction memory | Drop content/ranges/timestamps and classified summary-derived memory from every supported public and materialized container; preserve summary enable/threshold/window policy. Rebuild snapshot/envelope binding if nested projected bytes change. |
| History pins | Remap only references to selected retained rows, drop omitted-row references explicitly in review. Exclude one-shot/pinned assistant prefill and source pending-greeting authority. |
| Draft/queue/run/ingestion controls, source admission, secrets | Drop. Copying the chat neither cancels nor resumes the source job and creates no sync publication intent. |
| Unrecognized behavior/metadata/asset carrier | Reject before child/input writes; do not reinterpret as plain text or “no settings.” Advertise the exact unsupported mode. |

A source provenance ID is display/audit data only. Set child lineage root to the independent child; optional source IDs in receipt/provenance have no foreign key that can erase it and no authority to read or mutate the source.

For the current accepted memory schema, retain explicit creation-request text and `manual` entries. The known `fact`, `relationship`, `event` and `preference` categories without a source conversation can represent manually created entries and are retained. Those non-manual categories with a source conversation are not sufficiently classified: the extraction endpoint writes the same categories, while the accepted snapshot lacks finer derivation provenance. Reject that source with an explicit unsupported derived-memory code; do not silently copy or discard it. Explicit summary/compaction entries are excluded. A future typed provenance adapter is required to qualify additional derived memory.

Remove both public `roleplayPendingGreetingV1` and materialized `values.greeting`: the latter is populated from source pending/selected greeting records. Keep declarative `behavior_controls.greeting` and the accepted base snapshot greeting definition, with no new greeting execution or live lookup. Rebuild the envelope after removing source authority.

## 7. Accepted character behavior through reopen, edit and send

Add protected `assistant_binding_mode='snapshot_v1'` with `assistant_kind='character'`, `character_id=NULL`, and `assistant_id='snapshot:' + child_uuid`. Validate a single accepted primary character and a valid child-owned `BehaviorSnapshotV1` plus materialized envelope in the insertion transaction. Use a dedicated internal insertion seam; public new-character creation remains numeric-card validation. Do not let generic identity setters, public settings keys or legacy Sync manufacture/rebind this mode.

A snapshot-bound child may itself be forked. The fork-purpose resume read carries the protected binding mode and child ID. For that source, require `assistant_id='snapshot:' + source_child_id`, null card FK, valid accepted single-participant snapshot and bound envelope; the accepted participant's original card ID is inert provenance and need not equal the child-local assistant ID. An unprotected row that merely uses a `snapshot:` string cannot claim this rule.

A bounded server binding descriptor carries mode, opaque ID, accepted display name, schema/digest and canonical settings revision. List responses do not contain full prompt bodies. List/filter/detail/settings readers recognize this protected identity, derive presentation from accepted data, and do not call `getCharacter`. General character lists include snapshot-bound children; live-card-specific lists do not claim ownership of an independent child solely because of inert provenance.

Cold reopen in a new browser must recognize native ready/binding authority from the server, with no local fork receipt. Canonical source settings/snapshot determine the child context. Stale Plasmo settings, draft assistant state and live card defaults cannot overwrite it. Title/model/sampling or supported child behavior edits validate/rebuild the child accepted envelope atomically; explicit assistant replacement is a separate rebind and is not an incidental settings read. Reset removes the child's summary/prefill state without reloading a live card or reseeding greeting.

Extend H1's selected-history admission with `FrozenHistoryBehaviorPlan`. Validate its full supported effect inventory before appending current user input, under the same owner transaction as selected-history validation. Compose afterwards over the exact detached selected messages and admitted input. Extract pure matching/packing/placement from existing preset, worldbook, exemplar, author-note and memory helpers and supply frozen accepted values. The regular character route that reloads live card/preset/book is not a substitute.

The supported single-character plan includes accepted custom preset templates and order; worldbook definitions, scan/recursion/priority/token policy; accepted authored memory and exemplar selection policy; author-note placement; selected/remapped pins; effective sampling. Summary policy starts from child-selected history with no copied summary; reuse deterministic summary construction and child-owned fenced persistence rather than querying source rows. Carry both admitted settings version and the post-input-append history version into any detached summary update; compare both under the child owner lock. An edit/delete/other append while composition is held makes that cache write stale and it is discarded, never installed under a fresh fence. Every ordinary/character/direct completion entry point for a snapshot-bound child either enters this admission/composer or rejects before persistence/provider dispatch. There is no legacy live-source escape hatch.

Persona-primary, multi-participant/routing and effects whose accepted schema lacks complete frozen inputs must return an explicit unsupported capability. They remain listed broader-parity dependencies, not evidence that the accepted single-character gate is complete. Storage-byte equality is insufficient: required qualification poisons all live behavior readers and verifies cold reopen, child edits and the next actual provider payload.

## 8. Native asset representation and retention

Native asset claims live in ChaCha, under `(client_id, conversation_id, asset_id, revision)`, with immutable content hash, size, MIME, representation and native internal namespace. Message/context references name that claim/revision and role, not an external file ID. Supported representations are `embedded_image_v1`, `document_original_v1`, `document_text_v1`, `generated_image_revision_v1`, and `unavailable_v1`. Original bytes and extracted/OCR text are separate representations; a historical citation alone is display provenance, not a promise of the whole original.

Typed manifests distinguish original document, processed text and generated image revision. `UploadedFile.content` often holds extracted text under the original PDF/DOCX name: never pass it through `asUploadFile` as if it were original binary. An explicitly retained text representation uses truthful text MIME, actual UTF-8 byte length/hash and its own identity. Original fidelity requires actual original bytes. If those are gone, the UI offers restoration/re-upload or reviewed degradation, not relabeling text as the original.

For an external original, an existing authorized download may supply the bytes; an explicit subsequent upload is a new user-submitted copy. External revocation/deletion after native retention does not revoke those already owned bytes. Promotion does not directly adopt MediaFiles/Collections/AuthNZ rows. Retention uses the existing validated upload sink followed by a narrow native destination adapter and a source owner/attachment-fence transaction. An ingested Media ID, draft ID or upload success alone is not completed retention. Lost retention responses resolve their own original operation before source recapture.

Freeze the selected browser/native asset revision and bytes before upload. The source manifest update compares the original attachment/selection revision and original account/workspace; a held upload cannot attach to a later selection/chat. It advances the native asset/context fence. After native commit, discard the earlier fork capture and review the new authoritative manifest. Delete/cancel on the child never sends a source ingestion job/batch/draft cancellation.

Generated events are classified before generic text. Retain the exact selected revision bytes plus supported declarative generation metadata; variant count/index or a FileArtifact ID cannot establish byte identity. No regeneration and no hidden one-shot export consumption. Remap executable refine/reference-image links to native claims; external `fileId`/`referenceFileId` are inert provenance only. Missing required reference-image bytes prevent a faithful refine/context capability even when the generated output itself exists.

For a later **explicit** refinement send, carry `reference_image={kind:"native_chat_asset_v1", conversation_id, asset_id, revision, scope}` through `ImageGenerationRequestSnapshot`, both `createImageArtifact` client implementations and `/api/v1/files/create` image payload. It is mutually exclusive with legacy `reference_file_id`; supplying both rejects. `ImageAdapter.normalize` preserves/validates the typed discriminator; export admits either representation. Inject the authenticated native claim resolver through `FileArtifactsService`/image request context. Resolve current owner/scope, required projection support and exact native revision/hash/MIME/size, then supply detached verified bytes in the existing `ResolvedReferenceImage`/`ImageGenRequest.reference_image`. No fallback to MediaFiles or remote URL is permitted. Preserve existing backend/model reference-image capability checks. H2's full-page refinement route uses the existing inline synchronous export; async job/re-export paths reject this native representation before creating work until they carry their own current authorized resolver. Delete the original MediaFiles source in the qualification case and assert the provider receives the retained native bytes. This is a consumer adaptation, not image regeneration during fork.

Use `LocalSyncBlobStore` directly behind a small native adapter with root `DatabasePaths.resolve_user_base_directory(user_id)/"chat_assets"`. This uses byte mechanics only, not Sync enrollment/coordinator/GC. Reserve per-attempt opaque candidate namespace first; publish verified chunks to its immutable namespace/hash key outside the chat transaction. Atomic adoption keeps that key, so ready state needs no postcommit rename. Initially copy external bytes independently for every child; no cross-conversation deduplication. Multiple refs in one child may share that child's claim. Native embedded images retain ordered independent DB bytes through `add_message(..., conn=conn)`.

Candidate cleanup first locks operation/candidates, resolves any committed receipt/claims and fences abandoned generations. Mark only unowned exact candidates `reclaiming`, which makes them non-adoptable, then drain physical writers and unlink outside the transaction. Unknown active outcomes retain bytes. Failed unlink remains a retryable record. Hard purge releases its claims; recoverable soft deletion retains them. Cleanup never deletes another child/source namespace. Normal source asset removal uses conversation-before-asset order, matching fork admission.

**Physical writer fencing:** the native adapter supplies one stable per-candidate filesystem I/O guard outside the deletable candidate/upload directories. Every chunk writer and final publisher acquires it, checks the durable attempt/candidate state under a short DB read, closes that transaction, and only then performs byte I/O while still holding the guard. Cleanup commits `reclaiming` first, closes its transaction, then waits for the same guard, removes exact final bytes **and upload chunks**, and finalizes reclamation before releasing the guard. A waiting stale writer rechecks state and cannot recreate files. No DB lock is held while waiting for the filesystem guard; no byte I/O occurs inside a DB transaction. Reuse existing secure lock-file/platform primitives and exact namespace deletion; the existing blob store's GC-only lock by itself is insufficient because its publisher does not acquire it. Failure to obtain a supported secure lock is explicit unavailable capability. Test suspended chunk publication and final rename, process death, retries and generation replacement.

**Quota authority and limits of the guarantee:** the existing aggregate budget belongs to `StorageQuotaService`/AuthNZ (user and applicable team/org), not ChaCha. Add an operation/candidate-keyed reservation ledger through that service, before any native byte write. It records the expected logical retained bytes once across preparing/adopted states; adoption does not allocate a second charge. Let `L` be legacy usage excluding the managed `chat_assets` tree and `N` the active native ledger. Stored legacy usage counters and their cache entries hold **L only**. Admission and public quota/storage summaries report `L + fresh N` once, with separate native/total fields; never also charge native bytes through `update_usage`. Recalculation excludes the managed native root, stores only L, then returns L+N; it must not write that public aggregate back into the L counter. Apply the same split to applicable shared pools. Native reservations use an uncached current budget read and serialized quota-owner row updates, so two native preparations cannot spend the same remaining allowance. `check_quota`/combined checks include fresh N even when L is cached. Existing non-native and embedded-DB storage keeps its current accounting semantics; H2 does **not** claim to repair existing cross-feature check-then-write races or enforce a new global hard quota. A previously admitted legacy upload may still race the native reservation; qualify and disclose this inherited limit rather than promise serialization that does not exist.

ChaCha stores a quota reservation intent/key before calling the quota service outside its transaction. If the quota response is lost, reconcile the same key before writing bytes. Committed native claims keep the charge. Cleanup releases the charge idempotently only after guarded writer drain and confirmed byte removal; missing/unknown native operation state never frees it. Reconcile reserve-before-native-ack and unlink-before-quota-release crashes; a temporary conservative charge is preferable to uncharged live bytes. No AuthNZ work occurs inside the chat commit. User/team/org identity is derived from authenticated destination scope, not supplied by the client. This uses the existing configured allowance, not a second native allowance. Quota is logical retained-byte accounting as in existing admission, not a guarantee about temporary filesystem peak space; ordinary disk failures still occur before readiness.

Reuse destination limits, including current native 5 MiB/image default, selected image aggregate 32 MiB, and applicable document preflight/storage limits. These differ from completion ingress and must be advertised separately. Revalidate effective limits if configuration changes before commit; no arbitrary H2-specific lower cap. Timeout remains unknown/recoverable, not “over limit.”

Strict fidelity is default. Known missing assets can be reviewed as `unavailable_v1` with child-local ID, safe display label and reason; no dereferenceable source path/credential. This changes request digest. Unknown formats cannot be converted to missing markers without an understood typed projection. Text remains readable; **all** sends/refine/tool paths requiring missing context block before new message persistence or provider/tool dispatch.

Canonical context changes use the PATCH route above. Under one owner transaction, lock conversation then target/reference claims, require expected `asset_manifest_revision` and target revision, and apply only the reviewed mutation. `remove_from_context` marks that reference excluded from future request assembly while preserving safe historical display; it neither cancels a job nor purges retained bytes. `replace` points the target context reference to a verified already-retained claim in this conversation. `restore` additionally requires the known expected original hash; if the original identity is unknown or bytes differ the user must explicitly choose replacement. Retaining replacement bytes is the separate operation above, followed by a patch against its returned current manifest revision. Increment manifest/context fences and return the complete canonical result; stale/wrong-owner requests write nothing. On lost PATCH response the client reloads this owner's manifest and reconciles the desired state; it cannot blindly replay against a newly fetched revision or hide the marker optimistically. A new conflict requires review. Existing browser `useFileUpload` cancellation is not used. Hiding a marker is not resolution. Degraded results do not qualify rich-asset parity.

## 9. Shared client recovery and compatibility

Add a protocol discriminator to client `ForkOperation`; absent means `legacy_native_v1` for native records. Existing local/temporary owners retain their current protocol. Never reinterpret an unknown/partial legacy native operation as `native_atomic_v1`. Capability absence can leave the existing deliberately limited legacy path available before dispatch, with truthful non-atomic outcomes. After atomic dispatch there is no fallback to legacy, local owner, different server or a fresh ID.

Recovery uses the frozen request/owner/scope. `not_recorded` permits explicit same-key submission only; `pending` offers check/resume under the same ID; committed displays **“Copy saved”** independently of opening/result-cache success; gone/expired explain that this operation cannot recreate the child. A deliberate new copy requires another reviewed action. Keep unknown operations visible and recoverable, and never use elapsed client time as evidence of failure.

Every await before/after transport, result persistence, child load and UI adoption checks the originating owner lease. An account/profile/workspace change hides old operation details and prevents stale writes into the new view. Returning to the original owner may resolve it. A client failure writing the committed result preserves the known committed result in that active owner UI; it does not send another creation request.

Server ready/binding/asset metadata, not a browser receipt, enables cold reopen. Every H2 child, including neutral plain children with no snapshot or assets, exposes a bounded `native_bundle` descriptor: version 1, ready state, required projection, canonical settings revision and asset manifest revision. The optional character binding is additional data, not the test for whether a child has canonical native settings. A source that commits typed retention exposes the same projection requirement. Both full-page shells use the common controller and exact scoped proxy methods. Sidepanel expansion preserves selected chat/operation through an extension-local route; no WebUI handoff is used for advanced workflows.

New storage capabilities must be enforced on all mutation/read/send entry points that could lose required typed data. Persist `required_projection_version='native-fork-v1'` on every H2 child and on a source acquiring typed native assets. Clients send `X-TLDW-Chat-Projection: native-fork-v1` on exact detail/settings/message/send/asset routes for these owners; absent/unsupported version returns `409 projection_upgrade_required` before a lossy read or mutation. The header asserts protocol support and never grants ownership. List rows expose a bounded unsupported/ready descriptor so old clients can still list other chats. Protected DB APIs reject legacy sync/import identity or manifest overwrites independently of the HTTP header; a serializer cannot bypass the invariant. Add the header to the existing explicit CORS/proxy allowance. Active enrolled Sync owners reject new H2-native creation/retention until H4 supports the bundle. Already committed native receipt resolution does not re-run source admission; it reauthorizes the child and current access.
