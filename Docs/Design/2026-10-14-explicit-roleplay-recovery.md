# Explicit roleplay recovery — TASK-13676

Ordinary Send must not adopt unfinished original requests. Retain the original input and outcome for explicit recovery. Before potentially dispatching a completion, durably store unknown status; after failures preserve it whenever dispatch occurred. Only proven nondispatch may remain accepted_unsent. Existing explicit original Retry uses frozen owner/input/assistant IDs and may generate another provider reply if none is already saved; state that fact clearly rather than describing it as a read-only check. Preserve all earlier returned text, original account leases and receipt replay. No new server schema/API or automatic expiry retry. ADR assessment: existing ADR-049 and protected original Resume semantics.

Recovery is not a read-only receipt check: explicit original Retry preserves saved identity and may request another generation while an earlier request is still running. That risk must be visible before activation; ordinary Send never assumes this consent. The server guarantees original fences and one saved assistant identity, not exactly one concurrent provider invocation. Provider dispatch/storage controller doubles are identified separately from actual native controller/browser evidence.
