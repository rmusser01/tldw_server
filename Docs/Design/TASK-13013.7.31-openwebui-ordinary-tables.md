# OpenWebUI import table validation

TASK-13013.7.31 fixes a reproduced validation defect: `sqlite_master.type='table'`
includes virtual tables. A valid FTS5 external-content table can therefore pass
the required-column checks and execute an uploaded view's MATCH query during
ordinary user enumeration. The reproduction uses normal data, not corrupt pages.

Use SQLite's parsed `PRAGMA main.table_list` metadata to accept only ordinary
tables for the required import and hydration names. This avoids parsing attacker
supplied CREATE statements or trusting a forgeable root-page field. Views,
virtual tables and shadow tables cannot satisfy the required schema. Preserve
the existing read-only connection, extension disabling and column validation.

This metadata requires SQLite 3.37 or newer. An engine without it must reject
database imports with a clear version error; it must not fall back to the unsafe
check. The retained backend SQLite 3.46.1 satisfies this requirement. Ordinary,
STRICT and WITHOUT ROWID tables remain acceptable. This closes the reproduced
import path and does not claim complete SQLite CVE remediation or release
admission for other database consumers.

Independent review confirmed that table metadata introspection can prepare
expressions in unrelated views. This change prevents accepting the required
virtual table and subsequently reading its external content; it does not claim
that SQLite never parses or prepares uploaded schema expressions.

Verification covers the benign external-content case, all five required table
names, mixed-case/commented SQL, ordinary table compatibility, unsupported
metadata, and existing import/hydration tests. No package or model execution is
needed for the regression.
