## Confirmed scope and corrected component roles

Every Chatbook chat capability should be usable in both the WebUI and the extension's full-page UI. The extension sidepanel is a compact companion with direct chat and run controls, plus expansion into the extension's own full-page UI for larger workflows. Full-page extension functionality must not depend on handing advanced work off to the WebUI.

`tldw_chatbook` supplies the reference chat behaviors and already has local operation, optional synchronization, and server/local handoff foundations. `tldw_server` supplies the destination chat services used by the shared WebUI and extension UI. `tldw-agent` provides execution in an external OS environment on behalf of the server, including the user's machine in a remote deployment. It is not a Chatbook runtime, conversation store, sync service, or a host for an offline browser chat application.

Support tools/actions in server workspaces and in an external environment through `tldw-agent`. Preserve the independently requested local chat operation and optional synchronization through the existing chat/store/sync foundations. Extend those contracts only where a ported feature needs additional state. Do not make new `tldw-agent` chat/storage/sync integration a prerequisite for ordinary chat features.

Keep deployment location, conversation storage/synchronization, model routing, and tool execution target separate. A server can be deployed locally or remotely. A local-only conversation does not opt into synchronization just because a server is reachable. Selecting an external tool target does not move the conversation's persistence owner into that target.

The earlier draft conflated these roles and described its invented local Chatbook-to-agent bridge as approved architecture. That interpretation and the resulting first milestone were rejected by the user. The corrected scope above supersedes them.

Parity means equivalent user-observable behavior and retained state, adapted to browser interaction. It does not require terminal-specific layout, identical keyboard shortcuts, or replacing browser capabilities that already go beyond Chatbook. Native features with platform or rollout restrictions need explicit capability states, not an unconditional promise of availability everywhere.

## Surface and mode qualification

Every applicable row below must be qualified in both full-page surfaces. The sidepanel must preserve the same conversation/run identity and state while using smaller presentations. Expansion opens the extension's full page at the selected conversation, message, run, or artifact; it must not create an accidental second conversation or replay a request.

| Dimension | Required cases |
|---|---|
| Surface | WebUI and full-page extension each qualify local-only behavior in their own browser origin. Sidepanel expands into the extension owner. Sharing a local conversation across WebUI/extension origins requires an explicit transfer or enabled sync. |
| Storage mode | Local-only; local with explicit conversation/dataset enrollment; server-backed. Test both native server and genuinely enrolled Sync v2 paths because their current behavior differs. Temporary chats retain an explicit save lifecycle. |
| Execution | Server workspace; external OS environment through `tldw-agent` acting for the server; no execution workspace when the feature does not require one. |
| Availability | Independently configured model connection versus sync connection; each may fail separately. Verify the WebUI shell can reopen without its hosting/sync server for the promised local mode. External executor availability is another boundary. |
| Lifetime | Change chat, switch surface, reload browser view, restart owning host, and recover according to the feature's actual durability contract. These events must not be conflated. |
| Isolation | Two conversations on different hosts/workspaces; two server users; two authorized clients changing the same synchronized record. |
| Failure | Duplicate delivery, interrupted persistence, stale version, unavailable asset, cancelled turn, pending approval, and incomplete synchronization. |

## Findings that support feature-level work

1. **Common UI is already available.** The work primarily needs contract completion, consistent state ownership, and qualification across transports and lifetimes. Replacing both interfaces wholesale would discard working chat, compare, document, and roleplay functionality.
2. **Existing persistence/sync are foundations, not proof of wire compatibility.** The pinned chat producer/public schema/reverse applier differ. Local storage also lacks an independent ordinary model route. Resolve these specific contracts and consent boundaries within chat/provider/sync work; no Chatbook runtime role belongs to `tldw-agent`.
3. **Forking needs selection, identity and publication semantics first.** Repair unsafe local field copying and ambiguous fallback, define legacy/variant selection and separate revision fences, then implement the exact copy contract through each owner. Native server, browser local/temporary and enrolled sync have different atomic boundaries. The reviewed H1–H4 split keeps all required modes visible.
4. **Server/runner execution has real owners and specific control defects.** Preserve ACP persistence, orchestration, sandbox reattachment and bundled execution. Repair the WebSocket and shared stdio receive boundaries, cancel settlement and common budget admission before relying on independent-child responsiveness. External-host deployment remains a separate qualification.
5. **Compaction and Canvas are semantic work.** A recent-message summary prompt is not a durable context-memory boundary. A recent-artifact list is not a branch-aware revision graph. Each deserves a bounded domain design.
6. **Source behavior has limits and some documentation drift.** Current app-owned runtime code/tests supersede older screen-scoped guide prose for accepted work. Finished-child retention has process-lifetime limits; provider-native compaction is an extension point; speculative voice has rollout limits; Canvas is not currently server-synchronized. Capture these explicitly rather than promising more than the source implements.

## Revised proposal after design review

The first fork proposal was too broad and assumed incompatible persistence paths were interchangeable. The [review][review] records the corrections; the [audit's reviewed contract and H1–H4 gates][audit] define the required result.

Start the history work with authoritative selected-path/legacy semantics, fresh owner-scoped fork identities, and an idempotent recovery contract. Then qualify native server copying, browser local/temporary copying, and synchronized publication separately. The complete fork retains its original acceptance target: selected lineage, rich assets, independent settings/character snapshots, ancestry, source isolation and correct reopen in both full-page clients. A native-only partial release does not complete B01–B03.

Before implementation, settle the contracts used by that delivery: H1 selection/legacy/copy rules; H2 native receipt/assets/character binding; H3 browser commit/cache recovery; H4 sync version/encryption and consent lifecycle. F02 independently covers local model routing and WebUI cold availability. Queue and ACP work does not wait for unrelated sync/provider decisions. All required matrix behaviors remain open until qualified.
