## D1. History selection is client-scoped; accepted context is immutable

**Selection owner.** The conversation owns its graph. Each client view/session owns a tagged cursor, selected variants and a monotonic selection revision. Persist the reopen bookmark under the local profile/client, persistence owner and conversation. Valid cursor states distinguish `after_message(id)`, `before_message(id)` and `empty`; before the first root and an empty conversation must never fall back to the latest message. A synced default/reopen hint may initialize a view without a bookmark. It cannot retarget an open view, its draft, a queue or an accepted turn.

**Admission.** Normal send and fork submit the same versioned projection: owner scope, conversation identity, tagged cursor, selected path/boundary, ordered message IDs and revisions, relevant settings/character/assets digest, interpretation version and originating selection revision. The owner validates authorization and a coherent graph snapshot before accepting it. The accepted attempt records that immutable projection; all resulting messages attach to its parent/path even if another view changes selection. Completion advances the originating view only if its selection revision still matches; other views can explicitly follow the result. Merely changing another view's cursor is not a content mutation and must not stale this request.

History, settings and conversation versions remain distinct. Compare the copied/request-relevant projection when a settings version changes; excluded draft/prefill/summary changes alone do not invalidate a fork. Recheck durable source identity/deletion, graph membership and the captured view's selection. A conversation-wide default leaf is not a second authority. Mutation of retained source content, selected variants, required settings or assets invalidates an unaccepted review. Comparison mode retains its own explicit per-model projection and tests; it cannot silently use whichever normal-chat array is visible.

**Legacy adaptation.** New histories use explicit parent/variant relationships. Automatically interpret an old history only when an authoritative ordered manifest or a valid unique chain accounts for the complete source snapshot. Parentless/mixed/contradictory rows cannot prove ancestry from timestamps. They remain readable/exportable and offer a one-time review of the owner's complete ordered ID list before the first history-dependent mutation. Server legacy display order is `timestamp, last_modified, id`; local legacy order is `createdAt` with stable ID tie-breaking. These are transcript presentation orders, not inferred branch ancestry. The review shows alternatives and permits selecting the intended path.

Freeze the complete ordered IDs, versions and digest for that review; never use the capped/paginated rendered window. Confirmation compares the same owner snapshot and atomically stores the accepted `legacy_linear_v1` projection/bookmark without deleting alternative rows or rewriting content/IDs. A stale snapshot requires a new review. Future graph writes parent to the accepted projection. No universal timestamp-based migration is required.

**Gate (H1).** Two views select different variants; send/fork uses each captured path, and completion cannot retarget the other view. Test before-first rewind, empty history, reopened bookmarks, same-content distinct IDs, source mutation during review, parentless/mixed graphs, equal timestamps, complete histories exceeding UI pagination and a normal continuation after legacy adaptation.

Evidence: the destination currently separates displayed variants from request history ([variant control](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/components/Option/Playground/PlaygroundChat.tsx#L1149)); the owner has explicit legacy query ordering ([message store](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/DB_Management/chacha/message_store.py#L1036)). ## D2. A fork commits once; readiness belongs to each persistence owner

**Operation identity and result.** Freeze an unpredictable operation ID and canonical request digest in the originating owner's pending operation record before dispatch. The namespace includes the authenticated owner/profile, server/account/dataset where applicable and operation kind. Validate that namespace before lookup. A committed same-key/same-digest receipt is resolved before reconsidering source freshness; key reuse with different input conflicts. Reauthorize access to the child before returning its IDs/map/content. Source deletion after a successful commit does not undo that result.

The immutable receipt contains operation/digest, target identity, message map, projection version and commit outcome. It is independent of child deletion/cascade. A child deletion leaves a minimal operation tombstone: replay returns deleted/gone or access denial, never recreates/restores the child. Full result data may follow retention policy, but an accepted key cannot later become a fresh create. Expired keys are rejected; deliberate new fork/restore uses a new operation. An unknown response retains the original pending operation and owner. Neither timeout nor failed lookup authorizes a local fallback or a new request ID.

**Native server.** Stage external blob transfers before the chat transaction under that operation. Inside one native chat DB transaction, revalidate source and asset authority and commit the child graph, independent settings/accepted character snapshot, references, mapping, receipt and ready state. No normal character creation/greeting or newer behavior resolution is substituted. Reuse existing DB abstractions and SQLite/PostgreSQL locking; no network awaits belong inside the transaction. Unadopted staging is reclaimable only after operation reconciliation establishes that no committed reference owns it.

**Browser local.** The corresponding Dexie transaction contains the child graph, owned asset references/blobs or adopted staging references, canonical required settings/snapshot, receipt and ready state. Plasmo settings become a replayable cache for this bundle. Canonical settings remain authoritative for all later reads and edits, not only until initial cache publication. Every cache write carries the canonical settings revision; stale writes cannot overwrite a newer revision, and reopen/send accepts only a matching cache revision or reads the canonical record. It never silently falls back to defaults. Temporary forks use the same projection in their ephemeral owner, with no durable history, receipt, draft or queue written merely by forking. Explicit Save promotes to a durable independent root through its own reviewed operation; temporary host loss has no false recovery promise.

**Local readiness versus replication.** A locally committed complete child is usable immediately with an available independent model, including when enrolled sync is down, paused, disabled or conflicted. Its status is “saved locally” plus the separate pending/conflicted sync state. An outbox entry refers to that committed version; a remote acknowledgment is not a prerequisite for local use. Server-owned native creation is usable after its owner commit. Transport receipt, applied version and remote usable completion are distinct states; the UI must not turn an allocated remote ID or an envelope append into “saved on server.”

For explicitly enrolled child creation, the same owner transaction commits a publication intent with the frozen initial bundle/manifest (or immutable version-addressed members), the child's authorized destination enrollment/policy/consent revision and operation ID. Source enrollment is not inherited upload authority. Bridge that committed intent to the existing external outbox idempotently; a crash before outbox append is repaired from the owner intent. Later local edits produce dependent versioned operations and cannot rewrite the original manifest. Dispatch still checks current consent under D4; a durable intent is evidence of its original authorization, not permission to bypass later disable/detach. Local-only creation has no dispatchable intent; later enrollment is a separate explicit operation.

**Remote publication.** For trusted sync, publish a versioned fork manifest in the existing sync protocol with the complete member IDs/hashes, graph/settings/snapshot projection and required asset references. Sync storage stages received members; a per-owner materialization operation reuses the receipt/replay facilities. The destination chat transaction makes the complete validated bundle ready at once. Missing members/parents remain staged and fetchable/retryable, not partly readable as a ready child. Existing list, direct load, search/export and send paths must all enforce this admission; a separate sync activity entry may show progress. Changes depending on the fork wait for its initial manifest and then apply in dependency order. Transport acknowledgments may advance received progress, but applied/usable progress advances only after owner commit.

Required parents above are members of the child's self-contained graph. The source conversation/fork boundary is inert provenance, not a publication dependency or authority to fetch/upload the source. A child can enroll while its source remains local/private, unavailable or deleted. Preserve only policy-permitted scoped provenance, show an unavailable origin honestly, and populate existing source foreign-key lineage only when that authorized source exists in the destination owner. Otherwise use the versioned provenance descriptor, with no dangling FK or automatic source enrollment. Imported provenance never authorizes access to another account's conversation.

A retry after a crash between chat commit and sync acknowledgment resolves the same operation. Tombstones and authorization revocation supersede pending publication; replay cannot resurrect a deleted child. Unsupported manifest/projection versions stop apply without discarding the envelope or advancing the applied cursor. A dataset capability gate prevents old clients from writing a lossy projection, and they show an upgrade-required state instead of a partial history. Private relay publication follows D4 and completes only in the receiving client owner.

**Assets and copied state.** Preserve the audited allowlist: fresh IDs/remapped references, settled complete/stopped/failed text, eligible replay/citations, declarative policies, accepted character behavior and the selected asset revision. Exclude source mutation authority, live effects/approvals/secrets, drafts/queues, one-shot/pinned prefill and existing summary/compaction memory. Retain independent asset references; deleting either conversation cannot delete bytes still owned by the other. Native and local fork preparation use the destination's existing advertised ingestion/storage limits; reject over-limit work before commit. Do not invent a second upload pipeline.

Missing/unavailable assets are explicit: default fork fidelity requires all selected retained assets. The user may review a degraded copy with an unavailable marker and no dereferenceable source credential/path; that choice changes the request digest. The child can display retained text, but a send requiring missing asset content is blocked until the asset is restored/replaced or explicitly removed from context. Degraded copies are not evidence of rich-asset parity. Blobs use verified content identity, owner-authorized lookup and staged-copy cleanup; URL/path coincidence never transfers authority.

**Gates.** H2 proves native transaction, character reopen and receipt behavior on SQLite/PostgreSQL. H3 proves Dexie/cache recovery, delayed v1 publication after a v2 settings edit, temporary Save and local usability with sync down. H4 proves crash between owner commit and outbox append, local edits before delayed initial upload, staged remote publication, child-only enrollment with unavailable/private source, deletion during transfer, dependency ordering, unsupported writers and received-versus-applied cursors. All include lost response, child deletion then retry, changed permissions, precommit failure, missing/large assets and source isolation. No receipt test waits for an unrelated model/provider feature.

Evidence: [Dexie copy boundary](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/db/dexie/branch.ts#L9), [external settings](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/apps/packages/ui/src/services/chat-settings.ts#L622), [individual sync materialization](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/Sync/v2/server_origin_batch.py#L917), [hard deletion](https://github.com/rmusser01/tldw_server/blob/59049e094e0845a4611ea725ae19b7c1754ea709/tldw_Server_API/app/core/DB_Management/chacha/conversation_store.py#L1389). ## D3. Local operation has a concrete model route and browser execution owner

**Required initial model route (F02).** Reuse the existing server-compatible completion adapter with an independently selected model connection: endpoint, credentials, capabilities and connection revision. A locally deployed existing tldw_server with a local model is the first all-local configuration. The synchronization server may be a different, unavailable remote deployment. Direct-provider browser adapters can extend this route later; they are not an F02 prerequisite. A remote inference endpoint remains an explicit network dependency.

The local conversation owner assembles the complete accepted request. For this independent route, transport sends `save_to_db=false` and no foreign/local `conversation_id`; storage IDs and server mutation versions never leak into a different endpoint's persistence path. Credentials/capabilities are bound to that model connection, not borrowed from the current sync account. Resolve referenced context/assets locally into authorized request data or stop at capability admission; do not send a foreign server resource ID and hope the model host can resolve it. Model use authorizes that selected request's inference transport, not enrollment or conversation upload. Changes to the owning model binding invalidate new admission; an unrelated sync-account change does not cancel or retarget independent inference. Late results remain scoped to the original accepted attempt and cannot write another chat. Reuse the existing scope-lease pattern with the relevant binding instead of watching global sync configuration for every request.

**WebUI availability.** F02 includes an explicitly installed offline shell from the existing shared WebUI build. Cache only versioned application assets and a local entry route after a successful initial install; do not cache authenticated API responses, credentials or server-rendered user data as shell assets. Cold reopen after that install must load local profile/history/settings without consulting remote sync authentication/readiness. A first visit without installed assets is not claimed to work while the host is down. Locally serving the same WebUI is also supported. Browser restrictions, endpoint permissions and connection reachability are checked for the selected configuration before generation; a cached model label alone is not readiness. If browser storage was evicted, report missing local data and allow explicit recovery; never invent successful persistence.

Local-only data is scoped to its local profile in each browser origin. Server logout/switch must not expose another account's mirrored cache. WebUI and extension do not implicitly share Dexie, credentials or runtime; moving a local conversation between them requires explicit transfer or enabled sync. Extension sidepanel/full-page share the extension owner.

**Browser attempt lifetime.** Reuse the shared chat execution code behind a same-origin host, separate from React views: an extension background host for extension surfaces and a shared worker host for WebUI views. The host owns admission, AbortController/transport, accepted attempt IDs, terminal settlement and queues. Views attach/detach observations and send commands; the initiating view's port is not the request lifetime. Extend existing browser messaging/storage rather than creating a second conversation or task database. Platforms unable to provide the required shared host remain unqualified for that lifetime promise.

Only one host generation may own an active attempt, acquired through a compare-and-set lease in the existing local DB. Persist the accepted-attempt marker before external dispatch for durable chats; commands carry attempt and host generation, events carry attempt and sequence. Deduplicate attachment/command delivery and replay the retained projection/events to a new view. Broadcast messages are notifications, not write authority. Stale hosts and callbacks cannot settle another generation. Temporary attempts/queues stay in ephemeral host memory.

Changing viewed chat or expanding the sidepanel detaches the observer, then attaches to the same attempt; it does not cancel or reissue generation. Browser-host/process loss is a different event: reopen reconciles retained accepted attempts, marks interrupted/unknown where the provider cannot prove completion and requires an explicit new attempt. Never replay a request or tool effect automatically to fabricate resume. Losing temporary host state loses that temporary session; expose the existing explicit Save lifecycle. Server-owned ACP/orchestration work retains its server owner under D5 and is not moved into this browser host.

**Gates (F01/F02, C02/C04/C10, A02 and M08/M09 as applicable).** Cold installed WebUI reopen with sync/hosting server down and a separate model ready; local send/Stop/reopen with no upload; model scope change during a held response; sidepanel expansion during streaming with exactly one provider request and retained draft; two views racing admission/Stop; worker loss after dispatch; stale-host settlement; duplicate event replay; storage eviction and temporary host loss. These are separate from H1/H2 and do not delay native fork design.

## D4. Sync trust, enrollment and capability are separate decisions

Continue using the existing outbox, commit proof, Sync v2 transport/storage, receipts and apply owners. The integration target is registered `chat.conversation` and `chat.message`, with versioned payload/operation adaptation in both directions. Never introduce a name-only alias for legacy `chat/upsert/delete` or weaken M1 validation to accept an incompatible encrypted payload.

| Mode | Authority and completion |
|---|---|
| Local-only | No sync dispatch. The local owner can use any explicitly configured ready model route. Reachability never enrolls or uploads it. |
| Trusted sync, first interoperability delivery | Explicit conversation-and-dataset enrollment into `server_trusted_v1`; the enrollment presentation states that the server receives plaintext and may materialize native chat state. Extend public operations/payloads for retained graph, settings/snapshot, revisions and assets; trusted server apply uses D2's transaction/publication boundary. |
| Client-private sync | Preserve `client_private_v1` and its key ownership. Use a separately negotiated version of the existing envelope/relay protocol, encrypted chat payload and metadata-only server storage. Receiving clients decrypt, validate and apply to their local owner. Server-native plaintext chat resume/materialization is unavailable in this mode. Until that version is supported on both ends, show unavailable sync and retain pending work; local chat still works. |

Trusted compatibility and private relay are separate H4 deliveries with explicit capabilities; completion of one is not completion of both modes. Private relay does not change the plaintext authority of pinned M1. It retains encrypted graph/settings/snapshot/asset manifests and encrypts retained asset bytes; public routing fields remain limited to the protocol's metadata-only allowlist. Keys use the existing private-key owner and explicit device provisioning, never sync plaintext credentials. Missing keys remain locked; authentication/hash/decryption failures quarantine unapplied work without moving the applied cursor. Neither an old client nor a server lacking the negotiated version may discard unknown fields and continue writing. Version/capability checks precede enrollment and repeat on reconnect, while already-received work remains recoverable.

Enabling sync cannot relabel a private history/dataset as trusted. A user-reviewed transfer to a new trusted binding is a separate copy operation with explicit disclosure and source preservation. Likewise, selecting an inference endpoint may disclose the selected request to that endpoint but does not grant plaintext sync/storage authority over the private history. Native chat endpoints operate only on server-owned/native or explicitly enrolled trusted conversations; a user's default dataset no longer implicitly changes all conversations' persistence. Per-conversation enrollment and policy determine routing. Until an enrolled operation's required retained-field capability exists, reject it explicitly rather than bypassing sync with an unpublishable direct DB mutation.

**Consent lifecycle.** Pause stops new dispatch under the same enrollment; already accepted work may settle. Disable/detach increments a durable consent revision, stops further batches/local apply and keeps unsent work under its original binding without automatic release. Each batch and apply checks both enrollment revision and existing server/account scope lease. Late success/error may record the original operation receipt for reconciliation only; it cannot restore enrollment, change dataset or authorize another batch. Re-enrollment presents retained backlog for explicit review; remote deletion is a separate action. Received/applied progress never overwrites current consent. This preserves S1's correction.

**Gate (H4 and F04–F07).** Public schema and real owner round trips both directions; normal append, edit, delete/restore and fork manifests; trustworthy received/applied/usable states; same-base conflict resolution; private-mode no plaintext materialization, locked/missing key and unsupported peer; old client write rejection; default dataset with an unenrolled conversation; held transport followed by pause/disable/detach, error/success, restart and reviewed backlog adoption. Existing source/domain tasks are reused. No encryption or enrollment gate is a prerequisite for an unrelated native queue/ACP repair.

## D5. ACP runs own accepted work; observers and controls are fenced

The existing server ACP/orchestration owners persist admission and lifecycle. A session admits at most one active prompt through a common REST/WebSocket transaction; another ordinary prompt receives a busy result. It is not silently queued, concurrent or interpreted as steer. An explicit steer/redirect is a different capability and command. Persist an accepted attempt ID/generation before downstream dispatch; deduplicate the originating command ID and record terminal/cancel/unknown outcome against that attempt.

The complete transport chain must remain responsive: server WebSocket, Python ACP stdio, bundled Go upstream `Conn.Run`, and each Go downstream `Conn.Run`. Dispatch long requests/permission handlers as bounded session/attempt-owned work; no reader awaits a prompt, user decision or free worker slot. Responses and control messages keep a reserved responsive path. Reject excess work explicitly before acceptance rather than blocking the reader or spawning unlimited tasks. Preserve ordered admission/control per session, serialize writes, and settle every pending call/handler on EOF, protocol error, cancellation or shutdown. Review shared Go session state for concurrency and run its targeted race checks. Resource/budget/exhaustion admission and stop enforcement live in the common executor; neither REST nor WebSocket bypasses them.

**Disconnect and approval.** Closing a view/socket only detaches an observer. An accepted run continues under the server owner, and a permission request remains waiting with stable decision ID, owning attempt/generation and server deadline, even if no observer is attached. Reconnect replays current run and pending decision state after authentication/authorization. Expiry denies the permission and settles the wait; it does not imply approval. An explicit Stop, deadline/authorization failure or host-loss transition invalidates the pending decision generation and settles its future. Late/duplicate approval cannot authorize another attempt.

**Cancel targeting.** Every client control carries the accepted attempt ID/generation and idempotent command ID. Under the session admission fence, apply Stop only to that still-active attempt before emitting a downstream session-level cancel. Keep admission closed until cancel/terminal settlement is established; after an uncertain downstream cancellation, mark the session reconciling and do not admit a new prompt on that same unreconciled runtime. A delayed Stop for A can never reach B. If the peer lacks attempt-specific control, the server's serialized admission/control adapter supplies this fence; it cannot forward an unscoped cancel after ownership has changed.

The bundled Go runner must dispatch Python's existing `session/cancel` notification to its cancellation implementation; an empty notification handler is not compatible. Preserve request-form cancellation for compatible callers, without manufacturing a response to a notification. Capture/check the active session attempt generation at control admission and keep downstream forwarding ordered before successor admission; a delayed worker must not look up the newer attempt and cancel it. The actual downstream notification must be observed in the transport fixture, not inferred from a successful server send.

**Host/external target loss.** Persisted transcript and effect receipts survive independently from a live downstream process. If the bundled runner cannot `session/load`, show interrupted/unknown, reconcile completed effects and allow explicit fresh continuation only with the required evidence; never call transcript replay process resume. Capability-gated sandbox reattachment remains useful where supported. Every attempt binds the actual authorized server workspace or external `tldw-agent` environment; host changes/reconnect cannot silently select another target. `tldw-agent` remains the server-directed OS/tool executor, with no Chatbook runtime, conversation-storage or sync role.

**Gate (ACP control repair, A02/A04/A08/F08).** Exercise Python transport through the actual bundled Go runner to a controlled downstream: A waits for permission while B in a different session progresses; disconnect/reconnect preserves A's pending decision; approval reaches the waiting downstream; cancel notification reaches and settles A; late approval and delayed Stop cannot affect the next attempt. Also prove bounded overload and connection-loss settlement. A Python-reader-only fixture cannot qualify this path. Race REST against WebSocket admission, exhaust budget through each route, lose the runner after a completed effect and verify reconciliation without duplicate execution. External-host deployment, PTY and fleet/steer features have their own remaining qualification; they do not prevent this bounded repair.

## D6. Retained corrections and delivery gates

The following prior corrections remain mandatory; D1–D5 do not replace them:

- Queue chains have a stable client-session/cursor owner in the shared host, scoped by persistence owner and conversation. Their evolving selected branch/context baseline survives observer detach. The host admits at most one active attempt per local conversation; a busy result is not a successful dequeue. A second view observes an existing chain or explicitly adopts its context with a queue-version check; merely browsing another branch never substitutes that view's cursor. The controlling session's semantic branch/edit/rewind/compaction or source/policy change pauses pending items. Linear responses admitted on the chain advance its baseline without pausing, while unrelated branch appends do not retarget it. Explicit adoption compares the reviewed context token and queue revision, keeping frozen queued model/settings snapshots distinct. Test A queuing on X, B selecting Y, A detaching, and reviewed takeover after a second context change. Propagate terminal outcomes through both sidepanel layers and pause on direct as well as queued Stop/failure. Reattaching a view cannot resume a paused queue.
- Each accepted voice turn/attempt settles independently. A's delayed save cannot clear B, duplicate final events cannot create another message, and interruption records retained partial text/status before supersession. The selected conversation context/settings/character and persistence owner travel with the accepted request; an attached visible chat ID alone is insufficient.
- Forks clear source pinned/one-shot prefill and existing summaries/compaction memory, including an in-path summary. Preserve declarative policies and accepted character behavior, and test the child's next request after reopen.
- H1 defines selection, safe identity projection and the common operation contract. H2 implements native receipt/transaction proof; H3 implements browser/temporary commit/cache recovery; H4 implements trusted and private sync contracts with separate qualification. H2/H3 may proceed independently after H1. F02 local model/shell and the browser execution host have their own deliveries. Native queue outcome repair and ACP reader/control repair do not wait for unrelated fork/sync/model specifications.
- Every required mode stays in the 90-row inventory until qualified. No row becomes Equivalent from this review. A limited delivery names its unsupported mode; existing failed/precondition-blocked tests are never counted as passing acceptance. A feature specification must supply exact schemas, migrations and tests for its selected delivery, without reopening these owner/behavior decisions or inventing a global prerequisite.
