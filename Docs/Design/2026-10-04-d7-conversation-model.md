## Summary

### The decision in one paragraph

Make the **server conversation the only identity a chat has**. Every chat that is not temporary gets a server conversation id at its first send (this is D1), and every surface (WebUI, extension full page, side panel) addresses it by that id. Each browser origin keeps a **device cache** of server chats (the Dexie mirror that already exists) and, later, a small **outbox** for sends made while the server is unreachable. A side-panel tab becomes a **view**: a conversation id, a position in the message graph and a draft, with no copy of the messages. The server's parent graph is the only place branches live. A send that would silently fork (because the client's view is stale) is refused by the server and shown as "updated elsewhere", on every surface. Generation moves to the server in two steps: first the server **settles turns itself, saves partial replies and records model metadata** (CM-04), then it **runs turns detached from the HTTP request** so a reload or a closed laptop no longer loses the reply, and any surface can re-attach to it.

This is option C in §3 (server identity, device cache, outbox), delivered "A first": the outbox comes last and only if the owner wants offline sends (Q1 in §8).

### Why this model

- **Every reply is already generated by the server.** `pageAssistModel` always returns `ChatTldw` (`ui/models/index.ts:275`). Without the server there is no answer, so a local-first model buys only offline reading and drafting, at the cost of a sync engine.
- **The WebUI and the extension can never share a local store.** They run in different browser origins, so their IndexedDB databases are separate. Only the server can give a conversation one identity across them.
- **Most of the machinery exists.** The server stores a parent graph with versioned, idempotent admission and settlement (`api/core/DB_Management/chacha/message_store.py:700-998`). The client already has a "native" (server) owner for the history-selection controller (`ui/services/chat-history-selection.ts:40-51`) and a Dexie mirror for server chats (`ui/db/dexie/server-chat-mirror.ts`). `/chat/completions` can already admit and settle a turn on the server (`api/api/v1/endpoints/chat.py:4648-4667`). The client just doesn't use that path for saved chats.
- **It matches Notes**, which are already server-only with optimistic `expected-version` writes (`ui/components/Notes/hooks/useNotesEditorState.tsx:1334`).

### What the user gets

- A chat saved on one surface appears, with the same title, branches and Trash state, on every other surface and device.
- Every chat has a link (`/chat/<id>`), and the side panel, full page and WebUI open the same chat from it.
- Continuing a chat that changed elsewhere never silently forks it; the user sees "Updated in another window" instead.
- After step 2 of generation, a reload, a route change or a closed side panel no longer loses a reply. The reply keeps generating, and the chat shows it when the user returns.
- Temporary chats stay on the device and never reach the server.

- **Phase 1 (one identity):** 10 PRs, mostly S–M. Four have a backend part, three of them small. Phase 1 is the D1 work plus its cleanup, so most of it is already scheduled.
- **Phase 2 (resumable generation):** 4 PRs, backend M–L.
- **Phase 3 (offline outbox):** 3 PRs, optional (Q1).

Phase 1 retires the three Stage 1 workarounds this spike was asked to address (§1.3).

## 1. Problem statement

### 1.1 What users hit

The review (§1 theme 4, §7 theme 1) found that "a conversation exists as a side-panel tab snapshot, a local Dexie record and a server chat, and nothing reconciles the three". The defects that trace to this:

| Symptom | Review ids |
|---|---|
| "Saved · Locally + Server" on chats that were never sent to the server | CS-03, XS-05 |
| Past chats can't be found: local chats are listed nowhere, there's no URL, and ⌘K doesn't find them | CS-02, XS-06, XP-05, XP-06 |
| Opening a past chat in the side panel overwrites the current tab | XS-01 |
| Delete and Rename in the side panel act on the tab, not the chat | XS-07 |
| Continuing a chat in the side panel after using the full page silently forks it | XP-08 |
| Pins, recents and UI mode live in different stores per surface | XP-18, XP-12 |
| Hand-offs keep half the context each | XP-09 |
| A reload or route change mid-reply loses the reply; returning can leave an empty server chat | CS-04, CS-N3 |
| The model that wrote an answer is lost after reload | CM-04 |
| Regenerate, Continue and Edit → Save & Send fail on saved chats | CM-01 (via the half-integrated controller, review §1 theme 2) |
| Save to Notes is missing on unsynced chats | XP-01 |

There are two root causes:

1. **Two authorities.** A saved chat is owned either locally (Dexie, owner key `local-history-v1:<profile>`, `ui/db/dexie/history-selection.ts:114`) or by the server (the "native" owner), and the code refuses to mix them (`ownedHistory` rejects server rows, `history-selection.ts:145`). New chats default to the local owner, so they never reach the server (CS-03). Server chats are mirrored into Dexie under a *different* local id (`server-chat-mirror.ts:21-40`), and side-panel tabs copy the messages a third time.
2. **The browser runs the turn.** For saved chats the client admits the user message, streams with `save_to_db: false`, and writes the assistant reply itself afterwards (§2.3). If the page goes away mid-stream, nobody writes the reply.

### 1.2 Why D7 now

Stage 2 slice 9 (D1, "save chats to the server by default") is about to choose *how* new chats reach the server. It could extend today's local-owner-plus-promotion path, or create a server conversation at the first send. The two lead to different end states, and Stage 4 (CS-02 history, XP-05 routes, XS-06/XP-18 parity, CM-04) builds on whichever is chosen.

### 2.2 Identities in play

One conversation can have up to six identifiers today:

1. The server `conversations.id` (a UUID, `api/core/DB_Management/ChaChaNotes_DB.py:1138-1152`).
2. A Dexie `chatHistories.id` for its mirror in the WebUI origin.
3. A different Dexie id for its mirror in the extension origin.
4. A side-panel tab id per browser tab that has it open.
5. A history-selection bookmark per `(profile, client session, owner, conversation)` (`schema.ts:401-404`).
6. Any local-only "fork" of it (`HistoryInfo.root_id`, `parent_conversation_id`, `ui/db/dexie/types.ts:26-30`).

Message ids are mapped the same way (`Message.serverMessageId`, `types.ts:155-157`). Every cross-surface defect in §1.1 is a place where two of these disagree.

### 2.3 How a saved turn is written today

For a chat with a native (server) owner:

1. **Capture.** `POST /api/v1/chat/conversations/{id}/history/selection` returns the whole message graph with fences and revisions (`api/api/v1/endpoints/chat.py:8282-8321`; `ui/services/tldw/domains/chat-rag.ts:1289`).
2. **Admit.** `POST /chats/{id}/messages` with the client's message `id` and `tldw_history_selection_v1` (`chat-history-selection.ts:569-611`). Under an owner lock the server re-resolves the selection, appends the user message with parent = last selected message, and returns `tldw_history_admission_v1` (`message_store.py:700-878`). This is idempotent by message id and intent digest (`:723-741`).
3. **Generate.** `/chat/completions` with `save_to_db: false` (`clientManagedHistory`, `ui/hooks/chat-modes/chatModePipeline.ts:716`; `ui/models/ChatTldw.ts:113-115`).
4. **Settle.** The browser posts the assistant message with `tldw_history_admission_v1` (`chat-history-selection.ts:612-645`, called from `ui/hooks/chat-helper/index.ts:618`). For native owners it strips `generationInfo`, `modelId`, `metadataExtra` and the rest (`chat-helper/index.ts:602-615`). `nativeHistoryMessagePayload` would reject them anyway (`chat-history-selection.ts:473-496`), and `MessageCreate` has no metadata field (`api/api/v1/schemas/chat_session_schemas.py:418-440`).

For a local owner, steps 1, 2 and 4 run against Dexie (`ui/db/dexie/history-selection.ts:662-920`).

**What the server could already do.** `/chat/completions` accepts `tldw_history_selection_v1`, admits the user message in the same transaction, streams the admission back as the first frame, and settles the assistant reply itself when the stream ends cleanly (`api/core/Chat/chat_service.py:4147-4166`; `chat.py:4648-4667, 5744-5755`). The client opts out of this.

### 2.4 Server model facts that shape the options

All verified in code:

- **Parent graph, no stored leaf.**
  - `messages.parent_message_id` (`ChaChaNotes_DB.py:1194-1208`).
  - No `active_leaf` column. `GET /chats/{id}` returns a computed `tail` (newest message by timestamp), `version`, `history_version` and `settings_version` (`chat_session_schemas.py:331-360`).
  - `history_version` is bumped on every message add, edit or delete (`message_store.py:1030-1041`), which makes it a cheap change signal.
- **The server accepts stale parents.**
  - Plain appends only check that the parent is in the same conversation (`api/api/v1/endpoints/character_messages.py:345-351`).
  - Versioned admission takes the parent from the client's selection and rejects only an inconsistent explicit parent (`parent_mismatch`, `message_store.py:745-747`).
  - "Fence changes alone are not evidence of a changed retained path" (`:643`), and settlement deliberately doesn't check the current branch (`:889`).
  - So a stale view forks the chat without error. This is the server half of XP-08.
- **Client-supplied ids.**
  - `MessageCreate.id` is client-supplied and required for versioned writes (`chat_session_schemas.py:420-431`).
  - `POST /chats/` takes no id and has no idempotency key (`ChatSessionCreate`, `:139+`).
  - The idempotent create that does exist is `POST /chats/workspace-startup` with a required `Idempotency-Key` header (`api/api/v1/endpoints/character_chat_sessions.py:4538-4608`).
- **Message metadata.**
  - `message_metadata(message_id, tool_calls_json, extra_json)` exists (`ChaChaNotes_DB.py:2483-2488`) and is returned as `metadata_extra`.
  - Model, provider and `finish_reason` are never written per message. Usage is written only by the character persist route.
  - The client already reads `metadata_extra` (`ui/hooks/chat/useServerChatLoader.ts:372-375`).
- **Search.**
  - The chat list searches titles only (`conversations_fts`).
  - Message full-text search (`messages_fts`) is exposed only within one chat (`GET /chats/{id}/messages/search`).
- **Trash.** After #3154, trashing flags only the conversation, so Restore brings messages back.
- **Sync v2 coexists badly with versioned history.**
  - The server has a cursor-based sync protocol (`/api/v1/sync/push` and `/pull`) with `chat.conversation` and `chat.message` domains (`api/api/v1/schemas/sync_v2_models.py:112-122`), built for the local-first Chatbook client (`Docs/Design/Sync_V2_M1_Implementation_Decisions.md`).
  - When a user has an active Sync v2 profile, every versioned (history-selection) capture and write on a global chat returns 409 `sync_owner_unsupported` (`character_messages.py:423-427`; `chat.py:8299-8300`).
  - No web client uses Sync v2 today (grep of `ui/` and `apps/tldw-frontend/lib`).

### 2.5 Generation and background-work facts

- **Generation dies with the request.**
  - Starlette cancels the response iterator on disconnect.
  - `safe_stream_generator` closes the provider stream in its `finally` (`api/core/Chat/streaming_utils.py:2028-2038, 2085-2126`).
  - The chat path never checks `request.is_disconnected`.
  - Character `complete-v2` does the same (`character_chat_sessions.py:7076-7089`).
- **No partial is ever saved.** The assistant message is written only if the stream was not cancelled, didn't error and produced output (`streaming_utils.py:2191-2196`).
- **No resumable SSE.**
  - Chat frames carry no `id:` lines (`api/core/LLM_Calls/sse.py:42-54`).
  - Heartbeats are off by default (`Config_Files/config.txt:228`, `streaming_heartbeat_interval_seconds = 0`).
  - The only `Last-Event-ID` reader is notifications (`api/api/v1/endpoints/notifications.py:355`).
- **Jobs exists but doesn't fit token streaming.**
  - `api/core/Jobs/` has leases, renewals, cancel, idempotency keys and exactly-once completion, with SQLite or Postgres backends.
  - Its event outbox is off by default and rate-limited (`api/core/Jobs/event_stream.py:84-102`).
  - Workers poll for work, which adds start latency.
  - Chat Macros already runs an LLM call as a job and posts the final output as an assistant message, but without streaming (`api/core/Chat_Macros/jobs.py:163-200`).
- **Closest precedents for streaming plus replay:**
  - **Workflows** writes `llm_stream` deltas to `workflow_events(run_id, event_seq)` and serves `?since=` and a WebSocket that polls the database every second (`api/core/Workflows/adapters/llm/llm.py:177-205`; `api/core/DB_Management/Workflows_DB.py:166-223`).
  - **ACP** keeps a per-process ring buffer with `last_event_id` replay (`api/core/Agent_Client_Protocol/event_bus.py:12-100`).
- **Deployments are multi-process.**
  - Production images run 2–4 uvicorn workers (`Dockerfiles/Dockerfile.prod:76-93`, `Dockerfiles/docker-compose.yml:34`).
  - Redis is optional and off by default (`config.txt:1566-1571`).
  - So any in-memory turn registry is per worker, and a re-attach can land on a different worker.

## 3. Options for one conversation model

### 3.1 Requirements every option must meet

- **R1** One identity per conversation on all three surfaces and across devices (S1/S2 acceptance criteria on #3126).
- **R2** D1: saved to the server by default when connected; temporary chats stay local.
- **R3** No silent forks; a branch is only ever created by an explicit user action (Edit & resend, Regenerate, Branch).
- **R4** Status copy comes from acknowledged state (review theme 1).
- **R5** Keep the strengths listed in review §9: per-tab drafts that survive reloads, per-chat Export, Trash with Restore, read-only share links, and temporary chats staying local.
- **R6** No data loss when migrating existing local chats.
- **R7** Can be built in small PRs behind the existing harnesses.

### 3.2 Option A: server-authoritative with a read cache

**Data model**
- A conversation *is* a server conversation.
- Dexie keeps the existing mirror (`chatHistories` rows with `server_chat_id` and `server_scope_key`, `messages` rows with `serverMessageId`) as a read cache. It is never treated as an owner for new chats.
- The history-selection controller uses only the native owner for saved chats. The local owner remains for legacy local chats until they are imported (§6.4).

**Identity and URL**
- `(server scope, conversation id)`, where the scope is the existing mirror owner key: server URL, auth mode, org and user (`server-chat-mirror.ts:10-17`).
- URL `/chat/<id>`, with `?branch=<leafId>` and `#msg-<id>` as N4 proposes. The extension uses `options.html#/chat/<id>` and `sidepanel.html#/chat/<id>`.

**Side-panel tabs**
- `{tabId, conversationId | temporary, view reference, draft, mode/model settings}`, with no messages.
- Tabs hold views, so two tabs can show the same chat.

**New chat**
- Created on the server at the first send, idempotently, before admission. This needs a client id or an `Idempotency-Key` on `POST /chats/` (small backend change, P3).
- An empty new chat has no server row (avoids CS-N3-style empty chats).

**Offline**
- Cached chats are readable. Send is disabled with the existing plain copy ("Can't reach your tldw server").
- New chats can't be started. The composer draft survives.

**Temporary chats**
- Unchanged: owner "unavailable", never sent to the chats API.
- Q3 asks whether they should survive a reload. Today the side panel's do (via the snapshot) and the full page's don't.

**Branching**
- Only the server graph. A view is a cursor on it (`HistoryViewSelectionV1`, unchanged).
- The server refuses an admission whose parent already has a live child unless the request says it is an explicit branch (P1). This is the R3 guarantee, and it holds on every surface.

**Sync**
- Pull on open, on focus or visibility, and before send. The cheap check is `GET /chats/{id}` → `history_version`, and a full capture runs only when it changed.
- Writes go straight to the server.
- No push channel. Polling on focus plus the server's leaf check (P1) is enough; a server-sent "chat changed" event can come later if polling proves too slow.

**Cost and risk**
- Cost: low. It is D1 done through the native owner plus cleanup. It probably deletes more client code than it adds: promotion, snapshot persistence, the send gate and the save-status observer.
- Risk: low to medium. Sends need a live server (true today in practice, because the server generates every reply). One more round trip on the first send of a new chat.

**Migration:** §6.

### 3.3 Option B: local-first with sync

**Data model**
- Dexie is authoritative on each device. Every conversation and message has a client-generated UUID that the server adopts.
- A background sync engine pushes appends, tombstones and metadata changes and pulls changes since a cursor.
- The obvious base is Sync v2 (`/sync/push` and `/sync/pull`, domains `chat.conversation` and `chat.message`).

**Identity and URL:** the client UUID everywhere; the same URL scheme as A.

**Side-panel tabs:** views over the device's Dexie.

**New chat:** created locally, synced when possible.

**Offline**
- Full reading and composing.
- **No replies**, because generation needs the server (`ui/models/index.ts:275`).
- Offline sends queue just as C's outbox would.

**Temporary chats:** a non-synced flag.

**Branching**
- Messages are append-only, so they merge cleanly.
- Ordering of concurrent sends from two devices becomes a sibling fork after sync, which is exactly the silent fork R3 forbids.
- Preventing it needs a server-side leaf check at sync time, and then a sync conflict UI.

**Sync**
- WebUI and extension stay separate replicas, because they are separate origins.
- Each side-panel instance must observe Dexie changes live (Dexie `liveQuery`).
- Settings, titles and Trash need last-writer-wins or versioned conflict handling.

**Cost and risk**
- Cost: high. A sync engine, a conflict model and a third owner kind in the history-selection controller ("replicated").
- Sync v2 rejects versioned history writes (`sync_owner_unsupported`), so either the history-selection contract or Sync v2 would need rework. Every chat feature would have to be tested against replication.
- Risk: high. Two authorities is the root cause the review found. B formalizes it rather than removing it.

**Migration:** every existing local chat becomes a replica to push; every server chat needs an initial pull into each origin.

### 3.4 Option C: hybrid, server id plus device cache plus outbox (recommended)

This is A plus a durable **outbox**: a Dexie table of writes the server hasn't acknowledged yet.

**Data model**
- A's cache, plus a new `outbox` table (Dexie v17):

  ```
  [scope_key + op_id]   op_id = client message id, or a create/rename op id
  conversation_id       server id, or a provisional client UUID before create
  kind                  create_chat | append_user | rename | trash | settings
  payload               message, selection or settings
  expected_parent_id    for append_user
  state                 pending | sending | failed | conflict
  attempts, last_error, created_at
  ```
- `create_chat` needs a client-supplied conversation id or an `Idempotency-Key` (P3), so a retried create never leaves a duplicate or empty chat.
- `append_user` replays through normal admission. Admission is already idempotent by message id plus intent (`message_store.py:723-741`).

**Identity and URL:** as A. A chat created offline keeps its client UUID as its server id, which is why P3 should accept a client id rather than only an idempotency key.

**Offline**
- Read the cache. Send shows a dimmed bubble, "Waiting for connection", with Cancel and Edit (N11).
- A new chat can be started offline if Q1 says so.
- Replies start when the outbox flushes.

**Conflicts**
- If the chat moved on while the user was offline, the queued admission fails P1's leaf check.
- The UI then offers "Send after the latest message" (re-parent) or "Branch here" (explicit fork), with the text intact. This is the same notice #3161 introduced, now on every surface.

**Temporary chats, branching and sync:** as A.

**Status (N14 and R4)**
- Derived from durable state: no server id → On this device. An outbox entry pending → Saving… or Waiting for connection. Failed or conflict → Couldn't save, with Retry. Otherwise → Saved.
- This replaces #3147's in-memory observer with something that survives reload.

**Cost and risk**
- Cost: A plus about 3 PRs (P15–P17). The outbox is a queue, not replication. Nothing is pulled through it.
- Risk: medium. Replay ordering per conversation must be strictly sequential, and a provisional id must never leak into a URL that is shared before the create is acknowledged.

**Migration:** as A. The outbox is additive.

### 3.5 Baseline D: keep both owners and patch (status quo after Stage 1)

Keep the local owner for new chats, finish promotion, keep side-panel snapshots and the send gate, and add a full-page gate. Listed for comparison only:

- Every surface keeps its own reconciliation code.
- XP-18 (pins), XS-06 and CS-02 each need a local-plus-server merge.
- CM-01 has to be implemented twice, once per owner kind.

## 4. Resumable generation (S3)

### 4.1 What a solution has to cover

1. **Reload or route change mid-reply** keeps the question and the reply (CS-04). #3163 covers this on the same device.
2. **Closing the side panel, sleeping the laptop, or a network blip** doesn't stop the reply.
3. **Another surface or device** sees the reply, including while it streams.
4. **Stop** keeps the partial reply, labelled Stopped (CM-02, N8). **Interrupted** and **length-limited** replies are marked (CM-03).
5. **The model, provider, finish reason and usage** are stored with each reply (CM-04, N9).

### 4.2 Option S3-1: server-settled turns that persist partials and metadata

The browser still holds the stream open, but the server writes the reply.

**Backend**
- (a) For native turns, settle server-side through the existing `/chat/completions` history-selection path (§2.3).
- (b) In `safe_stream_generator`, when the stream is cancelled or errors after producing output, call the save callback with the partial text instead of skipping it (`streaming_utils.py:2191`). Mark it `generation_status: "interrupted"`, or `"length"` when `finish_reason == "length"`.
- (c) Write `model_id`, `provider`, `finish_reason`, `generation_status` and usage into `message_metadata.extra_json` at settlement. This is server-internal, because the server knows these values; `MessageCreate` needs no metadata field for this path.
- (d) Define the allowed metadata keys once. The only client-written replies left are P8's imports of local chats, which reuse the list. `MessageCreate` can gain the same field later, but nothing in this plan needs it.

**Frontend**
- Stop using `clientManagedHistory` for native owners (`chatModePipeline.ts:716`). The client consumes the admission frame and the final `tldw_message_id` frame instead of settling.
- Render `generation_status` as Interrupted, Stopped or Incomplete with Continue and Retry.
- #3163's local-only partial path becomes the fallback for legacy local chats.

**Stop vs interrupted**
- An aborted request looks the same as a dropped connection to the server.
- S3-1 records `interrupted`. The client that pressed Stop labels it "Stopped" locally, and a server-side "stopped" waits for S3-3's cancel endpoint.
- Alternatively, add a tiny `POST /chat/turns/{admission}/stop` that sets a database flag the stream checks between chunks. This only works when the stream runs on the same process, which S3-3 removes as a concern.

**Covers:** 1 (on any device), 4 (mostly), 5. **Doesn't cover:** 2 and 3.

**Cost and feasibility:** S–M backend, S–M frontend. It uses only code that exists. It works the same with any number of workers, because the stream and its save run on the worker that took the request.

**Uncertainty.** Saving after a disconnect runs inside a cancelled task. Starlette's cancellation comes through anyio, which is level-triggered, so any `await` in the `finally` is cancelled again unless it runs in a shielded scope. The existing `finalize_callback(cancelled=True)` already does cleanup there (`streaming_utils.py:2112-2126`), but whether it awaits safely wasn't checked for this spike. P2 must start with a red test that drops the client mid-stream and asserts the partial row exists.

### 4.3 Option S3-2: resumable stream offsets (request-bound, with a grace window)

**Design**
- Add `id: <seq>` to chat SSE frames.
- On disconnect, keep generating for a grace window (for example 120 s) into a per-turn ring buffer.
- A client that reconnects with `Last-Event-ID` within the window gets the missed frames and the live tail.

**Feasibility problems**
- The buffer is per process, and production runs 2–4 workers with Redis off. A reconnect lands on another worker about half to three quarters of the time and finds nothing.
- Making it work needs sticky routing or Redis fan-out, which the Sandbox stream hub does opt-in (`api/core/Sandbox/streams.py:611-640`).
- After the window, the turn is lost anyway. So S3-2 adds most of S3-3's moving parts without durability.

**Covers:** 2 and 3 partly, and only within the window and on the same worker.

**Cost:** M. **Not recommended.**

### 4.4 Option S3-3: server-run turns, detached from the request

**Design**
- **Turn record.** A new `chat_turns` table in ChaChaNotes:

  ```
  id                    = admission input_message_id, or a turn UUID
  conversation_id
  input_message_id
  assistant_message_id  pre-allocated, so settlement is idempotent (message_store.py:955-973)
  status                queued | streaming | completed | stopped | interrupted | failed
  model, provider
  owner_key             captured at admission (api/core/Chat/persistence_service.py:144)
  worker_id, heartbeat_at
  started_at, finished_at
  finish_reason, usage_json, error_code
  last_seq
  ```
- **Start.** `POST /api/v1/chats/{id}/turns` with the history selection, model and settings. Equivalently, `/chat/completions` with `detach: true`.
  - The server admits the user message and creates the turn and the assistant row (`generation_status: streaming`, empty content).
  - It starts generation in an **in-process asyncio task** that the request does not own; Workflows' `WorkflowScheduler` is the precedent.
  - It returns an SSE stream that tails the turn.
- **While generating.** The task appends deltas to a per-turn in-memory buffer with a monotonic `seq`. It checkpoints the assistant row's content and the turn heartbeat about once a second, or every N tokens.
- **Re-attach.** `GET /api/v1/chat/turns/{id}/events` with `Last-Event-ID`:
  - **Same worker:** replay buffered deltas after `seq`, then tail.
  - **Other worker:** send a `snapshot` event with the checkpointed text and `seq`, then poll the checkpoint about once a second (Workflows' WebSocket does exactly this, `api/api/v1/endpoints/workflows.py:4596-4672`) until the turn is terminal.
  - Correct with any number of workers. The worst case is one-second granularity on a non-owning worker.
- **Stop.** `POST /api/v1/chat/turns/{id}/cancel` sets `cancel_requested` in the database. The owning task checks it between chunks, so cross-worker Stop works. The partial is saved as `stopped`.
- **Crash or restart.** At startup, and periodically, turns in `streaming` with a stale heartbeat are settled as `interrupted` with their last checkpoint.
- **Discovery.** `GET /chats/{id}` adds `active_turn_id`. Any surface that opens the chat attaches to it, so a turn started in the side panel streams live in the full page.
- **Limits.** One active turn per conversation, and a per-user concurrency cap through the Resource Governor. The reservation and refund logic in `chat_service.py:6388-6416` moves from the request to the task.

**Why not Jobs for v1**
- Jobs gives cross-worker scheduling and exactly-once completion.
- But its acquire loop adds latency to time-to-first-token, its event outbox is off by default and rate-limited, and nothing in it streams tokens.
- A chat turn is latency-sensitive and short. The in-process task with a database heartbeat gives the durability that matters (the checkpoint) without that latency.
- Jobs remains the path for queued or batch generation later. Chat Macros shows the "post the final output idempotently" half.

**Covers:** 1–5. **Cost:** backend M–L (turn table, task runner, two endpoints, sweep), frontend M (start, attach and cancel replace the client stream and settle). **Risk:** medium. Long-running tasks need the existing streaming idle timeout and maximum size limits applied by the task, not the request.

### 4.5 Recommendation

**S3-1 now, S3-3 next, skip S3-2.**

- S3-1 is small, uses existing server paths and is needed regardless: N8 Stopped and Interrupted states, N9 model chip, CM-04. It also removes #3163's "partial only on this device" for server chats.
- S3-3 then makes the server own the whole turn. It builds on S3-1's server settlement and metadata, so none of S3-1 is thrown away.
- #3163's client checkpointing remains for temporary and legacy local chats, which never touch the server.

**Adopt option C, delivered A first, with S3-1 then S3-3.** Scored against the project's decision framework:

| Criterion | Why C (A first) wins |
|---|---|

### 6.4 Data migration

**Legacy local chats** (Dexie `chatHistories` with `local_owner_key` and no `server_chat_id`, plus older unowned rows):

- They exist **separately in each origin**: the WebUI origin and the extension origin. Each runs its own migration UI.
- They stay fully usable as "On this device" chats under the local owner. No forced migration and no deletion.
- **Save to server** (P8) imports the whole graph losslessly:
  - message ids (kept as server ids, so `serverMessageId === id`)
  - parent links, roles, timestamps, images
  - allow-listed metadata: model, `generation_status`, sources
  - forks via `parent_conversation_id`
- After the server acknowledges, the local row is converted in place into a mirror (`server_chat_id` and `server_scope_key` set, `local_owner_key` cleared). The history id the user had open keeps working.
- The import is idempotent, so a retry after a crash can't duplicate.
- **Account choice:** local chats are "account-independent" (`ui/hooks/chat/useHistorySelection.ts:733-734`). The import always goes to the currently signed-in account and says so ("Save to <server> as <user>"). Bulk import is never automatic (Q2).
- **Legacy linear chats** (no parent ids) are imported with explicit parent links in their stored order, so the server sees an ordinary `parent_graph_v1` chain and needs no legacy review.

**Side-panel snapshots v2 → v3** (P7):

- For each tab, if the snapshot has messages that are in neither Dexie nor the server (temporary tabs, failed saves), write them to Dexie as a local chat first, then drop the arrays.
- Keep the v2 key read-only for two extension releases as a backup.
- Tabs bound to a server chat keep only their reference and view.

**Mirrors:** no migration. They already carry `server_chat_id` and `server_scope_key`.

**Recovery records** (`historySelections.pending_turns`): left as they are. #3163's keep logic continues to process them, and P13 stops creating new ones for server chats.

**Pins:** the full page's `tldw:server-chat-pins` (localStorage) and side-panel tab pins are uploaded once when server-side pins land (XP-18). Conversations have no pin field today, so that needs a small backend change.

**Server data:** none required for this design. Chats trashed before #3154 still restore empty; #3154 describes an opt-in repair job that needs #3153 fixed first.

### 6.5 Rollout and reversibility

- Backend changes are additive and opt-in per request, so old extension builds keep working against new servers. New clients feature-detect the new fields and fall back.
- One frontend flag per phase (`chat.serverIdentity`, `chat.serverTurns`, `chat.outbox`). P4 is the only change to where chats are saved by default, and it is the owner's D1 decision.
- Reverting P4 sends new chats back to the local owner. Chats created in the meantime are ordinary server chats, so nothing is stranded.

## 7. D6: should the side panel get a Notes surface?

**Recommendation: yes, a Notes quick panel, not a Notes editor.**

### 7.1 Why yes

- Notes are already server-only with versioned writes. A side-panel Notes view needs none of the reconciliation that chats needed: it is a view over the notes API, exactly the shape §3 recommends for chats.
- The panel's job is capture next to the page, and today capture is write-only. The context-menu quick-save has no tags and no "Open note" (XS-13). The Clipper route has tags and folders but lives under a separate route (`ui/components/Sidepanel/Clipper/WebClipperPanel.tsx:213, 506-510`). Nothing lets the user find or reopen what they captured (N3).
- Save to Notes from chat answers (N1) needs a destination picker, "Append to…", and that picker is most of a quick panel anyway.

### 7.2 Why not a full editor

- The Notes editor is where Stage 1's worst defects live: NE-01, NS-01, NS-N1 and the save state machine. A third editor host would triple that surface before G01 has stabilized it.
- At 320–420 px the editor's toolbar, wikilinks and preview don't fit (see XS-15 for what the composer alone does to the panel).
- Editing longer notes is a full-page task. "Open in full page" is enough.

### 7.3 Form

A **Notes** tab in the side panel header, alongside Chat, with:

1. **Search and Recent.** The last 10 notes edited or captured, with title, snippet and tags. Search uses the same server search as `/notes`, after NL-01's contract fix.
2. **Capture.** Quick capture with title, tags (prefilled `captured`) and a destination of **New note** or **Append to…**. It reuses the Clipper's destination fields, includes the page selection and source URL, and offers "Open note" in the confirmation.
3. **Light edits only:** append text, add or remove tags, and tick checklist items (the Notes Dock already does this through `TaskChecklistPreview`). All writes go through G01's save state machine with `expected-version`.
4. **Open in full page** for everything else, using `options.html#/notes/<id>` (XP-05/N4).
5. **"Save to Notes"** on chat messages in the panel uses the same capture sheet (N1), with provenance to the chat's server message id. After P4 every saved chat has one, which removes XP-01's main cause.

### 7.4 How to build it

- Extract the list, search and capture body of the Notes Dock (`ui/components/Common/NotesDock/NotesDockPanel.tsx`, about 1,200 lines). Today it is a floating draggable panel that is hidden on mobile (`NotesDockHost.tsx`). Make it a layout-agnostic `NotesQuickPanel`, used by both the Dock and the side panel, so there is one notes "quick" code path, not two.

### 7.5 Sequencing

## 8. Open questions for the owner

Only questions whose answers change the design:

1. **Q1: Offline sends?**
   - Should a user be able to send, and start a new chat, while the server is unreachable, with the message sent automatically on reconnect (option C's outbox, P15–P17)?
   - Or is "read cached chats offline; Send waits for the connection" enough (option A, and N11 shrinks to Stop and "Send after this reply")?
   - Recommendation: A first; decide the outbox after Phase 1 ships.
2. **Q2: Importing existing local chats.**
   - Confirm: local chats stay usable on their device, import is an explicit per-chat or "Save all" action, never automatic, and it always goes to the currently signed-in account.
   - In multi-user deployments, should bulk import be offered at all, or per chat only?
3. **Q3: Temporary chats across reloads.**
   - Today a temporary chat survives a side-panel reload (its messages sit in `chrome.storage.local`) but not a full-page reload.
   - Should "temporary" mean "never leaves this device" (keep a local copy until closed) or "gone on reload" (memory only)?
   - This decides whether P7 keeps a message array for temporary tabs.
4. **Q4: Sync v2 users.**
   - With an active Sync v2 profile, every history-selection capture and write returns 409 `sync_owner_unsupported`, so after D1 such a user couldn't send from the WebUI at all.
   - Is supporting Sync v2 users (the Chatbook desktop client plus WebUI on one account) in scope for this work? If yes, Phase 1 needs a backend task to let versioned history writes emit Sync v2 envelopes.
