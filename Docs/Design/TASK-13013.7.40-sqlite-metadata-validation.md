# TASK-13013.7.40: constrain SQLite import source reads

The OpenWebUI and APKG readers require ordinary tables, but SQLite prepares
virtual-table metadata before `PRAGMA table_list` returns its rows. A tiny,
well-formed database with an unrelated FTS5 `_config` view executes a benign
FTS5 MATCH during that preparation while all required tables remain ordinary.
The behavior was observed with host SQLite 3.49.1 and the exact TASK39 candidate's
SQLite 3.46.1. This establishes pre-validation source-query execution; no
malformed page or native memory-corruption payload was created or run.

The initial persistent read authorizer blocked a single configuration view, but
independent review found a nested configuration view still executes MATCH while
SQLite skips authorizer callbacks during nested virtual-table initialization.
This second case uses only built-in SQL and well-formed FTS data; a custom
function is not required. Host SQLite 3.49.1 and exact-candidate SQLite 3.46.1
both reproduced the bypass and the effect of disabling trusted schema.

Each importer now disables `trusted_schema` immediately after opening its owned
connection and reads the setting back before inspecting metadata. A setting
error, ignored change or unavailable readback rejects the import and closes the
connection. SQLite's native trust boundary prevents FTS5 virtual-table use from
uploaded views even while nested preparation skips the authorizer. A persistent
read authorizer also limits source reads to SQLite's main schema metadata and
the importer's fixed source table names, rejecting view/trigger-origin reads.
OpenWebUI additionally permits the built-in `json_each` reads used by attachment
hydration. A persisted FTS object named `json_each` cannot use that exception to
execute an uploaded view or MATCH search. The authorizer remains active through
hydration and ordinary row reads until the owned connection closes. The generic
ordinary-table helper does not change trust settings or callbacks on
caller-owned connections.

Retain native table-type checking, required columns, case-insensitive Anki table
names, and ordinary/STRICT/WITHOUT ROWID compatibility. Unrelated benign FTS5
objects may remain without executing uploaded-view or MATCH queries. Denied
constructor errors may be suppressed by SQLite metadata enumeration, so the regression
contract is absence of uploaded FTS-view evaluation and MATCH index searches,
together with successful intended ordinary-row reads; rejection of every unused
object is not required. Required view/virtual substitutions must still be rejected.

Tests use real SQLite databases created by ordinary SQL, the real importers,
and a harmless function marker registered on the newly opened source connection.
The nested-view cases use built-in SQL only and inspect native FTS index-search
traces, avoiding a false pass caused solely by denying the custom marker function.
Tests check that markers and index searches remain absent, actual imported data
remains available, hydration retains the same restriction, and caller-installed
authorizers survive use of the generic helper. Existing schema, exporter,
importer and hydration helper tests cover compatibility. No ML/application
workload is part of this fix.

The change does not patch SQLite or alter intentional administrator-selected
whole-database restoration. The latter copies pages that later first-party
searches can query; it remains a separate privileged input/trust decision.
CVE-2026-11822 and CVE-2026-11824 are grouped by SQLite as the same FTS5 bug,
with Debian documenting malformed index pages plus MATCH as the trigger.
