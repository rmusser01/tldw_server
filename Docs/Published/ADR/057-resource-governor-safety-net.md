# ADR-057: Resource Governor ingress safety net

**Status:** Accepted
**Date:** 2026-09-29
**Task:** TASK-13396 (closes TASK-13395)
**Amends:** ADR-018 and ADR-044

## Decision

Resource Governor ingress (`RGSimpleMiddleware`) resolves a policy for every request through one resolver — `route_map.by_path` glob, then the innermost matching `route_map.by_tag` from the served-route index, then a catch-all `default` policy for any other `/api/` path, otherwise ungoverned. Every policy is a per-entity safety net: buckets key on the validated principal (`user:<id>` or `api_key:<id>`), or on `ip:<addr>` for anonymous or invalid credentials, or on `tenant:<id>` when tenant scoping is enabled and the request carries a tenant. `global` (one bucket shared by the whole server) survives only on the three request policies that send email — `authnz.forgot_password`, `authnz.resend_verification`, `authnz.magic_link.request` — because mail capacity and sender reputation are shared resources. No configuration can produce a permanent 429: an unknown or undefined policy ID falls back to `default`, then to a policy compiled into the code; a policy that doesn't list the caller's entity scope still gets its own per-entity bucket instead of being denied; an over-large token reservation is admitted once the bucket is full rather than denied forever. One switch, `RG_ENABLED` (env) or `[ResourceGovernor] enabled` (`config.txt`), turns off every RG-governed enforcement path at once, including the ingress middleware's lazy governor attach, the diagnostics endpoints' governor construction, and the `auth_deps.py` general ingress fallback (`check_rate_limit`); policies still load so diagnostics can report state. One deliberate exception: `auth_deps.py`'s `check_auth_rate_limit` — a 30/min brute-force floor on auth endpoints, not RG enforcement — keeps enforcing even with the switch off.

## Context

Self-hosters were being rate limited during ordinary single-person use. Three problems compounded: fourteen policies charged one `global` bucket shared by every user and every anonymous client at per-user rates (`core.default` covered ~40 route families at 120 rpm, `global`); `route_map.by_tag` never matched because the resolver ran before FastAPI routing, so ~57 tag-only routes and ~659 unmapped routes were ungoverned and miscounted as covered by the startup/coverage audits; and several code paths produced a request that could never be admitted — an unknown policy ID denied at `rpm 0`, a scope not listed on a policy meant no bucket existed at all (the ADR-044 bug class: an anonymous request to a `[user, api_key]` policy got 429 instead of 401), and a token reservation larger than a bucket's capacity could never fit. Identity also collapsed behind the reverse proxy: ingress ran before authentication and keyed cookie-session traffic by client IP, so every WebUI user behind the same proxy shared one bucket; ADR-044 only fixed this for single-user cookie sessions on policies with no `ip`/`global` fallback. `RG_ENABLED=false` did not disable governance either — the governor was still built, and several call sites (auth reservations, media job concurrency, the embeddings and evaluations rate limiters) called it regardless, with two of them (`auth_deps.py`, `Evaluations/config_validator.py`) reading `RG_ENABLED` from the environment directly, bypassing `config.txt`. UAT hit these limits five times, and each time the fix landed in the frontend while "preserving backend governance." See `Docs/Design/2026-09-29-rg-ingress-safety-net-design.md` for the full survey and the WebUI-replay acceptance test.

## Decisions in detail

- **One resolver, one truth.** `Resource_Governance/policy_resolver.py` (`resolve_policy` / `get_policy_resolver().resolve()`) is the only place that decides a request's policy. The ingress middleware (`middleware_simple.py::_derive_policy_id`), the coverage audit, the startup audit, and the RG diagnostics endpoints all call it, so what they report is what is enforced. Resolution order: `by_path` glob (first match, YAML order) → the served route's merged tags, innermost router first, first tag present in `by_tag` wins → `default` for any other `/api/` path → `None` (ungoverned) for everything else, including docs, static files and the frontend.
- **Identity: charge the validated principal, never the proxy.**
  - A multi-user bearer token that looks like a JWT (two `.` separators, not single-user mode) is keyed by its signature-verified `sub` claim (`jwt_service.decode_access_token`; no database access, no revocation check — the route's own auth still enforces revocation, so a revoked-but-correctly-signed token only ever spends its own user's bucket).
  - Everything else that carries a credential — API keys, non-JWT bearer tokens, and the single-user session cookie — resolves through `auth_principal_resolver.get_auth_principal(request)`. That call caches its `AuthContext` on request state, so endpoint auth reuses the same lookup instead of repeating it.
  - Absent or invalid credentials are **not** rejected by the middleware. `_principal_entity` returns `None` on any resolution failure, `_derive_entity` already computed the `ip:<addr>` fallback (honoring `RG_TRUSTED_PROXIES` / `RG_CLIENT_IP_HEADER`), and the request proceeds to the route, whose own auth dependency returns the canonical 401/403. The middleware never answers 401 itself. A failed resolution is not cached, so the route re-validates the same credential once more.
  - When tenant scoping is enabled and the request resolves a `tenant:` entity, that takes precedence over the principal: `middleware_simple.py` only calls `_principal_entity` when the tenant-derived entity does **not** already start with `tenant:`.
  - This closes a bypass: previously an unvalidated bearer or `X-API-KEY` value was hashed straight into an `api_key:` entity, so rotating fake tokens bought a fresh bucket each time. Identity now comes only from credentials that validate.
- **op_id is always server-generated.** The ingress reservation's idempotency key is `str(uuid.uuid4())`, never the client's `X-Request-ID` — a client-supplied, repeatable op_id would let a replayed header return the cached (already-charged) decision without spending another unit.
- **No permanent 429s** (`Resource_Governance/policy_eval.py`, `governor.py`, `governor_redis.py`):
  - An unknown or undefined policy ID resolves to `default`; if `default` itself is missing from a DB-backed store seeded before this change, a `BUILTIN_DEFAULT_POLICY` compiled into `policy_eval.py` is used, so a self-hoster's YAML/DB edit can never stop request admission.
  - A policy whose scopes don't list the caller's entity kind still gets a dedicated per-entity bucket (`entity` semantics) instead of "no bucket exists, deny." A policy's scopes decide which bucket *kinds* exist, never whether a request can pass at all.
  - An MCP tool category with no dedicated policy falls back to `mcp.default` (`MCP_unified/auth/rate_limiter.py`).
  - A token reservation larger than the bucket's capacity is admitted once the bucket is full (draining it to zero) rather than denied forever.
  - Idle, fully-refilled memory buckets are evicted after 10 minutes so an internet-exposed `default` policy governing all `/api/` traffic doesn't grow unbounded per-IP state.
- **Auth double-charge is closed, not doubled.** `_reserve_auth_rg_requests` (`endpoints/auth.py`) skips its own per-IP reservation only when **both** hold: ingress already resolved this exact `policy_id` for the request (`request.state.rg_policy_id`), and both the ingress-recorded entity (`request.state.rg_ingress_entity`, set only on an *allowed* ingress reservation) and the auth-side entity start with `ip:`. The two IP derivations are compared by entity *kind*, not by string, because AuthNZ's trusted-proxy resolution (`ip_allowlist.resolve_client_ip`) and RG's (`deps.derive_client_ip`, `RG_TRUSTED_PROXIES`) can disagree and would never match if compared directly (unifying them is tracked separately, TASK-13144). Reservations keyed on something else — per-email throttles, per-user MFA limits — still apply regardless.
- **Redis token windows are quantized.** `governor_redis.py::_window_members` packs `quantum = max(1, per_min // 1000)` tokens per ZSET member, bounding a per-minute token window to about 1,000 members regardless of how large `per_min` is (chat's token policy runs at 1,000,000/min).
- **The single switch.** `config.rg_enabled()` (env `RG_ENABLED`, then `config.txt` `[ResourceGovernor] enabled`, default `true`) is the only switch every RG-governed enforcement path reads: ingress, auth reservations, chat/embeddings token reservations, MCP admission, evaluations and audio concurrency, the workflows daily cap, and media job concurrency/bytes-per-day all call it directly now (the two direct `os.getenv("RG_ENABLED")` reads in `auth_deps.py` and `Evaluations/config_validator.py` are gone). When it is `false`:
  - the ingress middleware never lazily attaches a governor to `app.state` (`middleware_simple.py.__call__`), so no other call site can find one there either;
  - the RG diagnostics endpoint (`endpoints/resource_governor.py::_get_or_init_governor`) may still construct a `MemoryResourceGovernor` for the one diagnostic call it's answering, but does not persist it to `app.state`, so it stays invisible to every other code path;
  - policy loading still happens, so `GET /api/v1/resource-governor/policy` and friends keep reporting what *would* be enforced.
  - **auth_deps.py's local fallback limiters are not RG, but one of them honors the switch anyway.** `check_rate_limit` and `check_auth_rate_limit` apply an in-process fallback rate limit, multi-user only, to requests RG ingress did not govern (`request.state.rg_policy_id` unset) — a route outside `/api/`, or any route while RG is off. `check_rate_limit`'s 120/min general fallback takes an explicit `honor_rg_switch=True` and returns without enforcing when `rg_enabled()` is false, so disabling RG doesn't leave a hidden cap behind. `check_auth_rate_limit`'s 30/min auth-endpoint floor is a deliberate exception — it is a brute-force guard, not RG enforcement — and keeps enforcing regardless of the switch.
- **Safety-net defaults.** `global` was removed from every policy except the three email-sending policies above; a new `default` policy (`requests: rpm 600, burst 2.0`, scopes `[user, api_key, ip]`) now catches every previously-unmapped `/api/` route. Per-entity limits across the board moved well above normal single-person WebUI/extension/chat use (see the before/after table in the design spec, §3); the numbers are starting points validated by a WebUI-replay regression test, not hard architecture.
- **Config hygiene.** The policy loader accepts only `version`, `policies`, `tenant`, `route_map`, `templates`, `schema_version` at the top level and `by_path`/`by_tag` inside `route_map`; every other key logs a warning instead of being silently ignored (`policy_loader.py`). `Helper_Scripts/ci/rg_route_map_lint.py`, with its allowlist `Helper_Scripts/ci/rg_route_map_lint_allowlist.txt`, fails CI when a `by_path` pattern is dead or fully shadowed by an earlier one, or a `by_tag` key matches no served route.
- **DB policy store upgrade step.** Installs running `RG_POLICY_STORE=db` keep whatever limits and `global` scopes are already in their `rg_policies` table until an operator re-seeds (`python -m tldw_Server_API.app.core.Resource_Governance.seed_db_from_yaml`, optionally `--all`) or edits the DB policies directly; the built-in `default` fallback keeps resolution safe in the meantime.

## Alternatives considered

| Option | Why rejected |
| --- | --- |
| Keep `global` scope on every policy and just raise the shared limit | A single high shared bucket still lets one busy user or one flood starve every other tenant; it does not fix per-user isolation, only delays it. |
| Fix tag-policy matching by hardcoding more path prefixes (as `chat`/`audio` already were) | Doesn't scale to ~57 tag-only routes and drifts from the actual route table; the route index resolves tags generically from what FastAPI actually serves. |
| Deny requests when a policy's scopes don't cover the caller's entity (status quo) | This is the ADR-044 bug class generalized: any scope/entity mismatch becomes a permanent, unfixable-without-restart 429. |
| Compare ingress and auth-side client IPs directly to detect double-charging | AuthNZ and RG resolve trusted-proxy chains independently and can legitimately disagree; a direct string comparison would just never match and silently double-charge every auth-sensitive request. |
| Authenticate every ingress request fully (routed scope checks included) before deriving identity | Needs the matched route, which isn't available before routing; for virtual keys the scoped-token check always fails pre-routing and logs a security warning on every request. |
| Turn `RG_ENABLED=false` into "governor object still exists, just skip `.reserve()` calls" everywhere | Leaves an easy-to-miss call site (as `auth_deps.py`/`Evaluations/config_validator.py` were) that keeps enforcing after the operator turned governance off; the fix instead makes "no governor reachable" the enforced invariant at the two build sites. |

## Consequences

About 716 previously-ungoverned or server-wide-bucketed routes (about 57 through tags, about 659 through `default`) are now governed by generous per-entity limits; this is a safety net, not a new constraint, and is guarded by the WebUI-replay regression test. The aggregate server-wide request cap is gone except for the three email-sending policies — a distributed flood across many entities is no longer bounded in aggregate by RG itself; that remains the reverse proxy's job. Turning `RG_ENABLED=false` off now also disables media, workflows, auth-reservation, and the `auth_deps.py` general fallback (`check_rate_limit`) enforcement that previously stayed on regardless of the switch — this is intentional (the switch is now honest) but means "off" is more consequential than before. The one deliberate exception is `check_auth_rate_limit`'s 30/min auth-endpoint brute-force floor, which is not RG enforcement and stays on either way. Memory-backend buckets remain per uvicorn worker process (compose files default to 2–4 workers), so effective limits are that many times higher and less even under the memory backend; operators who need exact limits should use `RG_BACKEND=redis`. Invalid credentials on a governed route now reach the route's own 401/403 instead of an early middleware response; this is deliberate and tested (`test_middleware_cookie_owner.py`). DB-backed policy-store installs must re-run the seeding step (or edit their DB policies) to pick up the new limits and the `global` removal — they are not upgraded automatically.
